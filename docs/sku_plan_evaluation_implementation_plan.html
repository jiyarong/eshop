Technical Proposal / 2026-09

SKU 多规则诊断与 Planner：Plan / Evaluation 体系

把每周生成的经营计划、运营动作、经营结果和下一周期决策连接成可追踪、可复盘、可持续学习的闭环。

汇报对象：技术总监范围：Rails + ActiveJob + ERP AI周期：周一至周日
摘要 现状 生命周期 数据模型 Evaluation 历史 Context 流水线 实施与验收

汇报摘要

目标是形成“Diagnosis → Plan → Action → Evaluation → 下一周期 Planner”的周度闭环。

1 个周期每个 SKU 每个自然周一个 Planning Cycle
3 个状态维度生命周期、执行情况、效果评估分别管理
4 周默认历史近期完整历史 + 长期异常摘要
推荐决策：Evaluation 单独建表；Plan 增加自然周字段；用周期级 Job 串联评估、诊断和 Planner；is_latest 只保留为页面展示指针。

现状与缺口

  • Plan 已有关联 Action、执行状态和当前计划标记。
  • 已有 action 效果诊断可以计算逐周利润、库存和漏斗变化。
  • Plan 当前只有生成日期，没有明确的计划执行周期。
  • 动作匹配依赖 latest.active.retained，旧计划可能无法接收晚到动作。
  • Planner 当前只拿最新诊断事件，历史 Evaluation 尚未进入实际输入。
  • 现有 recurring 配置中 Planner 处于停用状态，需先完成流水线和幂等改造。

生命周期设计

Planning Cycle

pending→generating→active→closed→evaluated

failed 可以从生成或评估阶段进入，支持安全重试。每个 SKU 每个自然周只保留一个当前 revision。

Plan 条目

维度状态含义
生命周期active / cancelled / expired计划是否仍具有业务效力
执行情况not_started / partial / executed / not_applicable运营动作是否已经发生
评估情况pending / insufficient_data / evaluated / failed是否已经完成效果判断
关键原则：executed 不等于 evaluated。动作完成后仍需等待完整观察窗口。

周期窗口

period_start       # 周一
period_end         # 周日
execution_deadline # 周日 + 1~3 天宽限期

数据模型

Plan 表扩展

ec_ai_sku_operation_plans
  planning_period_start :date
  planning_period_end   :date
  execution_deadline    :date
  execution_status      :string
  evaluation_status     :string

保留 plan_date 作为生成日期，保留 is_latest 作为页面辅助指针。

Evaluation 表

ec_ai_sku_operation_plan_evaluations
  plan_id
  observation_from / observation_to
  execution_status
  effectiveness / confidence
  summary
  metrics / evidence / action_ids
  conversation_id / evaluator_version
  status / evaluated_at

使用 unique(plan_id, observation_to) 支持下一周初评和后续延迟复评。

长期演进：Planning Cycle 父表

第一版可以只给 Plan 增加周期字段。后续需要重跑版本、审批或计划集合级审计时，再增加 ec_sku_planning_cycles。

Evaluation 方案

  1. 查询上一自然周的所有 Plan，不使用 is_latest。
  2. 读取关联的 OperationAction，判断执行、部分执行或未执行。
  3. 复用逐周指标查询，采集利润、销量、库存、广告和销售漏斗。
  4. 先计算确定性指标，再由专用 Evaluation Agent 解释效果。
  5. 持久化原始指标、动作证据、AI 结论、置信度和版本。
执行情况效果处理方式
executedpositive / negative / mixed保存前后指标和 AI 解释
partial任意明确实际执行范围和未执行部分
not_started不判定负面记录未执行原因或等待补充数据
数据不足inconclusive允许后续观察窗口重新评估

Planner 历史 Context

Planner 输入分成当前事实和历史经验两部分。当前 Diagnosis 负责本周期决策，历史 Evaluation 负责提醒过去的效果、副作用和重复失败。

  • 默认传最近 4 个周期。
  • 8~12 周内的负面、不确定、未执行和重复计划额外保留。
  • Conversation Context 保存历史 Plan ID、周期和 Context 版本。
  • 完整历史保留在业务表中，输入模型时进行压缩和限长。

周度流水线

数据同步完成
评估上一周期 Plan
执行本周期 Diagnosis
构建历史 Context
生成本周期 Plan
执行并记录 Action

使用按 SKU、按周期幂等的 Pipeline Job。Planner 必须等待当前周期所有规则完成，不能只依赖两个相邻 cron 时间。

实施分期与验收

PHASE 01

周期与数据结构

增加自然周字段，创建 Evaluation 表，回填旧数据，补齐时区和周期边界测试。

验收：每个 Plan 都能回答“属于哪周、何时执行、是否等待评估”。

PHASE 02

执行归属与 Evaluation

调整历史 Plan 动作匹配，抽取逐周指标逻辑，实现 Evaluation Runner 和幂等写入。

验收：下一周每条上一周期 Plan 都有执行状态；已执行计划有指标和效果结论。

PHASE 03

Planner 历史 Context

实现 Context Builder，接入近期完整历史和长期异常摘要，保存输入版本。

验收：Planner 能区分有效、无效、未执行和数据不足。

PHASE 04

周度编排与灰度

统一串联 Evaluation、Diagnosis、Planner，增加周期锁、失败重试和灰度开关。

验收：连续运行 4 周不重复生成周期、不丢失历史，失败可安全重试。

PHASE 05

运营页面闭环

在 Plan 详情页展示执行状态、评估状态、指标和结论，并补齐 I18n 文案。

验收：运营可以从 Plan 看到计划、动作、结果和下一步建议。

重点风险

风险控制措施
新周期覆盖旧周期使用周期字段和 revision，禁止删除历史 Plan。
动作未关联计划扩展 Matcher；无法自动判断时提供人工关联。
数据尚未稳定以数据覆盖率和自然周结束作为评估门槛。
AI 误判因果保存原始指标、同期动作、数据缺口和置信度。
Planner 早于 Diagnosis使用 Pipeline Job 或周期完成状态。
首期建议：先落地周期字段、独立 Evaluation 表、下一周初评和最近 4 周 Context；Planning Cycle 父表、延迟复评和结构化成功指标作为后续增强。
