# Ozon 打托盘工作台：开发与实现方案

日期：2026-10-16。本文记录已落地的首版设计与实现边界；平台写入能力仍需按后续阶段实测接入。

## 1. 目标与已确认的业务选择

形成完整流程：选择 Ozon 店铺和集群 → 筛选缺货 SKU → 自动或手动选品 → 计算并调整托盘 → 保存确认并占用库存 → 填写、绑定 Ozon 供货单 → 跟踪供货与库存交接。

用户已确认：

- “发货单号”主要指 **Ozon 供货单号**。
- 补货按完整外箱 **向上取整，优先补足缺口**；不得突破实际可分配库存。

建议首版边界：

- 仅支持 Ozon；从自有/FBS 侧库存补向 Ozon 集群，使用计算器的 `ozon_fbo` 规则。库存来源叫 FBS 不表示使用 `ozon_fbs` 收货规则。
- 一份计划对应一个店铺、一个目标集群，可包含多个 SKU、多托盘。
- 一份计划首版绑定一个 Ozon 父供货单；按实际子供货 `supply_id` 分配托盘。不同子供货、最终仓不混托。平台拆成多个父单时拆分本地计划，首版不建立任意多对多绑定。
- 首版从已有 Ozon 供货单进行绑定和状态回读；自动创建供货申请、预约、上传货位和打印平台标签作为后续独立功能。
- 草稿可以保存；点击“确认方案并占用库存”才成为有效库存承诺。自动计算、预览、普通保存不占用库存。
- 沿用当前 SKU 共享自有库存池。店铺和集群是需求维度，不应各自拥有一份相同库存。自有仓精细库位/批次拣货不是首版范围。

这些边界是建议的开发默认值；除上面两项已确认选择外，不应描述成用户已逐项确认。

## 2. 仓库现有能力与缺口

| 现有能力 | 实现入口 | 本次用法与缺口 |
|---|---|---|
| Ozon 按 SKU/集群计算补货缺口 | `app/services/ec/ozon_warehouse_recommendation_query.rb` | 复用销量、库存、目标天数与缺口口径；补充计划占用、稳定集群 ID 和批量查询 |
| 集群报表 | `app/views/reports/ozon_warehouses.html.erb`、`ReportsController#warehouses` | 增加“进入打托盘工作台”链接；工作台本身也能选择店铺与集群 |
| 托盘计算 | `app/services/pallet_packing/{rules,calculator,fees}.rb` | 作为唯一几何装箱计算内核；新增多 SKU 编排及指定单托的复核 |
| SKU 包装资料 | `Ec::SkuDimension` | 使用外箱长宽高、毛重和每箱件数；缺失项明确阻断自动选入 |
| SKU 账面库存 | `Ec::SkuInventoryOverview`、`Ec::Inventory::BookLedger` | 当前集群页 FBS 值来自 `available_stock = ledger_total - platform_sellable - platform_inbound`，是跨店铺共享的 SKU 数量 |
| 自有实物推算 | `Ec::InventoryPhysicalReconciliationQuery`、`Ec::InventoryFbsStatusMatrixQuery` | 可复用出库、退回和待履约事实，需批量化并区分实物在库与可分配 |
| 平台供货同步 | `app/services/raw_ozon/syncs/supply_orders.rb` | 已同步父单、子供货、SKU、数量、目的仓和集群 ID；增加本地计划对账入口 |
| 审计、权限、通用控件 | `Ec::Auditable`、`WeeklyProfitReports::AccessScope`、`app/views/shared/` | 复用，补充计划管理权限与本次模型审计字段 |

需要在开发前明确的事实：

1. 当前计算器一次输入限制 1～5 个 SKU，最多输出 100 托。`max_skus: 5` 应视为当前计算策略/产品限制，不能未经核实宣传为 Ozon 通用平台限制。
2. 当前算法是稳定条带分区的启发式计算，优先覆盖 SKU，再增加装载体积，不承诺三维装箱全局最优。
3. 集群页按仓库快照中的 `promised` 计算集群在途；SKU 总在途另取 `fulfillment_type=inbound`。两者不能直接相加。
4. `PlatformInboundInventoryQuery` 当前只把 Ozon `IN_TRANSIT` 计为平台在途；实物推算从 `ACCEPTED_AT_SUPPLY_WAREHOUSE` 等状态就判为已离开自有仓。这两个口径存在时间差。
5. `RawOzon::SupplyOrderItem` 每次同步会删除并重建，不能把它的本地数据库 ID 作为长期绑定键。
6. 已有供货明细的 `quantity` 不能直接当作实收量；当前没有完整标准化的逐 SKU 实收字段。部分收货自动化需要补足真实数据来源。
7. 当前供货全量同步每天 08:30、20:30；库存快照每小时刷新。状态时效需要单独改善。

## 3. 页面与操作流程

### 3.1 工作入口

建议入口 `GET /reports/pallet_workbench`。

- 选择 Ozon 店铺，再选择该账号下的有效集群；从分仓报表进入时预填店铺、集群。
- 以 `account_id + macrolocal_cluster_id` 标识集群，同时保存名称快照，不用集群名称作唯一标识。
- 当前报表有名称分组，遇到同名不同 ID、无法映射的名称需显式处理；未知集群可展示数据，不能确认发货计划。
- 切换店铺/集群时处理未保存修改；已有草稿保留所属店铺和集群，不跨目标直接搬运已确认方案。
- 顶部展示目标天数、销量统计区间、库存与供货同步时间，以及返回分仓报表入口。

### 3.2 SKU 工作区

建议页面以 SKU 表格为主，辅以选品汇总和方案编辑区，沿用 ERP 布局、颜色、字体与现有表格组件。

建议首版列：勾选、SKU/商品名、运营人员、平台商品标识、集群销量/日均销量、集群可售、覆盖天数、平台待收、已有本地计划量、基准缺口、本次可补缺口、自有库存/已占用/可打托、每箱件数、建议箱数与件数、包装资料状态。

筛选：

- SKU/SPU、关键词、运营人员、开发人员。
- 缺口大于指定件数、覆盖天数小于指定值、有销量/零库存。
- 自有可打托库存至少一箱、包装资料齐全、已有计划/未计划。

排序：本次可补缺口、覆盖天数、日均销量、可打托库存、SKU。空值排最后，排序后分页。默认缺口降序，同分按销量和 SKU 稳定排序。

表格中明确区分“件”和“箱”。已选 SKU 不因翻页、重新筛选而静默丢失。

### 3.3 一键自动选择弹窗

建议选项：

- 范围：我运营的 SKU / 当前筛选结果中的全部可见 SKU。
- 条件：本次可补缺口大于 N 件，默认 N=10，严格使用 `> 10`；可选低覆盖天数、零库存且有销量。
- 只选包装齐全、平台商品绑定明确、可打托库存至少一箱的 SKU。
- 目标覆盖天数，默认沿用分仓报表 28 天，可调整且不超过现有上限 180 天。
- 数量：默认整箱向上取整；可手工修改每个 SKU 的箱数。
- 可选限制本次最多生成的托盘数；不设置时也遵守计算任务上限。

先预览命中的 SKU、箱数、件数和排除原因，再加入当前方案。自动选品针对全部筛选结果执行，不能只处理当前表格页。

自动选品不会自动确认库存占用。重复点击不产生重复行；再次生成可预览替换或补充结果，不能静默覆盖手工调整。

### 3.4 方案编辑区

- 显示每托 SKU、每 SKU 箱数/件数、尺寸、货重/毛重、总高、装载利用率和排布图。
- 支持增加/减少箱数、移除 SKU、增加空托、将箱数移到另一托、重新计算。
- 首版手动调整以 SKU/箱数/分托/朝向为单位，不实现任意三维坐标拖拽。
- 每次修改调用同一服务端计算内核。对用户指定的一托必须返回恰好一托，且数量完全一致；不能静默把超限托盘拆成两托后称原方案通过。
- 包装参数修改默认只保存在本计划快照；修改 SKU 主资料走原有尺寸维护入口和权限。
- 显示剩余未分配 SKU/箱数、库存不足、超缺口件数、资料缺失和校验错误。
- 草稿可保存不完整结果；确认占用前必须数量守恒且通过全部本地硬性检查。

### 3.5 计划列表与详情

建议 `GET /reports/pallet_plans`、`GET /reports/pallet_plans/:id`。

列表按店铺、集群、创建人、本地进度、平台状态、供货单号和日期筛选。

详情包含：托盘清单、包装/计算快照、计划量与平台量对比、Ozon 父单与子供货绑定、状态轨迹、库存占用来源、异常及同步错误。

用户输入 Ozon 供货单展示编号，也可输入平台 `order_id`。按当前店铺账号查找本地已同步单据；展示编号和平台 ID 分字段保存。单据未同步时进入待匹配，由后台定向查询，不能伪造绑定成功。

## 4. 缺口与数量计算

保留现有报表的销量时间边界、用户时区、日均销量精度和目标天数口径；共享计算方法，避免工作台另外实现一套。

```text
目标需求件数 = ceil(集群日均销量 × 目标天数)

基准缺口 = 分仓报表现有 distribution_gap

本次可补缺口 = max(目标需求件数 - 集群可售 - 已承诺补货覆盖量, 0)

目标箱数 = ceil(本次可补缺口 / 每箱件数)
库存支持箱数 = floor(自有可打托件数 / 每箱件数)
建议箱数 = min(目标箱数, 库存支持箱数)
建议件数 = 建议箱数 × 每箱件数
```

“已承诺补货覆盖量”按同一供货事实去重，包含当前集群的有效本地计划和平台待收供货。同一批货不能同时作为“本地已计划”和“平台在途”再次减少缺口。

`promised` 与供货明细不作简单加法：选定一个可追踪的主要来源，另一个用于对账；无法解释的差额标明数据不一致。首版建议以明确子供货明细为补货承诺来源，旧报表基准缺口继续单列，差异给出说明。需要连同集群页统一展示时再共用该新口径，并补旧报表回归。

供货完成后，承诺覆盖量交给实际 FBO 可售库存；没有实收或上架证据时不能机械清零或与库存双计。无法对应的数量进入待对账，不能伪造为已上架。

例：缺口 13 件、每箱 10 件、可打托 25 件，建议 2 箱/20 件，并标注超缺口 7 件；若可打托只有 15 件，则建议 1 箱/10 件，剩余缺口明确展示。

零销量、缺少绑定或库存缺失的 SKU 不自动推断补货量；允许有权限用户手动加入并保留原因。

## 5. 计算架构与逐托合规

在 `PalletPacking::Calculator` 外增加 Ozon 计划编排服务，不复制几何算法。

1. 根据缺口、覆盖天数和销量对候选 SKU 排序，形成有限候选池。
2. 明确每 SKU 的剩余箱数，尝试不超过当前内核输入上限的组合，调用既有计算器。
3. 比较紧急需求满足量、托盘数与装载率，选择可行组合；扣减剩余箱数并继续。不要直接按 SKU 顺序每五个固定切组。
4. 每个最终托盘重新验算，核对件数、箱数和所有 SKU 的数量守恒。
5. 搜索有固定候选范围和上限；超过任务容量时明确要求分批，不返回被截断的“完整方案”。

优先保证缺货补充和数量边界，再优化托数/利用率。不能为了装满托盘擅自增加某 SKU 的计划量。

当前 Ozon FBO 计算参数为：底面 120×80 cm、含托高度不超过 220 cm、货重不超过 800 kg、超边不超过规则允许值且默认不超边。规则快照日期为 2026-10-14；实际发运前核对当前目的仓、交付方式与平台约束。5 SKU 是当前工程限制。

合规分层：

| 层次 | 检查 | 执行时点 |
|---|---|---|
| 输入 | 有效 SKU/Listing、正整数箱数、尺寸/毛重/装箱数、库存足够 | 计算与确认 |
| 几何 | 高度、重量、外廓、朝向、支撑、无重叠、逐托数量守恒 | 每次自动/手动修改后 |
| 供货归属 | 同托仅一个账号/供货/子供货与最终仓、商品条码明确 | 绑定及发运前 |
| 平台准入 | 目的仓可接收、品类/危险品/温区等限制、平台货位要求 | 发运前 |
| 实物 | 外箱承压、固定、包装与标签、实物数量一致 | 打包完成/交接 |

计算器目前不验证特殊品类准入、实物承压和标签。界面分别展示“本地验算通过”“平台规则待核验/已核验”，不得仅靠几何成功就宣称全部合规。

平台货位校验接口已有仓库内研究资料，但尚需核实当前实际 schema 与账号能力。若接口校验要求先创建货位，它属于独立平台写入动作，不藏在“重新计算”中。首版未接通时，由运营针对具体供货完成规则核验，记录依据后才能进入可发运状态。

费用可复用现有 `PalletPacking::Fees`；缺少路线报价仍显示未知，不补 0，首版不自动推荐“最低运费”方案。

## 6. 数据模型：建议四张核心表

| 模型/表 | 主要字段与用途 |
|---|---|
| `Ec::PalletPlan` / `ec_pallet_plans` | `plan_no`、`store_id`、`platform=ozon`、集群 ID/名称快照、创建/负责人员、本地状态、Ozon 单号输入及 `order_id`、可选父单引用、统计时间/时区/目标天数、规则与数据快照、`lock_version`、确认/发运时间 |
| `Ec::PalletPlanItem` / `ec_pallet_plan_items` | 所属计划、`sku_code`、明确的 `sku_product_id` 与平台 SKU/条码快照、缺口快照、每箱件数、计划箱数/件数、包装参数、发出/实收/退回等已确认事实 |
| `Ec::Pallet` / `ec_pallets` | 所属计划、托序号、对应 `ozon_supply_id`/仓库、计算指标、布局 JSON、校验结果和规则版本 |
| `Ec::PalletItem` / `ec_pallet_items` | 托盘与计划 SKU 行关联、箱数/件数、分区/朝向；支持一个 SKU 分到多个托盘 |

约束：

- 计划号唯一；托序号在计划内唯一；计划内每 SKU 对应一个明确平台商品。
- 正整数箱数、件数与装箱数一致；托盘行数量汇总等于计划行数量。
- 核心数量、状态和业务键用普通列；布局、规则与证据使用 JSONB。
- 同店铺同一内部 SKU 对应多个 Listing 时，自动选品排除并提示指定；不能把同一缺口复制到多个 Listing。
- 原始明细长期绑定用 `account_id + order_id + supply_id + platform_sku_id`，必要时带 `bundle_id`；不得引用会被同步重建的原始明细主键。
- 首版禁止同一父供货单被多个有效计划重复完整绑定。父单多集群或内容超出计划范围时阻止直接绑定，要求拆分或明确处理。
- 不另建一张可独立修改的库存占用总量表。占用从计划行、状态和绑定供货事实计算，避免产生两套库存真相。
- 接入现有审计，记录数量、状态、绑定、包装和人工核验的变化；发运后不允许改写原装箱方案，后续差异作为事实对账记录。

索引按实际查询补充：计划的店铺/集群/状态，计划行的 SKU/计划，托盘的计划/序号，以及供货自然键。Migration 必须通过 `rails generate migration` 生成。

## 7. 状态与库存占用：核心验收点

本地作业进度和平台供货状态分开：

```text
本地：draft → reserved → packing → packed → dispatched → closed
                     ↘ cancelled（仅未实际出库数量可直接释放）

平台：保留 Ozon 原始状态，单独显示，不用它覆盖“已打包”等本地事实。
绑定/同步异常：作为独立异常信息，不自动改成取消或失败放回库存。
```

| 场景 | 占用处理 |
|---|---|
| 草稿、选品预览 | 不占用，注明未保留库存 |
| 确认、拣货、打包完成 | 占用对应 SKU 件数，所有 Ozon 店铺/集群工作台共享扣减 |
| 仅绑定平台 `DATA_FILLING/READY_TO_SUPPLY` | 绑定不是出库；本地/平台同批承诺去重后继续保留 |
| 本地已发出，平台尚未同步 | 保留未被基础库存计入的出库桥接量，不能释放后重新分配 |
| 平台出库事实已计入基础实物数量 | 该部分由基础库存扣减接管，移除重复的本地额外扣减 |
| 只取消未出库计划 | 释放对应未出库件数 |
| 已发货后取消、拒收、逾期、平台数量变化 | 转待对账；未有退回入库证据的数量不重新可分配 |
| 部分接收或分批到货 | 按 SKU/子供货的数量处理，父单状态不能整单释放 |
| 同步失败、未知状态、回退或过期响应 | 保留已有可靠事实和占用，显示异常，不能当作取消 |

### 7.1 建议的可分配库存口径

不建议简单执行 `现有 fbs_available - 所有 active 计划件数`。现有 FBS 值是账面自有侧，并非实物仓可拣货量；其平台在途也没有逐供货来源证据，无法可靠证明某条计划已被扣过。

建议工作台单独建立**批量可分配库存查询**，以已有实物收支规则为基础，明确分出：

```text
工作台可打托 = 推算在自有仓的合格实物
             - 尚未出库但有效的 FBS 客户订单承诺
             - 去重后的本地打托/平台供货承诺
             - 本地已发出但平台基础出库尚未计入的桥接量
```

- “合格实物”排除已知不可售/待检数量，并明确其证据；盘点调整沿用项目现有口径。
- 不直接使用 FBS 矩阵的 `not_departed_quantity` 作订单承诺，它包含取消订单；按有效业务状态筛选，取消且未发货的订单不占用。
- 同一供货对应的本地量与平台量按绑定关系合并；数量不一致时保守保留尚未解释的承诺并报差异，不直接相加，也不自动改写原计划。
- 已出库按同一事实自然键逐行识别；判断基础已扣减必须与本次库存计算使用同一数据版本。若使用快照，需保存来源贡献及版本，不能只比较时间。
- FBO 平台可售、`promised`、平台在途快照用于需求判断及对账，不再另扣一次自有实物。
- 保留现有分仓页 FBS 账面值作参照，工作台明确显示“推算自有在库 / 订单占用 / 打托占用 / 可打托”。与账面值不同需可查看差额，不静默替换全站库存定义。
- 这一查询只批量复用现有事实与规则，不逐 SKU 调用完整实物详情服务。

首次上线前，用代表性 SKU 对比账面自有侧与实物可分配池；无法解释的 SKU 显示待核对并阻止自动确认。需要统一分仓页 FBS 展示时，应共用本查询并明确标签变化。

### 7.2 去重示例

假设合格库存 100 件、没有其他承诺，计划 A 确认 30 件：

| 时点 | 自有基础数量 | 本地额外扣减 | 可再分配 |
|---|---:|---:|---:|
| 确认计划 | 100 | 30 | 70 |
| 绑定未发运供货单 | 100 | 同批承诺合并为 30 | 70 |
| 本地发出、平台未同步 | 100 | 出库桥接 30 | 70 |
| 平台出库已进入同版本基础数量 | 70 | 0 | 70 |
| 平台已完成收货 | 70 | 0 | 70 |

不能在发货时短暂回到 100，也不能因为本地与平台都记一遍而降到 40。若其中 10 件拒收，只有取得实际退回自有仓的证据后，这 10 件才重新进入可分配池。

### 7.3 并发与一致性

- 确认、增量修改、取消和绑定都通过统一服务，在事务内完成。
- 对涉及的共享 SKU 按稳定顺序加锁，重算全局可用量，再更新计划。仅锁计划本身无法防止两个不同计划争抢库存。
- 使用计划 `lock_version` 拒绝覆盖别人已保存的调整。
- 单纯加锁只保护遵守同一协议的写入方；平台订单/供货同步可能带来新的外部占用。相关本地写入接入同一锁顺序，异步外部变化触发占用重算与不足告警，不宣称能阻止平台独立接单。
- 当前计划编辑时排除自己的旧占用，再验证新总量；不能每次保存累计扣减。
- 重复提交、重复绑定、重复同步幂等。未知状态、缺失记录和过期响应保留可靠数量，不能释放库存。

## 8. Ozon 绑定与自动状态同步

绑定前比较：账号、父单 ID/编号、集群、子供货、最终仓、平台 SKU 和件数。不同账号同号不冲突匹配；只按编号或 SKU 相似度不得自动绑定。

建议沿用现有原始同步，增加两个动作：

1. 原始供货事务提交成功后，按受影响供货键入队本地计划对账。`upsert_all` 不触发模型回调，需要显式调用。
2. 对仍活跃、待匹配或待对账的绑定供货，增加定向状态刷新任务，建议每 15 分钟；保留早晚全量同步作补漏。

状态变化不是唯一触发条件：同状态下 SKU 数量、子供货、集群、目的仓变化也要对账。定向与全量同步共享解析/写入逻辑，避免两套标准。

不得以本次 list 未返回某订单就推断取消。绑定、刷新失败保留最后成功状态，记录错误与重试；过期响应不能覆盖新数据，按平台更新时间和请求版本处理。

对同步取消单后原始明细清空的现状，保留本地绑定快照与前次数量证据，不能因明细消失丢失占用来源。

已有 `Ec::SupplyOrderChangeRecorder` 继续记录平台运营动作；本地草稿/计算/确认不能伪造成平台已执行的供货动作。

## 9. Rails 实现拆分

建议采用 Controller + ERB + Turbo/Stimulus，HTML 与 `.json` 保留相同业务服务。

| 责任 | 建议实现 |
|---|---|
| 工作台数据、筛选排序 | `Ec::PalletWorkbenchQuery`，复用/提取分仓指标，按当前店铺与集群限定 |
| 共享可分配库存与承诺去重 | `Ec::PalletPlans::AvailabilityQuery`，批量查询与来源明细 |
| 自动选品与多托编排 | `Ec::PalletPlans::AutoPlanner`，调用 `PalletPacking::Calculator` |
| 确认/调整/取消 | `Ec::PalletPlans::Update`，统一事务、校验与锁，不依赖零散模型回调 |
| 绑定与平台对账 | `Ec::PalletPlans::OzonReconciler` + 后台定向刷新 Job |
| 页面 | `Reports::PalletWorkbenchesController`、`Reports::PalletPlansController`；避免继续扩大 `ReportsController` |

命名可在实现时按项目已有服务风格简化，不引入跨平台通用物流框架。

复用组件：负责人筛选、SKU/SPU 选择、日期范围、可搜索枚举筛选、排序表头、`table_viewport`、Turbo 抽屉、现有计算器 SVG 与交付说明。组件使用唯一 DOM ID，所有展示文案补齐中/英/俄 I18n。

权限：查看沿用 `view_reports` 和 SKU 可见范围；创建/调整/确认/取消需要独立 `manage_pallet_plans` 业务权限。查询、自动选品、计算、绑定和保存均在服务端重验可见 SKU。库存扣减必须包含其他人已建立的有效承诺，但不能泄露其无权查看的计划详情。管理员或仓库操作角色按既有角色体系赋权。

GET 页面请求只读；平台刷新和所有写入通过显式 POST/后台任务。计算预览本身不发起平台写入。

## 10. 分阶段交付与验收

| 阶段 | 交付 | 验收重点 |
|---|---|---|
| A：数据口径与基础模型 | 批量可用库存查询、承诺来源去重、四表、状态/事务/权限、样本对账 | 跨店铺/集群不重复分配；基准与实物差额可解释；确认/取消与并发测试通过 |
| B：可操作的工作台 | 店铺/集群入口、筛选排序、自动选品、多 SKU 编排、手动调整、保存/确认、计划列表/详情 | 超过 5 SKU 可分托；向上取整受库存约束；每托同内核验算；刷新不丢计划 |
| C：Ozon 联动闭环 | 按编号绑定、子供货映射、自动状态回读、定向刷新、差异和退回处理 | 绑定不重复扣；出库交接无瞬间释放；同状态数量变化、取消、部分收货均有测试 |
| D：平台执行扩展 | 创建供货草稿/预约、上传货位、平台规则核验、标签 | 实际账号验证当前 API；平台写入独立、可追踪、幂等 |

A～C 完成后才构成本次需求的完整交付；D 为后续增强。平台实收数据缺失时，C 必须提供人工核对数量与证据入口，不能宣称部分收货已全自动闭环。

建议按阶段拆提交，先完成库存与数量规则，再接 UI 和平台自动化。实施工期在样本对账和当前接口核实后估算，避免把库存口径补齐隐藏在页面开发中。

## 11. 必须覆盖的测试与性能验证

1. 需求：只统计所选店铺/集群；缺口阈值严格 `> 10`；目标天数、用户时区和现有精度一致；向上取整、库存不够一箱、零销量、空值和多 Listing 歧义。
2. 计算：多于 5 SKU 的多托方案；手动增减与跨托移动；单托超高/超重/超边/朝向限制；指定一托不得静默拆托；箱数/件数守恒；任务上限明确报错。
3. 占用：草稿不占、确认占、修改自身不重复、未发货取消释放；跨店铺/集群同 SKU、两个并发计划竞争；发出未同步、已计入基础、完成、拒收及实物退回。
4. 平台：同号不同账号、同单多子供货、多集群、数量/仓库不一致、同状态改数量、明细重建/清空、重复/失败/乱序同步、部分实收、终态后纠正。
5. 权限：无查看/管理权限、越权 SKU/店铺/计划 ID、只见部分 SKU 的整单修改限制、其他人占用仍参与共享可用量。
6. 页面：筛选/排序后分页、跨页选择、自动选择作用于全部结果、Turbo 错误与保存反馈、HTML/JSON 一致、三种 locale。
7. 性能：新增列表不得逐 SKU 调用 `inventory_overview`/完整实物详情；SQL 聚合、Relation 子查询、预加载；关闭 query cache 比较未缓存 SQL 次数、最大 SQL 长度和实例化记录数，批量场景检查查询次数增长。

运行相关 Rails 服务/模型/Controller 测试，并回归现有托盘计算器、Ozon 分仓、供货同步和库存测试。纯算法可独立测试；新增 Stimulus 做语法检查。不要求打开浏览器验收或运行前端 build。

代表性本地数据仅做只读对账与性能测量；不触发平台 API、同步或生产写入。明确区分服务测量和整页请求测量。

## 12. 开始编码前的首轮核对

不用再阻塞式询问已确认的供货单号和向上取整选择。实施第一步应拿代表性样本核对以下事实：

- 选定店铺（例如入口示例的 `store_id=3`）的账号、稳定集群 ID、SKU/Listing 绑定和包装完整率。
- 账面自有侧与实物可分配池是否存在影响可发数量的差异；同一批货在 `promised`、平台在途和供货明细中的关系。
- 一个真实供货单的展示编号、父 `order_id`、子 `supply_id`、集群和目的仓结构。
- 部分接收/拒收的实收数量从何处取得；没有可靠接口数据时落实人工证据入口。
- 目的仓平台规则、品类资格和标签核验方式，明确“本地计算通过”到“可实际发运”的门槛。

这些是实现所需的数据核对，不应把尚未核实的推断写成已经成立的接口能力或库存事实。

## 13. 单托工作流交互优化（2026-10-16）

- 默认“一次只打一托”，保留多托计划。左侧精简需求表，右侧同步展示当前清单、数量、货重、含托高度和货重容量；人员、SKU 条件及包装参数按需展开。列表每页 15 条，跨页清单保持在同一标签页。
- “一键推荐一托”从当前全部筛选结果中，按剩余缺口、日均销量、SKU 编码排序选取前 5 个可补货 SKU，再用现有几何内核裁减到一托。它是确定性启发式推荐，不保证全局最优装载率，也不保证所有候选都能进入这一托。
- “清单适配一托”沿用当前清单选品与箱数上限，自动裁减为一托；替换前保留一次撤销。普通箱数变更等待 650ms 后自动验算，不会静默裁减或拆成多托。超容量、超过 5 个 SKU、超库存和无效输入会阻止保存。
- 推荐结果同步裁减清单、重排 SKU 索引并保持保存的箱数/件数一致。保存前仍重新检查库存与几何约束；草稿不占库存。编辑已确认方案时，预览与自动选品排除自身占用，并继续检查整单 SKU 权限。
- 当前标签页保留清单、装托模式、收货/费用参数和分配；服务器方案版本变化时丢弃旧版本地清单。修改期间返回的旧验算结果不会覆盖更新后的输入。三种 locale 同步更新。
- Chrome 实测：店铺 3、集群 4039、2026-09-18 至 2026-10-15，推荐为 1 托 / 3 SKU / 21 箱 / 39 件，货重 351.6kg，含托高 218.5cm。验证了自动验算、单托超容量拦截、当前清单适配、撤销、分页/刷新恢复、库存明细显示和多托模式；未写入真实供货或占用库存。
- Rails 验收：`bin/rails test test/services/ec/pallet_plans test/controllers/reports/pallet_workbenches_controller_test.rb test/controllers/reports/pallet_calculators_controller_test.rb`；另通过 Stimulus 语法检查。
- 本地 development 只读服务测量（关闭 query cache，不代表整页请求）：WorkbenchQuery 全量 152 个 SKU，24 条 SQL、最大 SQL 14386 字符、实例化 6608 条、约 1035ms；单托 Build 的 5 个候选，16 条 SQL、最大 SQL 1682 字符、实例化 530 条、约 165ms。未触发平台 API、同步或补数据。
