# 01 现有 SKU 详情抽屉改造

## 结论

本次直接改造现有 SKU 详情抽屉，不新建 V2 抽屉。

“V2”只是本次产品改版名称，不是新的路由、Controller、layout、Turbo Frame 或页面入口。

明确禁止新增以下平行实现：

- `/v2/reports/skus/:sku_code` 路由。
- `sku_detail_v2` Controller action。
- `sku_detail_drawer_v2` layout 或 Turbo Frame。
- 一套长期与旧抽屉并存的 V2 partial。

## 保持不变的技术入口

- 路由继续使用 `GET /reports/skus/:sku_code?tab=...`。
- Controller 继续使用 `ReportsController#sku_detail`。
- 外层 Turbo Frame 继续使用 `sku_detail_drawer`。
- Layout 继续使用 `app/views/layouts/sku_detail_drawer.html.erb`。
- 抽屉外壳继续复用 `app/views/shared/_overlay_drawer.html.erb`。
- 主页面继续使用 `app/views/reports/sku_detail.html.erb`。
- 所有现有 `sku_detail_drawer_link` 调用方无需改成新入口。

## 这项研发具体要做什么

01 只改造现有抽屉的导航和加载机制，不实现生命周期、利润、漏斗、库存等业务内容。业务内容由后续研发包分别完成。

### 任务 1：整理现有 Tab 注册

在 `ReportsController` 中保留一份明确的 Tab 白名单和兼容映射，避免 Tab 判断分散：

| 最终参数 | 内容研发包 | 迁移方式 |
|---|---|---|
| `lifecycle` | 02 | 新增；02 完成后才进入正式导航 |
| `profit` | 04 | 原参数不变，04 直接替换现有内容 |
| `sales_funnel` | 05 | 原参数不变，05 直接替换现有内容 |
| `ads` | 09 | 继续使用现有内容 |
| `inventory` | 06 | 原参数不变，06 增量改造现有内容 |
| `warehouses` | 07 | 原参数不变，07 合并送仓内容 |
| `operation_actions` | 08 | 原参数不变，08 替换现有内容 |
| `search_terms` | 09 | 继续使用现有内容 |
| `ozon_chats` | 09 | 继续使用现有内容 |
| `basic` | 09 | 继续使用现有内容并补齐负责人 |

兼容参数：

- `operation` 继续映射到 `sales_funnel`，直到确认没有旧入口使用后再移除。
- `supply_orders` 在 07 完成前继续显示原内容；07 完成后映射到 `warehouses` 的送仓记录区域。
- `costs`、`stores`、`trend` 等隐藏旧参数在兼容期内保持现状，不突然返回 404。
- 未知 `tab` 回到当时的默认 Tab。

### 任务 2：严格限制当前 Tab 加载

调整 `load_sku_detail`：

1. 公共 Header 数据每次抽屉首次打开加载一次。
2. 只有当前 Tab 对应的 loader 可以执行。
3. 不得因为打开基础配置而运行利润、漏斗、库存、广告或仓库查询。
4. 重趋势继续使用独立懒加载 Turbo Frame。
5. Tab Frame 请求只返回该 Frame，不重新渲染整个抽屉。

需要对现有无条件加载的销售数据和公共筛选数据逐项判断：仅当前 Tab 使用的内容移入对应 loader；真正属于 Header 的内容才保留公共加载。

### 任务 3：在原有 Tab 内逐块改造内容

任务 3 不是更换 Tab 组件或新建一套 Tab。除生命周期外，后续研发都在原有 Tab 参数、链接和 Turbo Frame 内修改业务内容：

- 04 保留 `profit` Tab，在其现有 partial 中逐步改造利润内容。
- 05 保留 `sales_funnel` Tab，在其现有 partial 中逐步改造漏斗内容。
- 06 保留 `inventory` Tab，在现有库存内容上增加店铺库存和历史趋势。
- 07 保留 `warehouses` Tab，在现有分仓内容中并入送仓记录。
- 08 保留 `operation_actions` Tab，在现有运营记录内容上增加趋势和节点分析。

`lifecycle` 是唯一新增的业务 Tab，由 02 完整实现后再加入导航。原 `supply_orders` 不是重做为新 Tab，而是在 07 完成后并入 `warehouses`。

每个原有 Tab 可以按模块分批完成，但同一次上线不能在同一功能区域同时保留两套新旧实现。某个新增模块未完成时，原有可用内容继续保留；禁止先挂不可用的占位模块。

### 任务 4：最终调整导航顺序

导航顺序最终为：生命周期、利润归集、销售漏斗、广告、库存概况、分仓管理、运营记录、搜索词、Ozon Chat、基础配置。

导航顺序不是 01 单独上线的硬前置：

- 02 未完成前，不显示空的生命周期 Tab，默认 Tab 保持当前可用页面。
- 02 完成并上线后，加入生命周期并将其设为默认 Tab。
- 07 未完成前，保留独立送仓入口；完成后再从导航移除并设置兼容映射。
- 每次导航变化都必须保证所有可见 Tab 有完整可用内容。

### 任务 5：保留参数与访问模式

- 抽屉内切换保留 `locale` 和该 Tab 自己的筛选参数。
- 不把利润筛选参数带入库存等无关 Tab。
- 整页访问、抽屉首次打开、抽屉 Tab Frame 三种模式都要工作。
- 已有 JSON 响应不因 HTML partial 调整而改变。
- Header 在抽屉内切换 Tab 时不重新请求和闪动。

## 01 完成后的实际效果

01 单独完成后，用户看到的仍然是同一个 SKU 详情抽屉，业务内容基本不变。可观察到的变化只有：

- Tab 切换和 URL 更稳定。
- 打开某个 Tab 不再运行其它 Tab 的重查询。
- 旧参数仍然可访问。
- 后续模块可以在原有 Tab 内逐块改造上线。

01 不负责交付“完整 V2 页面”。

## 测试要求

在现有 `ReportsController` 测试中补充：

1. `sku_detail_drawer` 请求仍使用原 layout 和 Frame ID。
2. 每个 Tab Frame 只渲染自己的内容。
3. 使用测试替身或查询计数证明非当前 Tab loader 没有执行。
4. `operation`、`supply_orders` 和隐藏旧参数兼容。
5. 未知参数回默认 Tab。
6. 整页、抽屉、Tab Frame 和 JSON 请求均正常。
7. locale 和 Tab 内筛选参数正确保留。
