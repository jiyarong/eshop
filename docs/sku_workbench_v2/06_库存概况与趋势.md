# 06 库存概况与趋势

## 目标

沿用现有库存数据粒度，回答以下问题：

1. SKU 当前总库存是否安全，采购中、账面可用、平台在库分别有多少。
2. 库存分布在哪个平台和店铺，是否存在库存分配不均或局部缺货。
3. 最近八周库存和覆盖天数如何变化，变化是否与运营动作相关。
4. 普通预测日销量与严格预测日销量分别是多少，严格预测排除了哪些断货日、使用了哪条计算路径。

本模块以现有库存详情为基础增量改造。主要新增内容是“历史库存与趋势”和“严格预测日销量”展示，其余工作以字段名称统一、现有数据重新编排和店铺维度补充为主。

## 已冻结粒度

- 库存保持现有 `SKU + 平台 + 店铺/账号 + fulfillment_type` 粒度。
- 同一店铺同一内部 SKU 的多个 Listing 合并展示。
- `sku_product_id`、WB `nm_id`、Ozon `platform_sku_id` 不作为库存表或库存快照的新维度。
- 页面不得将店铺库存平均或按销量拆分给 Listing。
- 账面可用、采购中等内部 SKU 共享库存只在 SKU 汇总展示，不下摊到平台、店铺或 Listing。
- Listing 只能作为店铺绑定关系的说明信息，不返回 Listing 库存、Listing 覆盖天数或 Listing 库存趋势。

## 页面结构

库存概况按以下顺序展示：

1. SKU 库存概览。
2. 平台 / 店铺库存分布。
3. 历史库存与趋势。
4. 现有库存明细 Tab：待入库、账面可用、平台在库、退货。

现有明细 Tab、分页、公式说明和 Turbo Frame 局部刷新能力保留。本次不重做库存同步链路，也不改变库存详情抽屉的打开方式。

## 研发任务拆解

### 1. SKU 库存概览字段调整

复用 `Ec::InventoryPageDetailQuery`、`Ec::SkuInventoryOverview` 和现有库存详情顶部指标，统一展示：

| 展示字段 | 数据口径 | 改造类型 |
|---|---|---|
| 采购中库存 | 正常采购批次中尚未入账的有效数量 | 复用现有字段 |
| 账面可用库存 | SKU 账面库存 | 复用现有字段 |
| 平台在库 | WB `fbw` + Ozon `fbo` | 复用现有字段并明确名称 |
| FBS 库存 | 各店铺 `fbs` 合计 | 从现有最新库存层级汇总 |
| 预测日销量 | 现有 7/15/30 天加权预测 | 原“日均销量”改名 |
| 周转天数 | 账面库存 / 预测日销量 | 复用现有字段 |
| 周转天数（含采购） | （账面库存 + 采购中库存）/ 预测日销量 | 复用现有字段 |
| 严格预测日销量 | 排除全平台断货日后的动态预测 | 新增展示，复用现有算法 |
| 严格预测覆盖天数 | 账面库存 / 严格预测日销量 | 新增展示 |

具体任务：

1. 将库存模块内用户可见的“日均销量”统一改为“预测日销量”，同步补齐 `zh`、`en`、`ru` locale，不修改底层字段名 `daily_sales_velocity`。
2. 核对现有顶部指标中的“平台库存”“海外可用”等旧名称，按上表统一页面文案；只改展示名，不借此改变计算口径。
3. 在查询结果中显式返回 FBS 合计，避免 ERB 自行遍历库存层级计算。
4. 普通预测为 `nil` 或 `0` 时，覆盖天数显示空值，不显示无穷大，也不得以其它预测值兜底。
5. 顶部指标继续使用当前库存详情的紧凑指标布局；严格预测及覆盖天数的视觉形式与生命周期顶部汇总项一致。

### 2. 普通预测日销量解释

普通预测沿用 `Ec::InventoryVelocityMetricsQuery` 的当前算法，不新建预测逻辑。查询层应返回与最终结果同源的结构化解释，至少包括：

- 统计截止日期和 7、15、30 天窗口。
- 各窗口总销量、实际天数和日均销量。
- 各窗口权重：50%、30%、20%。
- 最终预测日销量。
- 该普通口径不剔除断货日的明确说明。

页面在“预测日销量”标题旁展示信息图标，鼠标悬停、键盘聚焦或点击后可查看说明。ERB 只负责格式化，不得在页面重复计算窗口均值或最终预测。

### 3. 严格预测日销量展示

“严格预测日销量”不是新算法，定义为生命周期顶部已经展示的“断货修正预测日销”，直接复用 `ErpAI::DynamicDailySalesForecast`。库存模块与生命周期模块必须读取同一个服务结果，避免两个页面出现不同预测值。

查询层需要返回完整结构：

- `forecast_daily_sales`：严格预测结果。
- `snapshot_period.from/to`：使用的库存快照周期。
- `snapshot_days`：周期内实际快照天数。
- `valid_days`：剔除断货后的有效天数。
- `stockout_days`：被剔除的全平台断货天数。
- `calculation.path`：`cold_start`、`stable`、`rising`、`declining` 或 `no_valid_days`。
- `calculation.s7/s15/s30`：各有效销售日窗口均值，存在时展示。
- `calculation.historical_s7`、`calculation.slope`：趋势判断使用值，存在时展示。
- 当前营销 Stage，以及清仓阶段上涨时按稳定路径处理的说明。
- `strict_cover_days`：账面库存 / 严格预测日销量。

页面要求：

1. 严格预测日销量和严格预测覆盖天数放在 SKU 库存概览顶部，卡片形式、数值精度、信息图标和生命周期顶部板块保持一致。
2. 信息浮层展示实际返回的快照周期、快照日数、有效日数、断货剔除日数、计算路径、S7/S15/S30 和最终结果，不只展示一段固定公式。
3. 固定公式说明继续通过 I18n 管理；路径名称、空数据提示和清仓规则说明也必须进入 locale。
4. 无快照或无有效日时展示明确的“暂无可用预测数据”状态。服务当前返回 `0` 时，展示层必须能够区分“真实预测为 0”和“没有有效数据”，判断依据使用 `calculation.path`，不得只看数值。
5. 严格预测计算截止到用户时区的昨天，与生命周期模块保持一致；页面 GET 只读快照和订单，不触发快照采集。

为防止重复调用，建议抽取一个库存预测结果组装器，或让 `Ec::InventoryPageDetailQuery` 一次性返回普通预测、严格预测及两者覆盖天数。生命周期查询可继续复用相同的严格预测服务，不要求本次重构全部生命周期代码。

### 4. 平台 / 店铺库存分布表

在 SKU 汇总下新增或调整店铺库存表。每一行代表一个 `平台 + 店铺/账号`，同店多个 Listing 仍只有一行。

字段如下：

| 字段 | 口径 |
|---|---|
| 平台 | `wb` / `ozon` |
| 店铺 | `store_id` 对应店铺；无法映射时显示账号标识 |
| Listing 数量 | 该 SKU 在该平台店铺绑定的 `Ec::SkuProduct` 数量 |
| FBS | 该店铺最新 `fbs` 库存合计 |
| FBO / FBW | Ozon `fbo` 或 WB `fbw` 库存合计 |
| 在途 | 该店铺最新 `inbound` 库存合计 |
| 上周净销量 | 上一个完整自然周、按订单与 `Ec::SkuProduct` 硬关联口径统计 |
| 预测日销量 | 仅在已有可靠店铺预测口径时展示；否则显示空值 |
| 可售覆盖天数 | （FBS + FBO/FBW）/ 店铺预测日销量 |
| 含在途覆盖天数 | （FBS + FBO/FBW + 在途）/ 店铺预测日销量 |
| 最新同步时间 | 该行库存 level 的最晚 `synced_at`，使用 `display_time` |

具体任务：

1. 扩展 `Ec::SkuInventoryOverview` 或 `Ec::InventoryPageDetailQuery` 的店铺行，使 `fbs`、`fbo_fbw`、`inbound` 分桶直接由查询层返回。
2. 上周净销量必须遵循项目订单与 SKU 的硬关联策略，同时限定平台、店铺和平台商品 ID；禁止使用 `ec_order_items.sku_code` 兜底。
3. 盘点项目是否已有店铺级预测日销量。如果没有可靠同源口径，本期店铺预测和覆盖显示空值并记录后续任务，不使用 SKU 总预测平均分配。
4. 同店绑定多个 Listing 时显示数量和“库存已合并”提示，并允许展开查看 Listing 名称/标识；展开内容只展示绑定关系，不展示库存数值。
5. 表尾增加 SKU 平台库存合计，确保各店铺 FBS、FBO/FBW、在途分别与顶部汇总对账。
6. 账面可用和采购中库存不进入店铺表，也不用于店铺覆盖天数。

总文档中的“Listing 库存”在此按已冻结数据能力修正为“平台 / 店铺库存分布”。这不是遗漏 Listing，而是避免把店铺共享库存伪造成 Listing 库存。

### 5. 历史库存与八周趋势查询

新增独立只读查询对象，建议命名为 `Ec::SkuInventoryTrendQuery`。不要把历史快照解析继续堆进 `Ec::InventoryPageDetailQuery`。

输入：

- `sku`。
- `to_date`，默认用户时区当天。
- `weeks`，首版固定或限制为 8。
- `time_zone`。

数据源：

- `Ec::Snapshot.of_type(Ec::InventorySnapshot.snapshot_type).for_sku(sku)`。
- 只读 `content` 中已经保存的 `overview`、`distribution` 等数据。
- 不读取当前 `Ec::SkuInventoryLevel` 来回填历史，不在 GET 中创建或修复快照。

当前 `Ec::InventorySnapshot.capture` 已确认会在每个日快照中保存：

- `overview.book_stock`：账面库存。
- `overview.platform_stock`：WB `fbw` + Ozon `fbo` 平台在库。
- `overview.platform_inbound_stock`：平台在途库存。
- `overview.incoming_quantity`：采购中库存。
- `overview.daily_sales_velocity`：普通预测日销量。
- `overview.turnover_days`：周转天数。
- `overview.turnover_days_with_procurement`：含采购周转天数。
- `overview.platform_totals`：按平台和 fulfillment type 汇总的库存。
- `distribution.levels`：平台、店铺/账号、fulfillment type 和数量明细。

因此总文档规定的三个默认趋势指标均可直接读取真实历史快照，不需要用当前数据回算。FBS 库存虽然没有单独的 `overview.fbs_stock` 字段，但可以在同一条快照内对 `distribution.levels` 中 `fulfillment_type = 'fbs'` 的数量求和，属于可靠的快照内派生值。

周取值规则：

1. 按自然周周一至周日分组，返回最近八个周桶。
2. 每周选该周日期最晚且内容有效的真实快照，不要求必须是周日。
3. 同一周的全部指标必须来自同一条选中快照，禁止各指标分别寻找最后非空值。
4. 返回 `snapshot_date` 和 `is_week_end`，页面可以提示该周实际取值日期。
5. 某周没有有效快照时保留周桶并返回缺口，不以前一周数值填充。
6. “有效快照”至少要求 `overview` 和趋势所需库存字段结构存在；具体校验集中在查询对象内。

SKU 趋势首版指标：

| 趋势指标 | 快照来源或计算方式 | 首版状态 |
|---|---|---|
| 账面可用库存 | `overview.book_stock` | 默认展示 |
| 平台在库 | `overview.platform_stock` | 默认展示 |
| 周转天数（含采购） | `overview.turnover_days_with_procurement` | 默认展示 |
| FBS 库存 | 同一快照 `distribution.levels` 中全部 `fbs` 数量求和 | 可选展示 |
| 在途库存 | `overview.platform_inbound_stock` | 可选展示 |
| 采购中库存 | `overview.incoming_quantity` | 可选展示 |
| 预测日销量 | `overview.daily_sales_velocity` | 可选展示 |
| 周转天数 | `overview.turnover_days` | 可选展示 |

严格预测日销量和严格预测覆盖天数只在顶部展示当前值，不进入首版历史趋势。当前快照没有保存每天的严格预测结果；运行当前服务回算旧日期还会受到后来补入的销量数据和当前营销 Stage 影响，不能视为当时的历史事实。

查询对象仍需对旧版本快照做字段能力检查，并返回 `available_metrics`。某条旧快照缺少直接字段时，只允许使用同一快照内能确定性计算的值，例如：

- `platform_stock` 缺失但 `distribution.levels` 完整时，可汇总 `fbo`、`fbw` 得到。
- `platform_inbound_stock` 缺失但 `distribution.levels` 完整时，可汇总 `inbound` 得到。
- `turnover_days_with_procurement` 缺失，但同一快照同时存在 `book_stock`、`incoming_quantity` 和正数 `daily_sales_velocity` 时，可按 `(book_stock + incoming_quantity) / daily_sales_velocity` 计算。
- `turnover_days` 缺失，但同一快照同时存在 `book_stock` 和正数 `daily_sales_velocity` 时，可按 `book_stock / daily_sales_velocity` 计算。

除此以外不得跨快照拼字段，不得查询当前批次、当前库存或当前预测来补历史。若旧快照既无直接字段也不满足同快照推导条件，该周对应指标保持空值。

查询结果建议结构：

```ruby
{
  weeks: [
    {
      week_start:,
      week_end:,
      snapshot_date:,
      missing: false,
      metrics: {
        book_available_stock:,
        platform_stock:,
        fbs_stock:,
        inbound_stock:,
        procurement_stock:,
        forecast_daily_sales:,
        turnover_days:,
        turnover_days_with_procurement:
      }
    }
  ],
  available_metrics: [],
  operation_events: []
}
```

### 6. 趋势图与历史明细

1. 使用现有 ECharts Stimulus controller，不新增另一套图表加载逻辑。
2. 默认展示“账面可用库存”“平台在库”“周转天数（含采购）”；不可用指标自动从默认集合移除。
3. 库存数量与天数使用两个 Y 轴，图例可切换；颜色需能明确区分库存、在途和覆盖类指标。
4. X 轴展示八个自然周，Tooltip 同时显示周范围、实际快照日期和该周全部有效指标。
5. 快照缺口在图上断线，并展示无数据提示，不做前向填充或插值。
6. 图下增加八周历史明细表，使用同一查询结果，便于对账；表格列为周、实际快照日期及当前可用指标。
7. 趋势区域置于当前库存概览和店铺表之后、现有四个库存明细 Tab 之前。
8. 页面需处理不足八周、全部无快照和部分周断档三种空状态。

### 7. 运营动作标记

1. 通过 `Ec::OperationActionChartEventsQuery` 获取八周范围内的 SKU 运营动作。
2. ERB 按现有图表协议输出事件 JSON。
3. 由 `echarts_controller.js` 调用 `applyOperationEventMarkLines` 绘制竖线和 Tooltip；库存模块不得自行拼接 ECharts `markLine`。
4. SKU 趋势默认展示该 SKU 范围内所有结构化运营动作。事件 Tooltip 保留平台、店铺、操作人、动作类型和变更摘要。
5. 事件发生日在周度 X 轴上的落点需要统一：建议查询层或图表选项将事件映射到所属自然周，同时保留真实 `operated_at` 用于 Tooltip。实现前需为周轴补充公共 marker 映射测试，避免直接把时间戳传给分类周轴导致竖线不显示。

### 8. 店铺历史趋势的条件性范围

首版必须完成 SKU 八周趋势。店铺趋势仅在快照 `content['distribution']['levels']` 能稳定提供 `platform + store_id/account_id + fulfillment_type + quantity + synced_at` 时实现。

如数据满足条件：

- 允许在趋势区选择平台 / 店铺。
- 展示该店铺 FBS、FBO/FBW、在途及可计算的覆盖天数。
- 同店多 Listing 继续合并，并展示同样的粒度提示。
- 仍然不提供 Listing 选择器或 Listing 趋势。

如历史快照缺少可靠店铺维度：

- 本期只交付 SKU 趋势。
- 不修改库存同步、快照表结构或历史数据来追求店铺趋势。
- 页面不显示不可用的店铺趋势入口。

## 测试拆解

### 查询与服务测试

1. 普通预测解释中的 S7/S15/S30、权重和最终值与 `Ec::InventoryVelocityMetricsQuery` 同源。
2. 严格预测值、计算路径、有效日和断货日与 `ErpAI::DynamicDailySalesForecast` 完全一致。

## 明确不做

- 不新增或训练另一套销量预测算法。
- 不做未来库存量预测、预计断货日期模拟或自动补货建议。
- 不做 Listing 库存、Listing 覆盖天数或 Listing 库存趋势。
- 不按 Listing 销量、利润或预测比例分摊店铺库存。
- 不改变库存同步频率、库存 level 粒度或通用快照表结构。
- 不在页面 GET 中同步平台、补快照或修复历史数据。
- 不为缺失历史字段使用当前数据倒推。

## 与 Listing 模块的关系

Listing 的上周销量、漏斗和利润放在对应业务模块中。库存页只可用这些指标辅助解释店铺库存，不将它们用于分摊库存。进入某 Listing 时，可以显示其所属店铺的合并库存，但必须明确标注“平台 / 店铺共享库存”。
