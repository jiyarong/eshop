## 1. 现状（代码事实）

### 1.1 页面结构

- 标签内容渲染在 Turbo Frame 里：抽屉里是 `sku_detail_tab_profit_prediction`（`sku_detail_shell.html.erb:36`，懒加载），独立详情页里是 `sku_detail_tab`（`sku_detail.html.erb`）。
- 页面由三块组成：顶部工具栏（版本切换、复制、新增、保存）、**6 场景竖向总表**（`profit-prediction-table`，每个场景一行，每个参数一列，单元格就是输入框）、**场景计算器**（`profit-prediction-process`，场景页签 + 计算过程表）。
- 计算器读取的是总表里同一行的输入框，所以总表的 DOM 必须一直存在，不能删除，只能隐藏。

### 1.2 版本的现状

- 模型 `Ec::SkuProfitVersion`：`status`（draft / published / archived）、`effective_from` / `effective_to`、`lock_version`。已发布版本在数据库有「同 SKU 生效区间不重叠」的排除约束。
- **页面没有任何「发布」或「归档」操作**：保存时沿用原状态（`saveVersion(this.statusValue)`），新建版本一律是 draft。所以线上所有版本实际都是草稿，`published` 这条路径在界面上用不到。
- 默认打开哪个版本（`reports_controller.rb:1200` 附近）：`version_id` 指定 → 否则「今天生效的已发布版本」→ 否则「生效日最新、同日 id 最大的版本」。这条规则同时被多处隐式依赖：
  - 漏斗估算利润：`SalesFunnelReports::SkuProfitEstimateQuery.version_for`
  - SKU 工作台列表的估算利润：`Ec::OperatorSkuSalesFunnelMetricsQuery#load_profit_versions`
  - 月度刷新复制来源：`Ec::SkuProfitMonthlyRefresh`（取最新版本）

### 1.3 A1 的根因

`profit_prediction_controller.js:229` 的 `changeVersion` 用的是：

```js
const url = new URL(window.location.href);   // 抽屉里这是「宿主页面」的地址，不是 SKU 详情地址
url.searchParams.set("version_id", ...);
Turbo.visit(url.toString(), { action: "replace" });   // 顶层整页跳转，不是 Frame 内导航
```

在抽屉里 `window.location` 是宿主页（如 `/operator_skus`），所以整页被跳转到「宿主页 + `tab` + `version_id`」，抽屉丢失，版本也没切成。另外 `turbo:before-visit`（未保存提醒）只拦顶层跳转，对 Frame 内导航不生效。

「复制」「新增」两个按钮是普通 `link_to`，在 Frame 内本来就走 Frame 导航，没有这个问题，但它们同样绕过了未保存提醒。

## 2. A1：抽屉内切换版本不再整页刷新

### 2.1 目标行为

- 在抽屉里切换版本，只刷新「定价测算」这个 Frame，抽屉、其他标签、滚动位置都保持。
- 在独立详情页里行为一致。
- 有未保存的修改时，切换前弹确认，取消则下拉框回到原版本。
- 复制、新增也走同一套未保存确认。

### 2.2 方案

1. 视图根节点新增 `data-profit-prediction-switch-url-value="<%= report_sku_path(@sku.sku_code, tab: "profit_prediction") %>"`，不再依赖 `window.location`。
2. `changeVersion(event)` 改为：
   - 若 `hasUnsavedChanges()` 且用户取消：把下拉框值还原为当前版本后返回；
   - 否则 `const frame = this.element.closest("turbo-frame")`，`url = switchUrl + version_id`，调用 `Turbo.visit(url, { frame: frame.id })`；找不到 Frame 时退回顶层 `Turbo.visit`。
3. `allowNavigation = true` 在确认后设置，避免 `turbo:before-visit` 再弹第二次。
4. 「复制」「新增」按钮加 `data-action="click->profit-prediction#confirmLeave"`，未保存时确认，取消则 `preventDefault()`。
5. 服务端不用改：抽屉里的请求带 `Turbo-Frame: sku_detail_tab_profit_prediction`，`ReportsController#sku_detail` 已能只渲染该 Frame；独立页的 Frame（`sku_detail_tab`）由 Turbo 从整页响应中提取。

### 2.3 测试

- JS（`test/javascript/profit_prediction_controller_test.mjs`，沿用 esbuild 桩）：
  - 有 Frame 时调用的是 `Turbo.visit(url, { frame })`，URL 来自 `switchUrl`，不含宿主页路径；
  - 无 Frame 时回退顶层跳转；
  - 未保存且取消：不跳转、下拉框回滚；确认：跳转一次。
- Rails 视图断言：根节点带 `data-profit-prediction-switch-url-value`；复制 / 新增按钮带确认动作。
- 手工验收：从 SKU 工作台打开抽屉 → 定价测算 → 切换三个版本，抽屉不关闭；修改一个数后切换，出现确认。

## 3. A2：「设置为当前版本」

### 3.1 概念

- **当前版本** = 这个 SKU 现在实际采用的一套测算，每个 SKU 同时只有一个。
- 与 `status` 正交：`status` 是版本生命周期（草稿 / 已发布 / 已归档），当前版本是「正在用哪套」。因为界面上没有发布入口，先不让两者耦合。
- 归档版本不能设为当前；未保存的新版本不能设为当前。

### 3.2 数据模型

迁移（用 `rails generate migration` 生成）：`AddIsCurrentToEcSkuProfitVersions`

```ruby
add_column :ec_sku_profit_versions, :is_current, :boolean, null: false, default: false
add_index  :ec_sku_profit_versions, :sku_id, unique: true, where: "is_current", name: "idx_sku_profit_versions_one_current"
```

回填：对每个有版本的 SKU，把「今天页面默认会打开的那个版本」标为当前（即现有解析规则的结果），保证上线后页面行为不变。

- `Ec::AuditConfig`：给 `Ec::SkuProfitVersion` 加 `is_current`（项目规则：新增可编辑字段必须同步审计配置）。
- 模型：`scope :current`；`Ec::SkuProfitVersion.resolve_for(sku, date: nil)` 统一解析规则，顺序为：
  1. `is_current` 的版本；
  2. 今天生效的已发布版本；
  3. 生效日最新、同日 id 最大的版本。

### 3.3 接口

`PATCH /reports/skus/:sku_code/profit_versions/:id/set_current`（权限与 `update_sku_profit_version` 相同，`manage_skus`；加入 `SKU_WORKBENCH_ACTIONS`）。

- 事务内对该 SKU 的版本加锁，先取消其他版本的 `is_current`，再设置目标版本。
- 拒绝：版本已归档、版本不属于该 SKU，返回 422，错误码沿用现有风格。
- 并发：以唯一索引兜底；`lock_version` 冲突返回 409。
- 返回新的当前版本 id；前端据此刷新 Frame。

### 3.4 界面

- 版本下拉框每项显示徽标：`名称 · 当前 · 草稿`；当前版本排在列表最前并带「当前」标记。
- 工具栏新增按钮「设为当前版本」：
  - 已经是当前版本：显示为不可点的「当前版本」；
  - 有未保存修改：点击先提示「请先保存」，不直接设置；
  - 该版本存在计算未完成的场景：设置前提示「N 个场景未算完」，允许继续。
- 非当前版本打开时，在版本条上显示提示「正在查看的不是当前版本」，并带一个设为当前的快捷入口。
- 文案走 I18n（zh / en / ru）：`reports.profit_prediction.current_version.*`。

### 3.5 下游统一使用 `resolve_for`

| 位置 | 变化 |
|---|---|
| `load_sku_detail`（页面默认版本） | 改为 `resolve_for` |
| 漏斗「估算利润」`version_for` | 改为 `resolve_for`（所有周期统一用当前版本，估算对应的是「按现在的定价看这批销量值多少」） |
| SKU 工作台列表估算利润 | 同上，按页批量预取，仍保持固定查询数 |
| 月度刷新 | 复制来源改为当前版本；新生成的草稿**不自动设为当前**，由人确认 |

### 3.6 测试

- 模型：同一 SKU 设置第二个当前版本，第一个自动取消；唯一索引拒绝两个并发设置；归档版本不能设为当前。
- `resolve_for` 三层优先级各一个用例。
- 控制器：权限、跨 SKU、归档、未保存（无 id）的拒绝，成功后唯一当前。
- 视图：徽标、按钮三种状态、非当前提示。
- 迁移测试：回填后每个有版本的 SKU 恰好一个当前版本，且等于迁移前页面默认打开的版本。
- 估算利润与月度刷新：按当前版本取数的用例。

## 4. A3：「场景计算器 / 场景总表」视图切换

### 4.1 目标行为

- 工具栏新增分段切换：「场景计算器」「场景总表」，**默认是场景计算器**。
- 两个视图互斥显示，当前选中的场景在两个视图间共享（在总表点了某行，切回计算器时就是那个场景）。
- 记住用户上次的选择。

### 4.2 方案

- 视图根节点增加 `data-view-mode="calculator|table"`，用 `hidden` 属性切换两块区域（总表区域、计算器区域），**不移除 DOM**，计算器依赖总表里的输入框。
- 总表专属控件（平台筛选页签、场景数量）随总表一起隐藏；计算器自带的场景页签保持显示。
- 偏好存在浏览器 `localStorage`（键 `profit_prediction_view_mode`），读写都包 `try/catch`，读不到就用默认的计算器；每个人各自一份，不写库。
- 从隐藏切到显示时触发一次窗口 resize，让总表的粘性表头（`sticky_table_header_controller.js`）重新量宽。
- 抽屉内切换版本会重新加载 Frame，视图模式要在新 Frame 连接时从 `localStorage` 恢复，不能因为刷新而跳回默认。

### 4.3 测试

- JS：默认进入计算器；切换后总表可见、计算器隐藏；偏好写入并在下次连接时恢复；`localStorage` 抛错时回落默认。
- 视图断言：两块区域都在 DOM 中；切换控件存在；默认状态下总表是 `hidden`。
- 手工验收：切到总表改一个输入，再切回计算器，计算结果同步；切换版本后模式不变。

## 6. 后续阶段（本期不开发，仅记录结论与待查事项）

### 6.1 第二阶段：公式可读性与真实数据口径

**B1 公式更具体。** 目标是每一项公式都能直接对应左边表单的字段：公式里使用字段的中文名而不是变量，再给出代入后的数值（例如「基础物流费 = 前 N 升价 + 超出升数 × 每升价 = …」），并支持鼠标悬停时高亮对应输入。依赖 `appendProcessStep` 的步骤数据结构，需要为每一步补充「参数字段 → 展示名」的映射，这一块放到 A1 ~ A3 之后单独设计。

**B2 真实数据口径。** 现状是各个「使用近 4 周…」按钮的口径各不相同，且与利润归集不一致：

| 数据 | 口径（当前代码） | 与利润归集的差别 |
|---|---|---|
| 成交价 | 订单表近 4 个整周，去掉取消单；按平台 + 市场 | 归集用账务的 SaleRevenue，按账务日期 |
| 物流费 | WB 按财务明细 `rr_dt`；Ozon 按 accrual 日期；按单取均值 | 归集按周期汇总再除净销量 |
| 退货率 | Ozon：返程单 ÷ 去程单；WB：按订单状态 | 归集按发货单净额判断 |
| 仓储费 | Ozon accrual ÷ 正向发货单；WB 付费仓储 ÷ 出口销量 | 归集直接汇总，不除件数 |
| 越库费 | 每条收费明细的平均额（口径有误，见 6.2） | 归集总额 ÷ 净销量 |
| 广告 / 收单 | 比例 | 比例 |

后续要做的事：为每个「真实数据」写清统一口径（统计窗口、分子分母、是否去取消、净销量定义），在界面展示口径说明；并增加一个对账用例，同一窗口下与利润归集的净销量、销售额逐项对账。利润归集的净销量口径已于 `1d1a5c73` 修复，对账以修复后为准。

### 6.2 第三阶段：公式修正（需先研究）

**B3 WB 返程运费。** 你的反馈是「现在应该是和去程一样，只是没有头程」。我此前在线上数据里的结论是不同的，所以先复核，不先改公式：

- 已有证据（2025-01 ~ 2026-10，约 2,000 笔「От клиента при возврате / при отмене」）：折成 RUB 后始终在 49.5 ~ 50.3，与商品体积、去程费无关；同一订单去程 43 ~ 62 BYN 而这一段只有约 1.78 BYN；2026-03 与 2026-05-21 前后没有台阶。
- 另一类「退回卖家」（`Возврат… (К продавцу)`）是独立费率（`deliveryDump*`），随体积变化，约为该 SKU 去程费的 0.9 ~ 3.2 倍，这一类可能就是「像去程」的来源。
- 待办：① 通读 WB 官方文档与卖家协议中关于退货物流的最新说明，并保留链接与日期；② 核对 `/api/v1/tariffs/return` 的返回字段是否有与买家退货对应的费率；③ 用最新一个月的财务明细再查一次；④ 确认你看到的新算法对应的是哪一段费用。复核完成前，计算器里的固定 50 RUB 不动。

**B4 越库费。** 现在把「近 4 周越库费每条明细的平均额」当成每件成本，约 40 CNY/件，而归集口径折到每件约 7 ~ 10 CNY/件，高估约 34 CNY/件（以 KJ-217-GD 为例）。正确方向是「期间越库费总额 ÷ 对应受益的件数」。待研究：越库费与供货单的对应关系（`raw_ozon_supply_orders`），受益件数应取供货入仓件数还是期间净销量，以及与表格的「4845 / 60」口径对齐。

**B5 物流费模式开关。** 目标：固定公式模式为准、历史实付仅作参考，或提供开关切换两种模式。要点：每个场景保存当前模式（建议新增 `logistics_mode`）；界面始终明确标出当前模式；另一模式的数值并列显示，并显示两种模式的差额；切换前后的利润变化可见。

## 8. 第二阶段研究记录

### 8.1 B1 公式可读性（已实现）

**现状**：计算过程表每行 4 列（项目 / 参数 / 来源 / 计算与结果）。公式列只有「数字 + 运算符」，例如 WB 基础物流费显示为 `46 + (23 - 1) * 14`，看不出 46、23、14 分别是哪个参数。代码在 `profit_prediction_controller.js` 的 `renderCalculationSteps` 及 `appendWbProcessSteps` / `appendOzonProcessSteps` / `appendCommonCostSteps`，公式是逐步手写的字符串，与后端 `Ec::ProfitCalculators::{Wb,Ozon}` 是两份各自维护的逻辑。

**逐步核对（后端公式 ↔ 页面公式）**

| 步骤 | 后端公式（字段名） | 页面现状 | 结论 |
|---|---|---|---|
| 收入 | `commission_base_price_rub ÷ exchange_rate_rub_cny` | 一致 | 仅缺字段名 |
| 商品成本 | `purchase_price_cny + freight_cny + customs_misc_cny` | 一致 | 仅缺字段名 |
| 关税 | `purchase_price_cny × duty_rate` | 一致 | 仅缺字段名 |
| 进口增值税 | `(purchase_price_cny + 关税) × import_vat_rate` | WB 与白俄显示；Ozon 俄罗斯不显示 | 后端对 Ozon 俄罗斯按 `ozon_import_vat_cost_rate`（默认 0）计入，页面无此行，见下 |
| 体积 / 计费体积 | `长×宽×高÷1000`、`ceil(体积)` | 一致 | 仅缺字段名 |
| WB 基础物流费 | `wb_logistics_base_rub + (计费体积 − 1) × wb_logistics_liter_rub` | 一致 | 仅缺字段名 |
| WB 平台物流费 | 有去程实付：`outbound_logistics_rub ÷ 汇率`；否则 `基础物流费 × logistics_coeff ÷ 汇率`；再加 `fbo_delivery_cny` | 一致 | 两种来源并存，页面未标明当前走了哪一种 |
| WB 退货费用 | `平台物流费 × r÷(1−r) + 返程费 ÷ 汇率 × r÷(1−r)`，返程费取 `return_logistics_rub`，没有则 `wb_fixed_return_base_rub`（默认 50） | 一致 | 参数格里还列了 `logistics_tax_rate`，**后端从未使用** |
| Ozon 平台物流费 | `outbound_logistics_rub + warehouse_operation_rub + warehouse_operation_rub × 2 × ozon_warehouse_rate(0.25)` ÷ 汇率 | 页面把后两项合成「附加费」一个数 | 附加费的算法没展示；参数格还列了本步不用的 `return_logistics_rub` |
| Ozon 越库费 | 不单独计费，计入「其他成本」 | 单独成一行并展示数值 | 同一笔钱在「越库费」与「其他成本」各出现一次，容易误以为重复计算 |
| Ozon 退货运费折算 | `(outbound_logistics_rub + return_logistics_rub) × 系数 ÷ 汇率`，系数默认 `r÷(1−r)`，可被 `return_amortization_factor_override` 覆盖 | 一致 | 仅缺字段名 |
| 仓储 | `storage_cny` | 一致 | |
| 佣金 / 收单 / 广告 | `收入 × 费率`（Ozon 收单默认 2%） | 一致 | Ozon 广告后端还加 `advertising_fixed_rub ÷ 汇率`，页面公式没有 |
| 销售税 | WB 小公司 `收入 × tax_rate`；WB 一般公司与白俄 `收入 × v÷(1+v) − 进口增值税`；Ozon 俄罗斯 `收入 × tax_rate`（页面写死 0） | Ozon 俄罗斯页面公式写 `0` | 后端读取了 `tax_rate`，页面却固定显示 0，二者在 `tax_rate≠0` 时不一致 |
| 其他成本 | WB：`(商品成本 + 进口增值税 + 关税) × damage_rate + misc_cny + other_cny`；Ozon：`越库费 + other_cny` | 一致 | 参数格对 Ozon 还列了 `damage_rate`、`misc_cny`（不适用） |

**数据核实**（本地库 816 个场景）：`wb_logistics_override_cny` 全空、`logistics_tax_rate` 全空、`advertising_fixed_rub` 与 `ozon_import_vat_cost_rate` 全为 0、`ozon_warehouse_rate` 为 0.25 或空。也就是说上面几处「页面与后端不一致」目前都不会让数值出错，只会在以后有人填了这些字段时出现隐性偏差；它们是 Google 表格导入时遗留的隐藏参数。

**方案**

1. **公式具名化**：每一步的公式改成两行 ——
   - 第一行用字段名：`基础物流费 + (计费体积 − 1) × 每升物流费`
   - 第二行代入数值：`46 + (23 − 1) × 14 = 354 RUB`
   实现上不再手拼字符串，而是为每一步声明一个「项」数组：`[{ field: "wb_logistics_base_rub", value }, "+", "(", { calc: "billed_volume_l", value }, "−", 1, ")", "×", { field: "wb_logistics_liter_rub", value }]`，同一份数据同时渲染具名行与数值行。字段名取现有 `process.parameter_labels`（三语已有），中间量（计费体积、基础物流费等）取 `process.steps` 的名称。
2. **悬停联动**：鼠标移到公式里某个字段名/数值上，高亮本行「参数」格里对应的输入框；该参数在更早的步骤里出现时，高亮那一行的输入框并滚动到可见位置。
3. **只展示后端真正使用的参数**：参数格不再列 `logistics_tax_rate`、Ozon 的 `damage_rate`/`misc_cny`/本步未用的 `return_logistics_rub`；Ozon 俄罗斯销售税、Ozon 附加费、广告固定费的公式与后端对齐。
4. **越库费重复展示**：保留「其他成本」中的计费，越库费这一行改为「已计入其他成本」的提示，并显示在「其他成本」公式里能看到它。
5. **防再次漂移**：增加一个对照测试，用同一组输入跑后端计算器与页面公式的数值，逐步比对（JS 测试里用后端导出的样例数据）。

**风险与取舍**：改动只发生在展示层，不改后端计算和已保存数据；JS 控制器已较大，新增的「公式项」渲染建议拆成独立的模块文件（`profit_prediction_formula.js`），由控制器引用，避免继续膨胀。

**实现记录**

- 新增 `app/javascript/controllers/profit_prediction_formula.js`：纯函数 `buildCalculationSteps` 生成所有步骤，公式是「项」数组（运算符 / 参数 / 引用的步骤 / 常数），`evaluateFormula` 可直接求值；控制器只负责渲染。原来手写在控制器里的 `appendWbProcessSteps` 等 6 个方法已删除。
- 公式列两行：第一行参数名（单位已去掉），第二行代入数值；鼠标悬停高亮左侧对应输入、其他位置的同名项，引用其他步骤时高亮那一行。**没有做悬停自动滚动**：自动跳动会打断阅读，只做高亮。
- 后端 `intermediate` 补充了页面没有输入框的参数：Ozon 的 `warehouse_rate`、`import_vat_cost_rate`、`advertising_fixed_rub`、`sales_tax_rate`、`return_amortization_factor_overridden`，WB 的 `logistics_source`（actual / override / coefficient）。数值计算没有变。
- 已按上表修正：WB 退货不再列 `logistics_tax_rate`；Ozon 物流显示附加费率且不再列返程费；Ozon 越库费行加注「已计入其他成本」；Ozon 销售税、广告固定费、进口增值税成本比例有对应公式；其他成本只列适用参数。
- 对照测试：`test/fixtures/files/profit_prediction_formula_cases.json` 保存 6 个场景（WB 一般 / 小公司 / 实付物流 / 覆盖值，Ozon 俄罗斯 / 隐藏参数 / 白俄）的输入与 Ruby 计算器结果；`test/javascript/profit_prediction_formula_test.mjs` 逐步求值页面公式并与计算器比对，`test/services/ec/profit_prediction_formula_cases_test.rb` 保证 fixture 与当前 Ruby 计算器一致。

### 8.2 B2 真实数据口径（考证结论，待确认方案）

**考证方法**：本地库数据截至 2026-10-14。窗口取「近 4 个完整自然周」2026-09-14 ~ 2026-10-11（与按钮默认口径一致），取 Ozon、WB 各销量前 10 的 SKU，把每个「获取近 4 周…」查询的结果，和同窗口的利润归集（`Ec::OzonProfitAttribution` 一次跑 4 周；`Ec::WbProfitAttribution` 按周跑再合并，汇率取各周 `Ec::WeeklyRate`）逐项对账。对账标准是：**计算器按「每件净销售」算出的成本，应等于归集的该项总额 ÷ 净销量**。

#### 8.2.1 现有口径一览

| 数据 | 平台 | 数据源与时间轴 | 分子 / 分母 |
|---|---|---|---|
| 售价（佣金基准价、买家实付价） | 两者 | 订单表 `ec_order_items`，按下单时间（用户时区），去掉 cancelled，数量加权均价；Ozon 用买家币种区分 ru/by | 均价，件数 = 非取消订单件数 |
| 物流费 | Ozon | `raw_ozon_accrual_by_day`，按 accrual 日期，按发货单汇总 | 去程/返程总额 ÷ 有该段费用的发货单数 |
| 物流费 | WB | `raw_wb_finance_details`，按 `rr_dt`，按 srid 汇总，BYN 按周汇率折 RUB | 同上；返程 = 买家退回 + 退回卖家的总额 ÷ 买家退回单数 |
| 退货率 | Ozon | 同上 accrual | **返程单数 ÷ 去程单数**（含未妥投退回） |
| 退货率 | WB | **订单表**，下单时间在窗口内且状态为 delivered/returned | **returned ÷ (delivered + returned)** |
| 仓储费 | Ozon | accrual，仓储类费用 | 总额 ÷ 净收入为正的发货单数 |
| 仓储费 | WB | `raw_wb_paid_storage`（calc_date） | 总额 ÷ **出口**报告的销售件数 |
| 收单费率 | Ozon | accrual type 0 / type 1 | 收单费 ÷ SaleRevenue（仅限窗口内有销售的发货单，退货两边都扣） |
| 收单费率 | WB | finance details 的**销售行** | 销售行 `acquiring_fee` ÷ 销售行 `retail_price_with_disc × qty` |
| 广告费率 | Ozon | Performance 花费 / accrual type 0 | 广告花费 ÷ SaleRevenue |
| 广告费率 | WB | 广告结算费按活动花费分摊 / finance details | 广告费 ÷ **净 `retail_amount × qty`** |
| 越库费 | Ozon | accrual type 12（越库） | 平均每条收费明细额（B4 处理） |

利润归集的对应口径：Ozon 净销量 = 发货单级净额（+1 销售 −1 退货，同期售后退货相抵为 0），WB 净销量 = 报告中销售件数 − 退货件数；费用按报告周/accrual 日期汇总。

#### 8.2.2 对账结果

**① Ozon：用「返程单 ÷ 去程单」作退货率，计算器与归集完全对上。**
例（物流 + 退货，RUB / 净销售）：

| SKU | 归集（去程 + 返程）÷ 净销量 | 计算器（去程均值 + (去程 + 返程均值) × r÷(1−r)） | 偏差 |
|---|---|---|---|
| KJ-217-GD | 381.2 | 377.9（r = 43/147 = 29.3%） | −0.9% |
| QJD001-3 | 342.4 | 343.0 | +0.2% |
| LDD002 | 323.1 | 323.0 | 0% |
| DJ002 | 1830.0 | 1830.0 | 0% |

结论：这个退货率口径是对的，且必须与「去程、返程均值」配套使用。**页面上它叫「退货率」，KJ-217-GD 显示 29.3%，归集里的退货率（SaleRevenue 冲销单 ÷ 订单）是 10.4%，这就是「看着对不上」的来源之一**：29.3% 里包含大量没有妥投、但去程返程都已计费的发货单。

**② WB：订单表退货率与物流口径不配套，物流成本被系统性低估 8% ~ 30%。**
KJ-217-GD 的 WB 去程有 67 单、买家退回 21 单：

- 页面现在的退货率（订单表）= 6.7%（2/30，分母仅 30，因为只数下单后已妥投/已退回的订单）→ 计算器物流 + 退货折算 560.1，归集实际 804.4，**低 30.4%**。
- 改用「买家退回单数 ÷ 去程单数」（21/67 = 31.3%，与 Ozon 同口径）→ 计算器 804.4，**偏差 0.0%**。
- 10 个 SKU 全部对比：订单表口径低估 8% ~ 30%（中位约 −23%）；物流口径偏差 0% ~ +11%（中位约 +6%），剩余偏差来自窗口错位（`rr_dt` 与报告周、窗口前销售的退货落在窗口内）。

原因（推断，由费用类型与单量差异支持）：WB 对取消、拒收同样收去程费和返程费（`К клиенту при отмене` / `От клиента при отмене`），这些单在订单表里不会是 returned，订单表口径因此漏掉了它们的成本；另外窗口内去程 67 单对应销售只有 51 件。

**③ WB 广告费率分母不一致，广告成本被高估约 14% ~ 33%。** 计算器把广告费 = 收入（佣金基准价，对应 `retail_price_with_disc`）× 广告费率；但 WB 的广告查询用的是 `retail_amount`（扣除买家折扣后的金额，约为前者的 78.5%）。以 KJ-217-GD 为例，分子与归集完全相同（377.0），归集费率 1.89%，页面取到 2.27%。5 个 SKU 都高估，幅度 14% ~ 33%（分母比值 ≈ 78.5%，对应约 27%）。Ozon 广告对账完全一致（5 个 SKU 到小数点后 4 位相同）。

**④ WB 收单费率只数销售行，漏了退货行上不退还的收单费。** KJ-217-GD：销售行收单 805.84 / 基数 25,130 = 3.21%（页面）；退货行 5 笔收单费 74.53 并未退还，归集 = (805.84 + 74.53) / (25,130 − 2,486) = 3.89%，按净基数算才与「每净销售」一致。10 个 SKU 中 9 个页面低于归集，差 0.1 ~ 0.7 个百分点，另 1 个（无退货）持平。Ozon 收单对账一致。

**⑤ WB 仓储：分子完全一致，分母不一致（偏差最多 12%）。** 页面只除以「出口报告」的销售件数（`report_type = 2`）；归集按净销量（白俄 + 出口）。例 KJ-226-GD：页面 36.29 对 33.14。

**⑥ 售价：订单表与归集接近，但「件数」不同。** 均价偏差在 ±3% 以内（单件样本的 SKU 除外）。但按钮旁展示的件数是「订单表非取消件数」，与归集的净销量不是一个量：QJD001-3 为 355 件对 492 件，KJ-217-GD 为 117 对 103。原因有三：订单表按下单时间、归集按账务日期（在途订单跨期）；订单表含最终会退货的件；以及**市场划分不同**——页面按买家币种分 ru/by，归集的白俄税基按发货目的地 `is_belarus` 分（QJD001-3：BYN 币种买家已妥投 154 件，白俄目的地净销量只有 87 件）。

**⑦ 越库费：总额与归集完全相同，但页面取「每条明细均值」，是总额 ÷ 净销量的 4.5 ~ 5.8 倍**（KJ-217-GD 525.9 vs 117.0；QJD001-3 361.7 vs 62.5）。这是 B4 的内容，这里只记录口径。

#### 8.2.3 建议方案

1. **统一「退货率」定义为「返程单 ÷ 去程单」（两个平台一致）**。WB 改成物流口径：买家退回单（`От клиента при возврате / при отмене`）÷ 去程单（`К клиенту при продаже / при отмене`），在 `SkuActualReturnRateQuery` 的 WB 分支改用 `SkuActualLogisticsQuery` 的结果。界面把标签改为「物流退货率」，并在结果旁说明「返程单 ÷ 去程单，含未妥投退回，与退货折算公式配套使用」；保留订单表口径的「买家退货率」仅作参考，不填入参数。
2. **WB 广告费率分母改为 `retail_price_with_disc × qty`（销售 − 退货）**，与归集税基同口径。
3. **WB 收单费率分子分母都纳入退货行**：（销售行收单 + 退货行收单）÷（销售基数 − 退货基数）。
4. **WB 仓储分母改为净销量（销售件数 − 退货件数，不分报告类型）**，与归集一致；Ozon 分母保持。
5. **件数展示统一标明口径**：按钮旁显示的件数改为「订单件数（下单口径，含在途）」，并新增归集口径的参考项「净销量（账务口径）」；售价继续用订单表（保持此前确认的「两个口径同源」）。市场区分仍按买家币种，但在说明里写明与归集的白俄税基不是同一划分。
6. **每个真实数据结果都写明口径**：统计窗口、数据源、分子、分母及数量；和归集的对应关系用一句话说明。
7. **对账用例（自动化）**：新增 `Ec::SkuActualsReconciliation`（或脚本 `script/reconcile_sku_actuals.rb`），同窗口逐项对比查询与归集的分子、净销量，并给出「计算器每净销售成本 vs 归集每净销量成本」的偏差；测试用造数覆盖 Ozon/WB 的物流、退货率、收单、广告、仓储，容差：分子完全一致，每净销售成本偏差 ≤ 1%（窗口内数据同源时）。线上可手动跑一次出报告。

**不在本项范围**：越库费（B4）、WB 返程固定 50 RUB（B3）、物流模式开关（B5）。

**需要确认的决定**

- 决定 1：WB 退货率改成物流口径（返程单 ÷ 去程单），订单表口径只作参考。（建议：同意——证据最充分，改后偏差由 −23% 降到 +6%。）
- 决定 2：WB 广告、收单、仓储三个口径按上面的 2/3/4 调整（分子不变，只改分母/纳入退货行）。
- 决定 3：件数展示新增「净销量（账务口径）」参考项，还是只加口径说明文字。

#### 8.2.4 已确认的决定

- **决定 1（2026-10-19，已确认）：退货率统一用账务口径「返程单 ÷ 去程单」**，Ozon 保持现状，WB 改用物流口径。依据：Ozon 12 个 SKU 对归集偏差 −4.0% ~ +0.2%；若 Ozon 改走订单（`return_business_status`）口径，已妥投口径偏差 −2.5% ~ −33.6%（中位约 −11%），含取消退回口径偏差 −13% ~ +23% 且样本一小就大幅跳动；WB 订单口径偏差 −4.6% ~ −30%。订单口径的「买家退货率」可保留为参考项，不填入参数。
- 决定 2、决定 3：待确认。

### 8.3 B4 越库费（考证结论，待确认方案）

**反馈**：越库费偏差非常大；用一段时间的越库费去摊那段时间的所有订单，做法不对。

**结论：反馈成立，而且问题比「摊法」更根本——有两层。**

1. **费用的单位不对。** 越库费在 `raw_ozon_accrual_by_day`（type_id = 12）里按**供货单**记账：`unit_number` 就是供货单号（等于 `raw_ozon_supply_order_items.ozon_supply_id`），一个供货单里每个 SKU 有若干条费用行，**一行 ≠ 一件**。以 KJ-217-GD 的 45 个供货单为例：每行对应 1 ~ 20 件不等（多数是 5 件一行，也有 3 件、10 件、20 件一行）。页面取「每条收费明细的均值」当每件成本，等于把「每箱费用」当成「每件费用」。
2. **时间错位。** 越库费发生在商品送到仓库那一刻，销售发生在之后；任何一个固定窗口里「已付越库费」和「已卖出件数」对应的并不是同一批货。窗口内多补货就偏高，少补货就偏低。

- 页面现值**既不稳定偏高也不稳定偏低**：QJD002-48 高估 11 倍，KJ-217-GD 高估 4 倍，LDD001-BK、SLHL001-2 反而低估，取决于每行对应几件。
- 归集口径（期间总额 ÷ 期间净销量）同样不稳：QJD001-3 为 62.5，实际每件 150 ~ 158；原因是期间卖出 492 件而期间只补了 205 件的货。
- 「每件供货成本」（费用 ÷ 同一批供货单里该 SKU 的件数）在 12 周和全部历史上很接近（KJ-217-GD 135.4 对 132.5，ZJ004 153.3 对 153.3，ZJ090 82.3 对 83.5），4 周窗口则波动较大（KJ-217-GD 93.0）。供货是一批一批发生的，窗口太短样本太少。
- 越库供货的占比：绝大多数 SKU 接近 100%（KJ-217-GD 601/606，LDD002 182/188，LDD001-BK 212/224）；有直供入仓的 SKU，这部分件数没有越库费，应把它放进分母。

**建议方案**

1. **成本按件算，单位用「供货件数」**：每件越库费 = Σ（该 SKU 在这些供货单上的越库费） ÷ Σ（这些供货单里该 SKU 的件数）。供货单通过 `unit_number = ozon_supply_id` 对应 `raw_ozon_supply_order_items`，件数取该 SKU 的 `quantity`。
2. **窗口用供货单，不用销售窗口**：取近 12 周（至少 20 件，不足时扩到全部历史）的越库供货单；不再受近 4 周销量影响。
3. **分母含直供件数**：用同一窗口内全部已完成供货（含非越库）的件数当分母的修正系数，即「每件越库费 × 越库件数占比」。
4. **只用已完成且已记账的供货单**；有费用行但找不到供货明细的供货单单独计数并展示，不参与平均。
5. 页面按钮的结果改为：每件越库费、样本（供货单数、件数）、窗口，并和现值对比提示；批量导入、月度刷新同步使用新口径，写入 `cross_docking_cny`（÷ 汇率）。
6. 对账：每件越库费 × 期间补货件数 应等于期间越库费总额（同源）；测试覆盖多供货单、多 SKU 供货单、直供混合、无明细。

**需要你确认**

- 决定 4：越库费按「供货件数」摊（每件越库费 = 同批供货单费用 ÷ 件数），窗口取近 12 周且至少 20 件。
- 决定 5：利润归集（按期间汇总、除以期间净销量）是否也要调整。我的建议是**暂时不动**——归集是按期间的现金口径，补货多的月份成本高是真实发生的；只改定价测算的单位成本口径。

#### 8.3.1 已确认的决定

- **决定 4（2026-10-19，已确认）：越库费按供货件数摊。** 每件越库费 = 同批供货单上该 SKU 的越库费 ÷ 这些供货单里该 SKU 的件数；窗口取近 12 周的越库供货单；至少 20 件，不足时扩到全部历史；分母含直供件数（按越库件数占比修正）。
- **决定 5（2026-10-19，已确认）：利润归集暂时不动**，仍是按期间汇总、除以期间净销量的现金口径；只改定价测算的单位成本口径。

### 8.4 实现记录（2026-10-19）：B2 退货率 + B4 越库费

**退货率（决定 1）**
- `Ec::SkuActualReturnRateQuery` 的 WB 分支改为物流口径：买家退回单（`От клиента при возврате / при отмене`）÷ 去程单（`К клиенту при продаже / при отмене`），取自 `SkuActualLogisticsQuery`；Ozon 保持不变。结果里 `return_rate.order_count / return_count` 现在两个平台都是「去程单 / 返程单」。
- 新增 `delivery_mode` 参数（WB）：按场景履约方式取 FBW / FBS，与同场景的去程、返程均值同源。KJ-217-GD（本地库）：FBO 28.3%（13/46），FBS 38.1%（8/21），不分履约方式为 31.3%；订单口径仅 6.7%。页面按钮、批量取值（`SkuProfitActualInputs`）、月度刷新都传场景的履约方式。

**越库费（决定 4、5）**

- 实现与决定的一处差别：**按「费用记账日期」选供货单，不按供货状态 `COMPLETED`**。数据显示 Ozon 在接收时就记账，早于状态变为 COMPLETED（例如 2000066064439 记账 09-16，状态 09-23 才完成；另有 83 条明细处于 `REPORTS_CONFIRMATION_AWAITING` 但费用已记）。只用 COMPLETED 会漏掉最新的供货。

### 8.5 决定 2 第一项：WB 广告费率分母（2026-10-19，已确认并实现）

- **决定**：WB 广告费率的分母由 `retail_amount × 件数` 改为 `retail_price_with_disc × 件数`（销售减退货），其余（分子、分摊、隐含汇率）不变。Ozon 不受影响（分母本来就是 SaleRevenue，即佣金基准价）。
- **依据**：本地库窗口内 3523 行 WB「销售」明细，`for_pay = retail_price_with_disc × (1 − 佣金%) − 收单费` 3523/3523 成立，换成 `retail_amount` 只有 2/3523 成立；`retail_amount ÷ retail_price_with_disc` 最小 0.578、中位 0.827、最大 1.113。计算器的广告费 = 收入（佣金基准价）× 费率，所以费率的分母必须是佣金基准价口径。
- **效果（每净销件的广告费，BYN，10 个 SKU）**：原算法比归集高 14% ~ 41%（中位约 +24%），改后偏差 −6% ~ +17%（中位约 +1%）。广告费率整体下调约 13% ~ 27%（KJ-217-GD 2.27% → 1.79%，KJ-207-WT 7.04% → 5.56%）。残差来自查询只统计有结算费记录的周，以及隐含汇率在小样本上的误差（ZJ004 广告总额仅 171.8 BYN）。
- 之前文档与汇报里写的「高估约 14% ~ 33%」是拿费率直接比得来的；严格按每净销件对账是 14% ~ 41%，以本节为准。
- 实现：`Ec::SkuActualAdvertisingQuery#wb_net_sales`；测试里销售行 `retail_amount` 与 `retail_price_with_disc` 取不同值，断言分母取后者；结果提示文案改为「净销售额（佣金基准价口径）」。已保存的版本不会自动变，月度刷新或重新取值后更新。
- 决定 2 中收单、仓储两项仍待确认，决定 3 同。
