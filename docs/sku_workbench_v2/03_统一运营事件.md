# 03 统一运营事件与趋势图标记

## 目标

继续使用 `ec_operation_actions` / `Ec::OperationAction` 作为唯一运营事件表，不改事件写入模型；新增一套跨板块复用的 ECharts 时间事件标记能力。任何以时间为 X 轴的 ECharts 趋势图，只需传入一组标准化运营事件，即可在事件发生日绘制竖线并展示事件明细。

利润、销售漏斗、广告、库存以及后续其它趋势图不得各自拼装 `markLine`、tooltip 或同日事件合并逻辑。

## 当前基础与缺口

- 现有 `app/javascript/controllers/echarts_controller.js` 负责加载 ECharts、读取 option JSON、初始化、响应尺寸变化和销毁实例。
- 现有 Controller 只有 `chart`、`data` 两个 target，没有事件输入，也没有公共 option 增强机制。
- `Ec::OperationAction` 已有 SKU、Listing、店铺、操作时间、操作类型、操作人、系统/人工标记和 `diff_result`，无需新表或迁移。
- 当前利润和销售漏斗的 chart option 分别在业务 Controller 内构造，直接在各 builder 中增加 `markLine` 会形成重复实现。

## 任务 1：冻结图表事件 DTO

后端统一返回以下结构。字段语义参考现有运营事件表格，但图表不直接接收 Active Record 对象：

```json
{
  "id": 123,
  "operated_at": "2026-08-18T14:30:00+08:00",
  "event_date": "2026-08-18",
  "operation_type": "listing_pricing",
  "operation_type_label": "价格调整",
  "platform": "ozon",
  "platform_label": "Ozon",
  "store_id": 4,
  "store_name": "Domos",
  "sku_code": "KJ-217-GD",
  "sku_product_id": 456,
  "listing_label": "KJ-217-GD 金色",
  "operator_name": "Valeria",
  "record_by_system": false,
  "diff_summary": ["价格：199 -> 189"],
  "diff_result": {}
}
```

字段规则：

1. `id`、`operated_at`、`event_date`、`operation_type`、`operation_type_label`、`store_name`、`operator_name`、`record_by_system`、`diff_summary` 为图表必需字段。
2. `event_date` 由后端按当前用户 `users.time_zone` 将 `operated_at` 转为日期，前端不得用浏览器默认时区重新判断事件属于哪一天。
3. `platform`、`store_id`、`sku_code`、`sku_product_id` 和 `listing_label` 用于 tooltip 和排查，但前端标记函数不据此重新做业务归属筛选。
4. `operation_type_label`、`platform_label` 和 `diff_summary` 由 Rails I18n 与现有 diff helper 生成；公共 JavaScript 不硬编码业务文案，也不自行解释不断扩展的 `diff_result`。
5. 保留原始 `diff_result` 供需要完整详情的页面使用，但竖线 tooltip 默认只读取已经安全格式化的 `diff_summary`。
6. 所有文本进入 HTML tooltip 前必须转义；不得信任备注、Listing 名、店铺名或 diff 内容。

## 任务 2：公共后端查询与 DTO 组装

新增公共 diff formatter 与 `Ec::OperationActionChartEventsQuery`：

```text
app/services/ec/operation_action_diff_formatter.rb
app/services/ec/operation_action_chart_events_query.rb
```

`Ec::OperationActionDiffFormatter` 负责把 `diff_result` 转成结构化变更项和简短 `diff_summary`；现有 `Erp::OperationActionsHelper` 与图表查询共同调用它，不能复制两套递归解析规则。

统一接口：

```ruby
Ec::OperationActionChartEventsQuery.run(
  sku:,
  from_time:,
  to_time:,
  user_time_zone:,
  store: nil,
  sku_product: nil
)
```

查询约束：

1. 必须限制 `ec_sku_id` 和 `operated_at` 范围；结束边界采用半开区间，避免相邻图表周期重复包含边界事件。
2. SKU 总趋势不传 `store`、`sku_product`，返回当前 SKU 范围内所有事件。
3. 店铺趋势传 `store`；当前一店一 SKU 一 Listing 时，由服务端解析唯一 `sku_product` 后按 `ec_sku_product_id` 精确过滤。
4. Listing 趋势如未来恢复 Listing 选择，必须显式传 `sku_product`；不能用 SKU 级事件猜测归属。
5. 查询结果按 `operated_at ASC, id ASC` 稳定排序，并转换为上述 DTO。
6. 一次预加载 store、sku、sku_product 和 operated_by_user，不得为每个事件逐条查询关联。
7. GET 保持只读，不补写事件、不触发同步。

## 任务 3：抽取纯 JavaScript 标记函数

新增：

```text
app/javascript/lib/echarts_operation_event_markers.js
```

导出单一公共入口：

```javascript
applyOperationEventMarkLines(option, events, {
  seriesId: null,
  xAxisIndex: 0
})
```

职责边界：

1. 输入原始 ECharts option 和标准化事件数组，返回增强后的 option；无事件时原样返回。
2. 按 `event_date` 合并同一天的事件：同一天只画一根竖线，tooltip 按 `operated_at, id` 展示当天全部事件，避免多根线完全重叠。
3. 使用 ECharts `series[].markLine` 绘制竖线，`symbol: ["none", "none"]`，竖线不进入业务图例，不新增假的数据系列。
4. 每根线定位到事件实际日期；默认挂载到指定 `seriesId`，未指定时选择第一个使用目标 X 轴的折线或柱状系列。
5. 合并目标系列已有的 `markLine` 配置和数据，不覆盖告警线、目标线等其它业务标记。
6. tooltip 至少展示：日期、操作类型、平台/店铺、操作人、系统或人工、`diff_summary`；同日多事件逐条分隔。
7. 公共函数只负责 option 增强，不查询接口、不读取 DOM、不初始化或销毁 ECharts，也不判断事件是否属于当前 SKU、店铺或 Listing。
8. 不修改调用方传入的 option 和 events；避免同一 option 在 Turbo 缓存或多图复用时重复追加竖线。

## 任务 4：扩展通用 ECharts Stimulus Controller

在现有 `app/javascript/controllers/echarts_controller.js` 上增加可选 `events` target：

```erb
<div data-controller="echarts">
  <div data-echarts-target="chart"></div>
  <script type="application/json" data-echarts-target="data"><%= raw json_escape(chart_option.to_json) %></script>
  <script type="application/json" data-echarts-target="events"><%= raw json_escape(chart_events.to_json) %></script>
</div>
```

Controller 初始化流程：

```text
解析 option
  -> 存在 events target 时解析事件
  -> applyOperationEventMarkLines(option, events, config)
  -> chart.setOption(enhancedOption)
```

兼容要求：

1. `events` target 完全可选；现有图表不传事件时行为不变。
2. Turbo reconnect 不重复追加 marker，disconnect 继续释放 ResizeObserver 和 ECharts 实例。
3. JSON 解析失败时不初始化半残图表；记录可定位错误，但页面不得执行事件 JSON 中的代码。
4. 一个页面多张图各自传入自己的事件数组，不能从全局变量共享当前 SKU 或店铺状态。

## 任务 5：时间轴统一约束

若要求竖线精确落在“某一天”，接入图表的 X 轴必须能表达真实日期：

1. 新趋势图优先使用 ECharts `xAxis.type = "time"`，series 数据使用 `[ISO8601 时间, value]`。
2. 现有 category 时间轴只有在类别值为标准日期且事件能精确匹配该类别时才能直接接入。
3. 周度类别若只使用“08-17 ~ 08-23”文本，无法把 08-19 的事件精确画在该周内部；需要先改为 time 轴。不得把事件默默吸附到周末或伪装成精确日期。
4. 图表查询与事件查询使用相同用户时区和半开时间范围。

## 各板块接入规则

- 04 SKU 利润趋势：传当前 SKU、图表时间范围内全部运营事件。
- 04 店铺利润趋势：页面只选择店铺，服务端解析唯一 Listing，传该 `sku_product_id` 的事件。
- 05 SKU 漏斗趋势：传 SKU 范围事件；店铺或 Listing 趋势只传明确归属事件。
- 06 SKU 库存趋势：传 SKU 范围事件；若只有店铺库存趋势，按店铺过滤。
- 广告及未来其它趋势：只要 X 轴为时间并符合 DTO/时间轴约束，即可复用同一函数。

## 测试要求

### JavaScript 单元测试

- 无事件时 option 不变。
- 单事件生成一根无端点竖线。
- 同日多事件只生成一根线，tooltip 包含全部事件且顺序稳定。
- 不同日期生成多根线。
- 已有 `markLine` 数据被保留。
- 输入 option/events 不被修改，重复调用不重复追加。
- 文本正确转义，恶意备注不能注入 HTML。
- 指定 `seriesId`、多 Y 轴和无兼容 series 的行为明确。

### Rails 测试

- SKU、店铺和 Listing 范围不会串事件。
- 起止边界、用户时区跨日和同秒多事件排序正确。
- DTO 标签使用 I18n，`diff_summary` 与运营事件表格语义一致。
- 不产生事件逐条关联查询 N+1。

### 页面集成测试

- 04、05 至少各有一张趋势图通过相同 `events` target 接入，不在业务页面拼 `markLine`。
- 无事件、事件接口/Frame 失败和 Turbo 重连不影响基础趋势曲线。

## 验收

- [ ] 不新增运营事件表，继续以 `Ec::OperationAction` 为唯一来源。
- [ ] 任意符合时间轴约束的 ECharts 图表可通过 option + events 调用公共函数获得事件竖线。
- [ ] 同日事件合并为一根线，tooltip 信息完整、安全且使用用户时区。
- [ ] 业务模块不重复实现 `markLine`、同日分组、tooltip 和 HTML 转义。
- [ ] 现有未接入事件的 ECharts 图表无回归。
- [ ] SKU、店铺、Listing 事件归属和查询边界测试通过。
