# 04 利润归集分析

## 目标

在现有 `profit` Tab 内完成原地改造，使用户按“SKU 总体 -> 店铺 / Listing -> 趋势”定位利润变化。保留 WR、WSU、WSU-DEEP 的现有口径，仅将 WR 改造为 Listing 级。当前业务中同一店铺内同一 SKU 只有一个 Listing，因此店铺与 Listing 合并为一个展示单元，不建设重复的独立 Listing 汇总区。

本研发包不新建 Tab、不新建平行报表路由，也不在页面上继续让用户以 `WR / WSU / WSU-DEEP` 技术名称理解业务。

## 与原始改进方针的对应

原《SKU 工作台修改》6.1～6.14 明确提出了以下界面改动，本文将其拆为可研发任务：

- SKU 四周期利润表。
- SKU 近八周“经营规模”和“利润质量”趋势。
- 平台、店铺、Listing 四周期利润表；本期按当前一店一 SKU 一 Listing 的事实省略 Listing 选择器。
- 选中店铺所对应唯一 Listing 的近八周趋势及运营动作标记。
- 新增销售均价、成本占比、其它分摊费用等解释指标。

原文将“Listing 汇总”与 WSU 混用。根据已冻结口径，WSU 仍为 `SKU + 平台 + 店铺`，Listing 明细来自 WR。两者在后台继续保留各自数据口径，界面按当前一店一 SKU 一 Listing 的事实合并为“店铺 / Listing 利润明细”。

## 页面总体结构

`profit` Tab 从上到下为三个展示板块，不使用嵌套卡片：

```text
利润归集分析
|
+-- 1. 周期与 SKU 总览（WSU-DEEP）
|   +-- 等长四周期利润矩阵
|
+-- 2. 店铺 / Listing 利润明细（WSU + WR）
|   +-- 一个店铺 / Listing 为一组
|   +-- 每组按 P-3 / P-2 / P-1 / P0 展示四行
|   +-- 每行横向展示全部利润指标
|
+-- 3. 趋势与运营事件
    +-- SKU 近八周经营规模趋势
    +-- SKU 近八周利润质量趋势
    +-- 选中店铺对应 Listing 的近八周趋势 + 运营事件
```

SKU 总览和店铺 / Listing 明细共用同一选中周期，不允许各自处于不同周期。页面虽然合并店铺与 Listing 展示，后台仍分别保留 WSU 店铺汇总和 WR Listing 明细，用于字段取数和核心指标对账。

## 任务 1：公共周期控制

1. 默认选中最近一个完整自然周（周一至周日），不将当前未结束周作为默认值。
2. 用户可选择由一个或多个完整自然周组成的连续日期范围；选中范围为 `P0`，向前读取三个等长、不重叠周期 `P-1 / P-2 / P-3`。
3. 例如用户选择两周，页面四列合计覆盖连续八周；每列均为两周。`P0` 是用户选中周期，不固定代表当前周。
4. 周期选择复用 `app/views/shared/_time_range_selector.html.erb`；服务端必须校验起止日期落在完整自然周边界，且总天数为 7 的整数倍。
5. 切换周期通过当前 Tab Turbo Frame 刷新，保留 `tab=profit`、`locale` 和当前店铺；本期不引入 Listing 选择参数。
6. 月度模式不在本包内默认开启；只有 00 明确口径后才增加周/月切换，不预留不可用控件。

## 任务 2：SKU 总览

### 数据来源与粒度

- 数据源：WSU-DEEP。
- 粒度：内部 SKU，跨平台、跨店铺汇总。
- 页面只查当前抽屉 SKU，不继续保留无关 SKU 对比作为主流程。

### 等长四周期利润矩阵

主体是一张表格：指标从上到下排列，列为 `P0 / P-1 / P-2 / P-3`，按新到旧展示。页面列头必须显示真实起止日期；`P0` 等名称仅作为研发内部标识。表格必须包含：

| 指标 | 计算/来源 |
|---|---|
| 净销量 | WSU-DEEP 现有净销量 |
| 销售额 | WSU-DEEP 现有销售额 |
| 销售均价 | `销售额 / 净销量` |
| 货物成本 | WSU-DEEP 现有货物成本 |
| 成本占比 | `货物成本 / 销售额` |
| 广告费 | WSU-DEEP 现有广告费 |
| 广告占比 | `广告费 / 销售额` |
| 其它分摊费用 | 越库费 + 罚金 + 现有其它分摊费用 |
| 净利润 | WSU-DEEP 现有净利润 |
| 利润率 | `净利润 / 销售额` |
| 平均每单利润 | 分母由 00 冻结；现有 WSU-DEEP 的 `average_profit_per_order` 实际为 `净利润 / 净销量`，不能仅因字段名写“每单”就视为订单数口径 |
| 年化收益率 | WSU-DEEP 现有 `annualized_return_pct` 口径 |
| 年化净利 | WSU-DEEP 现有口径 |

四列按 `P-3 -> P-2 -> P-1 -> P0` 展示；`P-2 / P-1 / P0` 使用已加载的前一列计算环比，不额外读取 `P-4`。利润查询使用 `include_comparison: false`，跳过报表内置比较归集。零分母返回空值，不显示无穷大或伪造 `0%`。

选择多周时，每个派生指标必须使用该完整周期汇总后的分子、分母或 WSU-DEEP 周期计算结果，禁止把周期内各周的比例、平均每单利润、年化收益率或年化净利再次求平均。

### AI 利润诊断边界

本期不开发 AI 利润诊断。没有真实诊断数据时不渲染空卡片或“即将上线”占位；后续有结构化诊断结果后再单独接入。

## 任务 3：SKU 近八周趋势

趋势固定使用八个完整自然周，以 `P0` 的结束日为右边界，通过独立 Turbo Frame 懒加载。趋势仍按单周落点，不因 `P0` 选择两周而改成两周一个点。不得在 Controller 中循环八次运行完整 WSU-DEEP 报表，必须提供批量周期查询，并使用 `include_comparison: false`。为让运营事件竖线精确落在发生日，X 轴按 03 约束改为 ECharts time 轴，不继续使用“周起止文本”category 轴。

### 经营规模趋势

- 可选：净销量、销售额、净利润、年化净利。
- 默认：净利润、年化净利。
- 数量与金额使用分开 Y 轴，图例可使用复选状态切换指标。

### 利润质量趋势

- 可选：平均每单利润、广告占比、成本回报率/ROI、年化收益率。
- 默认：平均每单利润、年化收益率。
- 金额与百分比使用分开 Y 轴。

两张图均复用现有 ECharts Stimulus controller，展示空数据断点，不将缺失周默认补零连线。运营事件竖线统一接入 03 的 `Ec::OperationActionChartEventsQuery`、`events` target 和 `applyOperationEventMarkLines`，04 不自行拼装 ECharts `markLine`。

## 任务 4：店铺 / Listing 利润明细

### 数据来源与粒度

- 当前业务约束：同一店铺内同一 SKU 只有一个 `Ec::SkuProduct`，页面将平台、店铺和 Listing 作为同一个展示单元。
- WSU 提供 `SKU + 平台 + 店铺` 的人民币核心汇总；WR 提供当前店铺内 Listing 的平台费用明细和趋势底层数据。
- WB 使用 `nm_id` 映射 `Ec::SkuProduct.product_id`；同一 `nm_id` 的白俄、出口等 WR 区域行先聚合到同一个 Listing 展示单元。
- Ozon 使用 `ozon_sku_id` 映射 `Ec::SkuProduct.platform_sku_id`。
- 禁止使用内部 `sku_code` 或 `offer_id` 把 WR 行兜底归属到 Listing。
- WR 原始币种、费用负号必须在服务层标准化为页面人民币口径；ERB 不执行币种换算或正负号修正。

### 展示范围与店铺选择

1. 本期不实现 Listing 选择器、Listing 筛选参数或“显示全部历史 Listing”开关；页面也不预留不可用控件。
2. 当前 SKU 的店铺数量很少，第二部分默认直接展示全部满足以下任一条件的店铺：`P0` 有平台库存、有有效成交或有有效访问。
3. 店铺不需要额外下拉选择器；点击表格中的店铺分组即可将其设为趋势区当前店铺。若未来店铺数量显著增加，再单独评估平台或店铺筛选，不在本期预先实现。
4. 服务端根据 `SKU + 店铺` 唯一解析对应 `Ec::SkuProduct`，用于 WR 归属和运营事件查询；页面不要求用户理解或选择 `sku_product_id`。
5. 当前店铺只影响下方店铺趋势和运营事件，不改变上方 SKU 总览或第二部分其它店铺数据。

### 表格结构

一个店铺 / Listing 固定占四行，每行对应一个等长周期；周期按时间从旧到新排列：`P-3 -> P-2 -> P-1 -> P0`。因此一个 SKU 在两个店铺上架时，正文共有 `2 × 4 = 8` 行。

```text
平台/店铺   Listing       周期             净销量  销售额  销售均价  ...  净利润  利润率
Ozon/Domos  Listing A     P-3 07/06-07/19     ...     ...       ...  ...      ...     ...
                            P-2 07/20-08/02     ...     ...       ...  ...      ...     ...
                            P-1 08/03-08/16     ...     ...       ...  ...      ...     ...
                            P0  08/17-08/30     ...     ...       ...  ...      ...     ...

WB/TaxiLink Listing B     P-3 07/06-07/19     ...     ...       ...  ...      ...     ...
                            P-2 07/20-08/02     ...     ...       ...  ...      ...     ...
                            P-1 08/03-08/16     ...     ...       ...  ...      ...     ...
                            P0  08/17-08/30     ...     ...       ...  ...      ...     ...
```

1. 固定识别列依次为：平台 / 店铺、Listing、周期；平台 / 店铺和 Listing 在同组四行中使用纵向合并单元格或等效粘性分组标题，不重复制造四份视觉噪音。
2. 周期列必须同时显示 `P-3 / P-2 / P-1 / P0` 和真实起止日期；不得只靠行位置或颜色表达周期。
3. 每个周期行之间保留约 8px 的视觉间距或等效分隔，不插入没有语义的空数据行；不同店铺 / Listing 组之间使用更明显的 16px 间距或分组分隔线。
4. 当前已有的利润指标全部横向展开，不提供“单指标切换”菜单。指标列依次为：净销量、销售额、销售均价、货物成本、成本占比、广告费、广告占比、其它可归属费用、净利润、利润率、平均每单利润。
5. 表格在抽屉内允许水平滚动；平台 / 店铺、Listing、周期三列固定在左侧，表头固定在可视区域顶部。
6. 一个周期行即可触发选中当前店铺；趋势命令放在店铺 / Listing 分组识别区，只出现一次，不在四行中重复四个按钮。
7. 表尾可以展示 SKU 各周期核心指标合计，但不得对比例、均值和年化指标直接求和；这些指标使用 SKU 总览结果。

### 字段口径边界

- WSU 与 WR 的净销量、销售额、广告费、货物成本、税前利润和净利润在区域聚合、币种换算及费用符号标准化后必须一致。
- 广告费、货物成本等费用在页面统一显示为正的费用金额，净利润保留正负号。
- “其它分摊费用”调整为“其它可归属费用”，只展示 WR 已明确归属当前 Listing 的越库费、罚金及其它平台费用；具体原始字段必须列白名单。
- 店铺 / Listing 年化收益率、年化净利复用 `Ec::ProjectedStockRoiCalculator`，以店铺净销量和净利润作为分子输入，并沿用 SKU 单位成本、单位体积和相同预测参数；不得复制 SKU 总览结果。
- 平均每单利润的分母仍由 00 冻结；在冻结前不得因现有字段名而默认按订单数或净销量计算。
- WR 的 `unallocated` 是账号级未归属费用，即使查询传入单个 SKU 也不能视为该 SKU 费用。本表不展示、不分摊账号级未归属费用，也不将其纳入单 SKU 对账。
- WR 每个 Listing 结果补充 `sku_product_id`、平台商品 ID、Offer ID、Listing 名、平台和店铺。四周期分桶、选择状态和趋势关联使用 `sku_product_id` 或平台商品 ID 作为稳定键。

## 任务 6：选中店铺近八周趋势

1. 页面只选择店铺，不提供 Listing 选择器；店铺使用单选控件，默认选择四周期表按 `P-1` 净销量降序后的第一家店铺。
2. 与 SKU 趋势一样，以 `P0` 结束日为右边界使用八个完整自然周。可选 SKU 两张趋势图的全部八项指标，默认显示经营规模四项；店铺切换使用已加载数据，不重新查询。
3. 只叠加 `Ec::OperationAction.ec_sku_product_id = 服务端解析的唯一 sku_product_id` 且 `operated_at` 落入图表范围的运营事件。SKU 级、其它店铺或无法精确归属的事件不叠加。
4. 事件标记复用 03 公共能力：按用户时区的事件日期画竖线，同日多事件合并为一根线并在 tooltip 逐条展示；04 不实现自己的同日分组、tooltip 或 HTML 转义逻辑。
5. 趋势使用独立 Turbo Frame 懒加载；更换店铺只刷新对应趋势和运营事件，不重新运行 SKU 总览或店铺 / Listing 四周期表。

## 已冻结统计粒度

| 报表 | 粒度 | 页面定位 |
|---|---|---|
| WR | 单店铺内 Listing | Listing 利润明细与趋势 |
| WSU | `SKU + 平台 + 店铺` | 店铺利润贡献；同店同 SKU 多 Listing 合并 |
| WSU-DEEP | SKU | 跨平台、跨店铺的 SKU 总体利润和 ROI |

## 指标与汇总规则

1. 净销量、销售额、货物成本、广告费、其它费用和净利润先按目标粒度求和。
2. 销售均价、成本占比、广告占比、利润率、平均每单利润、ROI 等比例/均值在本层汇总分子分母后重算，禁止平均下层比例。
3. SKU 总览的其它分摊费用沿用 WSU-DEEP 已归属当前 SKU 的口径；店铺 / Listing 表只展示 WR 明确归属当前 Listing 的其它可归属费用。两者都必须列出原始费用键白名单，不使用“除已知字段外的所有费用”反向归类。
4. 零分母指标返回 `nil`；页面统一显示 `-`。
5. 金额使用报表现有币种和换算口径，不在 ERB 中二次换算或四舍五入。

## 数据层对账规则

```text
WR 当前 Listing 的可归属明细
经过区域聚合、币种换算和费用符号标准化
= WSU 对应 SKU + 平台 + 店铺的核心指标

全部 WSU 店铺行的可加核心指标
= WSU-DEEP 对应 SKU 行的相同核心指标
```

这里的核心指标为净销量、销售额、广告费、货物成本、税前利润和净利润。WR 账号级 `unallocated` 不属于当前 SKU，不参与上述等式。若核心指标不能相等，服务必须返回差额、指标和可定位原因；页面不隐藏差额，也不拿账号级未归属费用强行闭合。

## 查询与加载边界

1. `ReportsController#sku_detail` 仅在 `tab=profit` 时运行利润 loader。
2. 页面结构一次渲染为纵向长页面；分阶段加载是各区域在原位置独立取数，不是切换 Tab 或打开新页面。
3. 第一阶段同步加载周期控制和 SKU 四周期矩阵，使抽屉先出现可用的 SKU 总览。
4. 第二阶段由独立 Turbo Frame 自动加载完整的店铺 / Listing 四周期明细表，加载期间保留稳定高度和加载状态，不推动已展示内容跳动。
5. 第三阶段加载 SKU 八周趋势；选中店铺后再加载其唯一 Listing 的八周趋势和运营事件。更换店铺不重新运行 SKU 总览或四周期明细表。
6. 各趋势使用独立 Turbo Frame 按需加载；任一 Frame 失败不遮蔽其它已加载区域。
7. 所有四周期查询使用 `include_comparison: false`。现有 `WeeklyProfitReports::ReportQueryRunner` 必须增加受调用方控制的内部参数并向 WR、WSU、WSU-DEEP 透传；不要仅把 URL 参数未经校验地直接下传。
8. 四周期使用一个连续范围批量读取并按 `P0 / P-1 / P-2 / P-3` 分桶；八周趋势同样一次读取并按自然周分桶。禁止按周期、周或 Listing 循环运行完整报表；相关店铺账号在一个连续范围内至多归集一次。
9. WSU、WSU-DEEP 与 WR 的公共平台利润归集不得在同一加载结果中重复执行；批量查询服务应从同一份标准化归集行派生 SKU 总览、店铺汇总和 Listing 明细，或复用具有明确失效规则的只读查询结果。
10. 页面 GET 保持只读，不触发利润导入、平台同步、运营事件补写或快照采集。
11. 当前已有 `sku_profit_trend` 路由可继续作为懒加载入口，但必须从“Controller 循环八次 WSU-DEEP”改为批量查询，并拆分经营规模/利润质量两组展示。

### 性能基线与验收预算

2026-08-31 使用生产数据对 `KJ-217-GD` 做只读基线：按现有服务循环“四个单周 × WSU-DEEP、WSU、单店 WR”，共触发 3,192 次 Active Record SQL 通知，其中 1,287 条实际发送到 PostgreSQL、1,905 次命中 Rails 查询缓存，单进程约 1.9 秒。该结果是禁止采用的朴素循环基线，不是 V2 的目标值。

研发验收必须分别记录实际 PostgreSQL 查询数、Rails 缓存命中数、总耗时和对象分配，不能再把 SQL 通知总数表述为真实数据库 SQL。最终预算在实现批量查询后以基准测试冻结；未达到预算前不得用“只有一个 SKU”作为免除性能验收的理由。

- 页面文案全部通过 Rails I18n，不在 ERB、helper、Controller 或图表 JSON 构建中新增硬编码文案。
- 无利润数据、无店铺、无 Listing、未绑定 WR 行、零销售额、部分周缺失和趋势加载失败必须是可区分状态。
- 负数使用警示色但不只靠颜色表意；同时保留负号和明确的下降语义。
- 表格在抽屉内优先使用固定识别列 + 水平滚动，不压缩到指标名或最长数值截断。
- 图表 tooltip 显示周期、指标全名和正确格式的值；不在曲线上同时强制展示所有数值标签。

## 测试要求

### 查询与口径

- WR 每个 Listing 稳定映射到 `Ec::SkuProduct`；未绑定行不进入其它 Listing。
- WB 同 `nm_id` 的区域行汇总到一个 Listing，并保留区域展开明细。
- WSU 同店同 SKU 多 Listing 只返回一行；WSU-DEEP 仍只按 SKU 返回。
- WR 账号级未分配费用不进入单 SKU 表、不强摊且不参与 SKU 店铺对账。
- WR 标准化后的核心指标与 WSU 店铺行闭合；全部 WSU 店铺核心指标与 WSU-DEEP SKU 行闭合，差额必须可定位；各层比例由本层分子分母重算。
- `P0` 支持一个或多个完整自然周；四个周期等长、不重叠并整体向前移动，跨年、零分母、负利润和缺失周期正确。
- 四周期不返回或渲染内置环比，不读取 `P-4`；所有利润查询实际收到 `include_comparison: false`。
- 店铺趋势由服务端解析唯一 `sku_product_id`，只使用其 WR 数据和 `Ec::OperationAction`；页面不提交 Listing 选择参数。

### Controller 与页面

- 非 `profit` Tab 不运行利润查询。
- 四周期一次返回四个等长周期，用户选择两周时覆盖连续八周；八周趋势不循环调用完整报表。
- 切换周期保留当前店铺和 locale；切换店铺不重载 SKU 总览，页面不存在 Listing 选择器。
- SKU 总览、店铺 / Listing 明细和两类趋势的空态/错误态可独立出现，不互相遮蔽。
- 每个店铺 / Listing 恰好展示四个周期行，按 `P-3 -> P-2 -> P-1 -> P0` 排列；两个店铺生成八行。
- 周期行和店铺 / Listing 分组具有明确标签与间距，固定识别列和横向滚动可用，全部指标均可访问。
- 运营 marker 同周多事件不丢失，不串到其它 Listing。
- 抽屉、整页和 Turbo Frame 请求均正常，JSON 响应能力不因 HTML 改造破坏。

- [x] `profit` Tab 不再使用 WR/WSU/WSU-DEEP 技术切换作为主界面，按 SKU 总览、店铺 / Listing 明细和趋势同页展示。

- [x] 查询使用 `include_comparison: false`，页面 GET 保持只读。
