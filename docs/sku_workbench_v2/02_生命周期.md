# 02 生命周期

## 目标

展示 SKU 从首次成交至今的关键事件、当前状态及 Grade/Stage 历史。

时间轴使用专门的生命周期事件投影表，避免每次打开抽屉都跨订单、营销状态、采购、送仓和库存快照实时识别事件。动态经营指标仍读取现有权威查询，不复制到事件表。

## 页面模块

1. 时间轴：使用横向组件，从左到右按业务时间由旧到新排列，用于一眼判断 SKU 大致经营过程。包含首次成交、Grade/Stage 变化、采购下单、采购到货、平台送仓、店铺平台仓断货、SKU 全平台实质断货、库存恢复和当前。首次成交始终固定展示在最左侧；可用宽度不足时，其余空间优先展示最新事件，中间较早历史可折叠。
2. 汇总：首次成交时间、生命周期天数、当前 Grade/Stage、累计净销量、累计销售额、累计净利润、预测日销和库存覆盖。历史不完整时标明数据起点。
3. 状态历史：生效时间、调整前后、调整人、备注，以及变更前最后一个完整周的销量、销售额、利润、利润率、预测日销和库存覆盖。

### 横向时间轴展示原则

- 主视图是横向概览组件，不在默认状态展开成纵向事件清单。
- 左侧第一个业务节点固定为首次成交；尚未成交时显示“尚未成交”占位状态。
- 右侧优先保留最新事件和当前状态，不得为了平均分配空间而隐藏最新风险、采购、断货或恢复事件。
- 被省略的中间历史使用单一折叠节点表达，不在主轴上为每条被隐藏事件保留空占位。
- 底层事件仍完整保留；横向主轴的省略、同日合并和送仓折叠只是查询/展示行为，不删除或合并 `ec_sku_lifecycle_events` 记录。
- 具体可见节点数量、节点宽度、横向滚动、折叠交互和移动端断点在实施阶段根据抽屉实际宽度确定，本需求不提前锁定像素和固定事件数。

## 两条读取链路

### 时间轴事件

只读取 `Ec::SkuLifecycleEvent`：

```ruby
sku.lifecycle_events
  .includes(:sku_product)
  .order(occurred_at: :asc, id: :asc)
```

查询对象从完整有序事件集合中固定选取首次成交，再从最新事件向前填充剩余可见位置，最终仍按时间升序返回给横向组件。页面 GET 不跨原始表补事件，也不执行投影或写库。

### 动态经营数据

继续从权威数据源读取：

- 当前 Grade/Stage：`Ec::SkuMarketingState`。
- 累计销量、销售额和利润：现有订单及利润查询。
- 预测日销、库存覆盖：现有库存和销量预测查询。
- 状态调整前经营数据：按状态生效时间批量读取前一个完整自然周。

动态指标不得写入生命周期事件表作为新的计算来源。

## 新增生命周期事件表

### 命名

- 表：`ec_sku_lifecycle_events`
- 模型：`Ec::SkuLifecycleEvent`
- `Ec::Sku` 增加 `has_many :lifecycle_events`。
- 模型命名统一使用 `lifecycle`，不要使用 `lift_circle`。

研发必须通过 Rails generator 创建 migration，例如：

```bash
bin/rails generate migration CreateEcSkuLifecycleEvents
```

不得手工创建 migration 文件。

### 字段

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `sku_id` | bigint | 是 | 内部 SKU 外键 |
| `sku_product_id` | bigint | 否 | 能明确归属 Listing 时填写 |
| `event_type` | string | 是 | 事件类型，不使用 STI 保留字段 `type` |
| `occurred_at` | datetime | 是 | 业务事件发生时间 |
| `content` | jsonb | 是 | 展示所需的事件快照，默认 `{}` |
| `source_type` | string | 否 | 来源记录类型或稳定来源名称 |
| `source_id` | bigint | 否 | 来源记录 ID |
| `source_key` | string | 是 | 全局唯一的幂等键 |
| `created_at` | datetime | 是 | 记录创建时间 |
| `updated_at` | datetime | 是 | 记录更新时间 |

不单独存 `title` 或硬编码展示文案。标题和描述根据 `event_type`、`content` 通过 Rails I18n 生成。

### 索引与约束

- `source_key` 唯一索引。
- `[sku_id, occurred_at]` 索引。
- `[sku_product_id, occurred_at]` 索引。
- `[event_type, occurred_at]` 索引。
- `sku_id` 外键必填；`sku_product_id` 外键可空。
- `event_type` 使用模型白名单校验。
- 若填写 `sku_product_id`，该 Listing 必须归属于同一个 SKU。

### 第一版事件类型

```text
first_sale
marketing_state_changed
purchase_ordered
purchase_received
replenishment
platform_stockout
all_platform_stockout
stock_recovered
```

不要将价格、广告等全部运营动作复制到生命周期表。只有产品确认属于生命周期关键节点的运营事件，后续才增加新的 `event_type`。

### content 约定

`content` 保存事件发生时用于展示的事实快照，不保存动态计算指标。例如：

```json
{
  "from_grade": "B",
  "from_stage": "grw",
  "to_grade": "A",
  "to_stage": "mat",
  "quantity": 200,
  "store_id": 12,
  "cluster_name": "Москва"
}
```

允许字段按事件类型不同，但每种类型必须在模型或投影服务中定义固定 schema，并在测试中验证必要字段。

## 事件来源、时间字段与幂等键

时间轴中的每种事件必须按以下规则投影。不得在实现时自行选择另一个日期字段，也不得使用 `created_at`、`updated_at`、`synced_at` 代替缺失的业务时间。

### 事件 1：首次成交

事件含义：该 SKU 第一次产生被现有有效销量口径认可的订单。

| 项目 | 精确定义 |
|---|---|
| 主来源表 | `ec_orders`、`ec_order_items`、`ec_sku_products` |
| SKU 关联 | Ozon：`ec_sku_products.store_id = ec_order_items.store_id`、平台均为 `ozon`、`ec_sku_products.platform_sku_id = ec_order_items.platform_sku_id`；WB：店铺和平台相同、`ec_sku_products.product_id = ec_order_items.platform_sku_id` |
| 有效状态 | `ec_orders.order_status IN ('pending', 'processing', 'shipped', 'delivered')`，与 `Ec::SkuDailySalesQuery` 排除 `cancelled`、`returned` 的口径一致 |
| 必要条件 | `ec_orders.ordered_at IS NOT NULL`、`ec_order_items.quantity > 0`、商品硬关联成功 |
| 事件时间 | 满足条件的最早 `ec_orders.ordered_at` |
| 同时刻排序 | `ec_orders.ordered_at ASC, ec_orders.id ASC, ec_order_items.id ASC`，取第一条 |
| `sku_id` | 硬关联所得 `ec_sku_products.sku.id` |
| `sku_product_id` | 第一条成交商品对应的 `ec_sku_products.id`；用于展示首次成交平台和店铺 |
| `source_type` | `Ec::Order` |
| `source_id` | 第一条成交对应的 `ec_orders.id` |
| `source_key` | `first_sale:sku:<sku_id>` |
| `content` | `order_id`、`order_item_id`、`platform`、`store_id`、`sku_product_id`、`quantity`、`platform_sku_id` |

后续导入更早的历史订单，或原首单变为 `cancelled`/`returned` 时，投影器重新寻找最早有效订单，并使用同一 `source_key` 更新 `occurred_at`、`source_id`、`sku_product_id` 和 `content`，不能新增第二条首次成交。

如果 SKU 已不存在任何有效成交，删除其 `first_sale:sku:<sku_id>` 投影事件；这是投影纠错，不代表删除原订单。

### 事件 2：Grade / Stage 变化

事件含义：SKU 的 Grade、Stage 或二者发生一次生效变更。

| 项目 | 精确定义 |
|---|---|
| 来源表 | `ec_sku_marketing_states` |
| 来源记录 | 每一条 `Ec::SkuMarketingState` |
| 事件时间 | `ec_sku_marketing_states.effective_at` |
| `sku_id` | `ec_sku_marketing_states.sku_id` |
| `sku_product_id` | `NULL` |
| 调整前状态 | 同 SKU 中 `effective_at < 当前 effective_at` 的最后一条；排序 `effective_at DESC, id DESC`。没有前一条时为初始状态 |
| 调整后状态 | 当前记录的 `grade`、`stage` |
| `source_type` | `Ec::SkuMarketingState` |
| `source_id` | `ec_sku_marketing_states.id` |
| `source_key` | `marketing_state:<ec_sku_marketing_states.id>` |
| `content` | `from_grade`、`from_stage`、`to_grade`、`to_stage`、`changed_by_id`、`note`、`initial_state` |

第一条营销状态也生成事件，`initial_state = true`，前态为空。若历史存在相同 `effective_at`，按 `id` 处理先后，不使用 `created_at` 判断。

### 事件 3A：采购下单

事件含义：内部 SKU 建立了一批已经下单的正常采购批次。该事件只表示向供应商下单，不表示货物已进入内部库存或平台仓。

| 项目 | 精确定义 |
|---|---|
| 主来源表 | `ec_sku_batches` |
| 可选补充表 | `ec_purchase_order_items`、`ec_purchase_orders`，仅用于补充采购单号和供应商信息 |
| 筛选条件 | `ec_sku_batches.batch_type = 1`（`normal`）；`status IN ('ordered', 'in_transit', 'received', 'closed')`；`purchase_date IS NOT NULL`；`purchased_quantity > 0` |
| 事件时间 | `ec_sku_batches.purchase_date` 在 `Asia/Shanghai` 当日 `00:00:00` |
| 时间精度 | `content.time_precision = 'date'`，页面只显示日期，不显示人为生成的 00:00 |
| `sku_id` | 通过 `ec_sku_batches.sku_code = ec_skus.sku_code` 获取 |
| `sku_product_id` | `NULL`，采购库存属于内部 SKU |
| 数量 | `ec_sku_batches.purchased_quantity` |
| `source_type` | `Ec::SkuBatch` |
| `source_id` | `ec_sku_batches.id` |
| `source_key` | `purchase_ordered:sku_batch:<ec_sku_batches.id>` |
| `content` | `batch_code`、`purchased_quantity`、`purchase_unit_price_cny`、`supplier_id`、`expected_arrival_on`、`status`、`time_precision`；如有关联采购单，再加入 `purchase_order_id`、`order_no` |

`expected_arrival_on`、`received_on`、`ec_purchase_orders.ordered_on`、记录 `created_at` 均不作为该事件时间。`purchase_date` 为空时不生成事件，进入投影审计结果，禁止回退到其它字段。批次编码为 `INIT-*` 不影响投影：只要补齐权威业务日期并满足上述条件，仍按正常事件生成，同时在 `content.initialized_batch = true` 保留历史初始化标识。

### 事件 3B：采购到货

事件含义：正常采购批次的货物已进入内部账面库存。采购到货不等于 WB/Ozon 平台送仓完成，页面必须使用不同图标、标题和说明。

| 项目 | 精确定义 |
|---|---|
| 来源表 | `ec_sku_batches` |
| 筛选条件 | `batch_type = 1`（`normal`）；`status IN ('received', 'closed')`；`received_on IS NOT NULL`；`received_quantity > 0` |
| 事件时间 | `ec_sku_batches.received_on` 在 `Asia/Shanghai` 当日 `00:00:00` |
| 时间精度 | `content.time_precision = 'date'` |
| `sku_id` | 通过 `ec_sku_batches.sku_code = ec_skus.sku_code` 获取 |
| `sku_product_id` | `NULL`，采购到货属于内部 SKU |
| 数量 | `ec_sku_batches.received_quantity`，不回退使用 `purchased_quantity` |
| `source_type` | `Ec::SkuBatch` |
| `source_id` | `ec_sku_batches.id` |
| `source_key` | `purchase_received:sku_batch:<ec_sku_batches.id>` |
| `content` | `batch_code`、`received_quantity`、`received_on`、`purchase_date`、`expected_arrival_on`、`supplier_id`、`status`、`initialized_batch`、`time_precision` |

`received_on` 为空时不使用 `expected_arrival_on`、`created_at` 或 `updated_at` 回退。已到货但 `expected_arrival_on` 晚于 `received_on` 时，事件仍以 `received_on` 为准，并在投影审计结果中记录日期冲突；不得把预计日期展示为当前仍待到货。

### 事件 4A：WB 送仓完成

事件含义：一个 WB 送仓单中的该 Listing 已产生实际接收数量。

| 项目 | 精确定义 |
|---|---|
| 主来源表 | `raw_wb_supplies` |
| 商品表 | `raw_wb_supply_items` |
| Listing 映射 | `raw_wb_supply_items.account_id` 对应 WB 店铺账号，`raw_wb_supply_items.nm_id = ec_sku_products.product_id`，同时限定该账号对应 `ec_stores.id` 和平台 `wb` |
| 筛选条件 | `raw_wb_supplies.status_id IN (5, 6)`；`raw_wb_supplies.fact_date IS NOT NULL`；`raw_wb_supply_items.accepted_qty > 0` |
| 状态含义 | `5 = accepted`，`6 = unloaded_at_gate`，取现有 `Ec::WbSupplyOrderChangeRecorder::STATUS_NAMES` |
| 事件时间 | `raw_wb_supplies.fact_date` |
| `sku_id` | 映射所得 `ec_sku_products.sku.id` |
| `sku_product_id` | 映射所得 `ec_sku_products.id` |
| 数量 | `raw_wb_supply_items.accepted_qty`，不使用计划 `quantity` |
| `source_type` | `RawWb::SupplyItem` |
| `source_id` | `raw_wb_supply_items.id` |
| `source_key` | `wb_supply_received:<account_id>:<wb_supply_id>:<nm_id>` |
| `content` | `account_id`、`wb_supply_id`、`preorder_id`、`nm_id`、`planned_quantity`、`accepted_quantity`、`warehouse_id/name`、`actual_warehouse_id/name`、`transit_warehouse_id/name`、`status_id` |

若同一送仓单后续增加 `accepted_qty`，使用相同 `source_key` 更新数量。`supply_created_at` 是建单时间、`supply_date` 是计划时间、`scan_dt` 是扫描时间、`synced_at` 是同步时间，均不得代替 `fact_date`。

### 事件 4B：Ozon 送仓完成

事件含义：一个 Ozon 送仓单已完成，其中每个 Listing 各生成一条完成事件。

| 项目 | 精确定义 |
|---|---|
| 来源表 | `raw_ozon_supply_orders` |
| 商品数据 | `raw_ozon_supply_orders.items`，结构为 `{ platform_sku_id => quantity }` |
| Listing 映射 | `account_id` 对应 Ozon 店铺账号，items 的 key 等于 `ec_sku_products.platform_sku_id`，同时限定该账号对应 `ec_stores.id` 和平台 `ozon` |
| 筛选条件 | `raw_ozon_supply_orders.status = 'COMPLETED'`；`items` 中该商品数量大于 0；`raw_json['state_updated_date']` 可解析 |
| 事件时间 | `Time.zone.parse(raw_ozon_supply_orders.raw_json['state_updated_date'])` |
| `sku_id` | 映射所得 `ec_sku_products.sku.id` |
| `sku_product_id` | 映射所得 `ec_sku_products.id` |
| 数量 | `raw_ozon_supply_orders.items[platform_sku_id]` |
| `source_type` | `RawOzon::SupplyOrder` |
| `source_id` | `raw_ozon_supply_orders` 记录 ID |
| `source_key` | `ozon_supply_completed:<account_id>:<supply_order_id>:<platform_sku_id>` |
| `content` | `account_id`、`supply_order_id`、`order_number`、`platform_sku_id`、`quantity`、`timeslot`、`drop_off_warehouse`、`destination_warehouses`、`state_updated_date` |

`raw_ozon_supply_orders.created_at` 是建单时间，`timeslot` 是计划时间段，`synced_at` 是同步时间，均不得作为完成时间。状态为 `COMPLETED` 但 `state_updated_date` 缺失或不可解析时，不生成事件并进入投影审计结果。

### 事件 5A：店铺平台仓断货

事件含义：某 SKU 在某平台店铺的 FBO/FBW 平台仓库存从正数进入持续为零的状态。断货保持现有店铺库存粒度，不生成 Listing 级事件。

| 项目 | 精确定义 |
|---|---|
| 来源表 | `ec_snapshots` |
| 快照范围 | `snapshot_type = 'inventory'` 且 `sku_id IS NOT NULL` |
| 库存来源 | `content['distribution']['levels']` |
| 分组键 | `sku_id + level.platform + level.store_id`；`store_id` 为空时使用 `account_id`，但两者不得混为同一键 |
| 计入库存 | WB 只合计 `fulfillment_type = 'fbw'`；Ozon 只合计 `fulfillment_type = 'fbo'` |
| 不计入库存 | `fbs`、`inbound`、账面库存、采购中库存 |
| 有效观察 | 当日该分组至少存在一条目标 fulfillment level，并且该 level 的 `synced_at` 在 `Asia/Shanghai` 的日期等于 `snapshot_date` |
| 进入断货 | 前一个有效观察库存 `> 0`，随后连续 3 个有效观察日库存为 `0` |
| 事件时间 | 连续零库存区间第一天的 `snapshot_date`，转换为 `Asia/Shanghai` 当日 `00:00:00` |
| 时间精度 | `content.time_precision = 'date'`，页面只显示日期 |
| `sku_id` | `ec_snapshots.sku_id` |
| `sku_product_id` | `NULL` |
| `source_type` | `Ec::Snapshot` |
| `source_id` | 连续零库存第一天对应的 `ec_snapshots.id` |
| `source_key` | `platform_stockout:<sku_id>:<platform>:<store_or_account_key>:<first_zero_date>` |
| `content` | `platform`、`store_id`、`account_id`、`store_name`、`previous_quantity`、`quantity = 0`、`first_zero_date`、`confirmed_on`、`consecutive_zero_days`、`fulfillment_types`、`time_precision` |

快照日期断档、目标 level 缺失、level 的 `synced_at` 不是当日，都属于无观察数据，既不是零库存，也不能累计连续天数。店铺平台仓断货属于重要经营事件，直接展示在 SKU 主时间轴；同一 SKU 同时有多个店铺断货时，各店铺分别保留事件，并通过时间轴滚动查看。

### 事件 5B：SKU 全平台实质断货

事件含义：同一内部 SKU 在全部 WB/Ozon 店铺的平台仓可售库存已无法支撑正常销售。这是 SKU 级主时间轴事件，不生成 Listing 级断货。

| 项目 | 精确定义 |
|---|---|
| 来源表 | `ec_snapshots` |
| 快照范围 | `snapshot_type = 'inventory'` 且 `sku_id IS NOT NULL` |
| 平台库存总量 | 当日 `content['distribution']['levels']` 中 WB `fbw` + Ozon `fbo` 的 `quantity` 合计，覆盖该 SKU 全部店铺 |
| 预测日销 | 同一快照的 `content['overview']['daily_sales_velocity']` |
| 平台库存覆盖 | 预测日销 `> 0` 时，`platform_stock / daily_sales_velocity`；否则为 `NULL` |
| 有效观察 | 当日至少有一条 WB `fbw` 或 Ozon `fbo` level，所有计入的 level 的 `synced_at` 在 `Asia/Shanghai` 的日期都等于 `snapshot_date`；任一应存在的已绑定店铺缺少目标 level 时，当日无效 |
| 实质断货日 | `platform_stock <= 1`，或预测日销 `> 0` 且平台库存覆盖 `< 1` 天 |
| 进入断货 | 连续 3 个有效观察日均为实质断货日；第 3 日确认，事件发生日回填为连续区间第 1 日 |
| 事件时间 | 连续区间第 1 日 `snapshot_date` 在 `Asia/Shanghai` 当日 `00:00:00` |
| `sku_product_id` | `NULL` |
| `source_type` | `Ec::Snapshot` |
| `source_id` | 区间第 1 日的 `ec_snapshots.id` |
| `source_key` | `all_platform_stockout:<sku_id>:<started_on>` |
| `content` | `started_on`、`confirmed_on`、`platform_stock`、`wb_fbw_stock`、`ozon_fbo_stock`、`daily_sales_velocity`、`platform_cover_days`、`threshold_quantity = 1`、`confirmation_days = 3`、`time_precision = 'date'` |

`fbs`、`inbound`、采购中库存和账面库存不计入平台库存总量。间歇出现 1 件残留库存不中断实质断货。投影时必须使用当日快照内保存的预测日销，不得用当前预测日销回算历史。

### 事件 5C：库存恢复

库存恢复是新的历史事件，不修改、删除或覆盖已确认的断货事件。

| 项目 | 精确定义 |
|---|---|
| 来源表 | `ec_snapshots` |
| 恢复日 | `platform_stock >= 2`，且（预测日销为空/零，或 `platform_stock / daily_sales_velocity >= 2` 天） |
| 确认恢复 | 断货后连续 2 个有效观察日均为恢复日；第 2 日确认，事件发生日为连续区间第 1 日 |
| `source_type` | `Ec::Snapshot` |
| `source_id` | 恢复区间第 1 日的 `ec_snapshots.id` |
| `source_key` | `stock_recovered:all_platform:<sku_id>:<stockout_started_on>:<recovered_on>` |
| `content` | `scope = 'all_platform'`、`stockout_source_key`、`stockout_started_on`、`recovered_on`、`confirmed_on`、`platform_stock`、`wb_fbw_stock`、`ozon_fbo_stock`、`daily_sales_velocity`、`platform_cover_days`、`confirmation_days = 2`、`time_precision = 'date'` |

店铺平台仓严格断货也可按同一模式生成 `scope = 'platform_store'` 的恢复事件，其恢复条件为连续 2 个有效观察日库存 `> 0`。店铺级恢复与全平台恢复均直接展示在主时间轴。

### 断货历史不可变规则

1. 后续采购下单、采购到货、平台送仓或库存恢复，均不得更新或删除断货事件。
2. 断货事件的 `occurred_at`、`source_id`和事发当日 `content` 在确认后保持不变。持续天数不回写到断货事件，由查询层使用恢复事件或当前日期计算。
3. 恢复后再次进入断货，以新的 `started_on` 生成新断货事件。
4. 只有原始快照迟到/纠错或人工显式重建才能修正历史。重建必须指定 SKU 和日期范围，输出新增、修改、删除的审计结果，禁止页面 GET 或普通定时任务静默改写已确认历史。

### 事件生成总表

| `event_type` | 业务事件 | 事件时间字段 | 一条事件的业务键 |
|---|---|---|---|
| `first_sale` | 首次成交 | `ec_orders.ordered_at` | 每个 SKU 一条当前有效投影 |
| `marketing_state_changed` | Grade/Stage 生效 | `ec_sku_marketing_states.effective_at` | 每条 marketing state 一条 |
| `purchase_ordered` | 正常采购批次下单 | `ec_sku_batches.purchase_date` | 每个 SKU batch 一条 |
| `purchase_received` | 正常采购批次到货 | `ec_sku_batches.received_on` | 每个 SKU batch 一条 |
| `replenishment` | WB 送仓完成 | `raw_wb_supplies.fact_date` | 每个送仓单 + `nm_id` 一条 |
| `replenishment` | Ozon 送仓完成 | `raw_json['state_updated_date']` | 每个送仓单 + platform SKU 一条 |
| `platform_stockout` | 店铺平台仓连续为零 | 首个有效零库存 `snapshot_date` | 每个店铺的每次断货区间一条 |
| `all_platform_stockout` | SKU 全平台实质断货 | 实质断货连续区间首日 `snapshot_date` | 每次全平台断货区间一条 |
| `stock_recovered` | 库存达到恢复条件 | 恢复连续区间首日 `snapshot_date` | 每个断货区间最多一条 |

## 生命周期事件投影器

新增统一服务，建议命名：

```ruby
Ec::SkuLifecycleEventProjector.run(
  sku_ids: nil,
  from_date: nil,
  to_date: nil
)
```

职责：

1. 从权威来源读取事件。
2. 生成稳定 `source_key` 和标准 `content`。
3. 使用 `upsert_all` 或等价方式幂等写入。
4. 只更新允许变化的投影字段：首次成交可因迟到订单改投到更早来源；同一送仓单可因平台补齐接收数量更新 `content`。
5. 已确认断货事件不因后续任何业务事件变化；恢复必须新增 `stock_recovered`，持续天数由查询层计算。
6. 按事件类型执行纠错：`first_sale` 是“当前最早有效成交”的投影，来源失效时允许更新或删除；采购、营销状态、已完成送仓、已确认断货和库存恢复属于历史事实，默认不因当前查询范围变化而删除。确需撤销时，必须提供显式、可审计的重建任务。

页面和 Controller 不得直接拼装、创建或修复生命周期事件。

## 写入与执行时机

### 明确业务事件

Grade/Stage、采购下单、采购到货和送仓记录成功后，可以在原业务事务完成后触发投影；不能让投影失败回滚平台原始数据同步。建议由后台任务执行，并保留定时补偿。

### 派生事件

首次成交、断货和库存恢复由定时投影任务计算：

- 首次成交在订单同步完成后投影。
- 店铺平台仓断货、SKU 全平台实质断货和库存恢复在每日库存快照完成后按顺序投影。
- 任务需支持指定日期和 SKU 补跑。

### 历史回填

首次上线前执行一次全量 backfill。Backfill 与日常投影使用同一服务和 `source_key`，重复执行不得生成重复事件。

生产调度方式需在实现时加入 `config/recurring.yml`，执行顺序必须保证断货投影晚于 `daily_snapshot`。

## 生命周期查询对象

建议 `Ec::SkuLifecycleQuery` 返回：

```ruby
{
  summary: {},
  events: [],
  marketing_state_changes: [],
  data_started_on: nil
}
```

要求：

- `events` 只读事件表。
- 使用 `stock_recovered.content.stockout_source_key` 与断货事件配对；已配对的持续天数为 `recovered_on - started_on`，未配对则为用户当前日期 `user_today - started_on + 1`。
- 默认主轴展示 `platform_stockout`、`all_platform_stockout`，以及 `platform_store` 和 `all_platform` 两种范围的库存恢复。
- 送仓事件同日过多时仅在查询结果中按日期和平台分组展示，不合并或删除底层事件记录。
- 经营指标批量查询，禁止每个事件分别运行周利润和库存查询。
- 首次成交不存在时返回明确状态，生命周期天数为 `nil`。
- 所有日期边界使用用户时区，时间展示使用 `display_time`。

## 不允许存入事件表的数据

- 当前预测日销。
- 当前库存覆盖。
- 累计销量、销售额和净利润。
- Grade/Stage 调整前一周的完整经营指标。
- 页面格式化后的标题、货币和百分比字符串。

这些值会变化或已有权威查询。写入事件表会产生多份口径和过期数据。

例外：断货/恢复事件可保存事件当日的 `daily_sales_velocity` 和 `platform_cover_days`，它们是用于解释当时判定的历史事实快照，不得作为当前预测日销或当前库存覆盖的读取来源。

## 测试要求

### 模型

- `event_type`、`occurred_at`、`source_key` 必填。
- `source_key` 唯一。
- Listing 与 SKU 归属一致。
- 各事件类型必要 content 字段校验。

### 投影器

- 重复运行不重复写入。
- 后导入更早订单会更新首次成交时间。
- 原首次成交订单取消后改投影到下一笔有效订单；不存在有效订单时删除首次成交投影。
- Grade/Stage 每条状态记录生成一条事件。
- 采购事件只使用 `ec_sku_batches.purchase_date`；日期为空、非 normal batch、draft batch 不生成。
- 采购到货只使用 `received_on` 和 `received_quantity`；不回退使用预计到货日、采购数量或记录创建时间。
- 同一 batch 的采购下单和采购到货各生成一条事件，并使用不同 `source_key`。
- WB 只有 `status_id IN (5, 6)`、`fact_date` 存在且 `accepted_qty > 0` 才生成；修改接收数量只更新原事件。
- Ozon 只有 `status = 'COMPLETED'` 且 `raw_json['state_updated_date']` 可解析才生成。
- WB/Ozon 缺少权威完成时间时均不回退使用创建或同步时间。
- 快照断档不生成断货，店铺平台仓连续 3 个有效观察日为零才生成。
- SKU 全平台合计连续 3 个有效观察日满足数量/覆盖阈值时，事件日期为第 1 日而非确认日。
- 断货后间歇出现 1 件库存不恢复；连续 2 个有效观察日达到恢复阈值才生成独立 `stock_recovered` 事件。
- 后续采购、送仓和库存恢复不更新或删除已确认断货；持续天数由断货与恢复事件动态计算。
- FBS、inbound 和账面库存变化不生成平台仓断货事件。
- 按 SKU、日期补跑只影响指定范围。

### 查询与页面

- 页面 GET 不写生命周期事件。
- 横向时间轴从左到右按时间升序，始终保留最左侧首次成交锚点，其余可见位置优先最新事件。
- 可见位置不足时生成中间历史折叠节点，且不改变底层事件集合。
- 尚未成交时状态明确且生命周期天数为空。
- 状态调整前指标取前一个完整周，且批量查询。
- 无事件、部分历史、跨年周和用户时区正确。
- 恢复事件能与对应断货配对，历史区间持续天数固定，尚未恢复区间的持续天数随 `user_today` 增长。
