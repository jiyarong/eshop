## 什么是平台分仓

平台分仓是决定以下事项的完整业务过程：

- 已确定的商品和待分仓数量如何分配。
- 补到哪些平台区域、集群或仓库。
- 通过直送还是中转送货。
- 选择什么包装方式和送货日期。
- 如何跟踪运输、验收和上架结果。

本项目中的分仓 Agent 不负责判断是否需要补货或提醒补货。商品和待分仓总量由独立的上游补货流程确定，分仓 Agent 负责把既定数量分配到平台、店铺和平台仓库，并继续处理平台执行与对账。

### 主要目标

1. 减少缺货，保证重点区域有货。
2. 缩短配送时效，提高转化率。
3. 控制库存总量，避免滞销和高额仓储费。
4. 控制入库、中转和运输成本。
5. 减少大量 SKU 带来的人工操作。

这些目标会互相冲突。例如，把商品分到更多区域可能改善配送时效，但也会造成库存碎片化，增加头程、入库和仓储成本。

## 分仓的完整流程

```text
商品绑定
  ↓
接收上游给定的 SKU 和待分仓数量
  ↓
跨平台、跨店铺分配自有库存
  ↓
在平台店铺内部按区域或集群分配数量
  ↓
调用平台接口校验仓库和包装准入
  ↓
检查预约容量、入库费、中转费和仓储费
  ↓
按照整箱、整托和体积要求调整
  ↓
创建供货草稿
  ↓
选择仓库、中转方式和送货日期
  ↓
装箱或装托并打印平台标签
  ↓
运输、到仓和验收
  ↓
核对计划量、实收量和上架量
  ↓
将结果反馈给上游补货流程和下一轮分仓
```

## 核心术语

| 术语 | 含义 |
|---|---|
| 可售库存 | 当前能够正常出售的库存 |
| 在途库存 | 已进入供货流程但尚未成为可售库存的商品 |
| 待分仓数量 | 上游补货流程已经确定、交给分仓 Agent 分配的数量 |
| 店铺配额 | 待分仓数量分配给某个平台、店铺的数量上限 |
| 分仓量 | 店铺配额继续分配到区域、集群或仓库的数量 |
| 最终目的仓 | 商品最终存储和销售的仓库 |
| 中转仓 | 卖家实际交货后，由平台继续转运的仓库 |
| 直送 | 直接送达最终目的仓 |
| Cross-dock | 送到交货点后由平台转运至最终目的仓 |
| FBW | Fulfillment by Wildberries，货物存放在 WB 仓库 |
| FBO | Fulfillment by Ozon，货物存放在 Ozon 仓库 |
| FBS | 货物存放在卖家仓库，订单产生后再发给平台 |
| ShK | WB 使用的条码或标签编号 |

## 商品主数据

自动分仓必须能够准确完成以下转换：

```text
内部 SKU
  ↓
店铺
  ↓
平台商品
  ↓
平台商品规格
  ↓
平台供货使用的商品标识
```

如果一个内部 SKU 绑定多个规格、绑定到错误店铺，或者缺少平台商品标识，后续销量、库存和发货建议都会失真。

### WB 商品标识

| 标识 | 含义 | 来源 |
|---|---|---|
| `vendorCode` | 卖家货号 | 卖家 |
| `nmID` | WB 商品卡片 ID | WB |
| `chrtID` | 商品规格或尺码 ID | WB |
| `barcode` | FBW 供货使用的商品条码 | 卖家提供或 WB 生成 |
| `packageCode` | 箱或托盘的包装 ShK | WB |
| `supplyId` | 正式供货单 ID | WB |

WB FBW 建单及仓库准入校验主要使用 `barcode + quantity`，不能用内部 SKU、`vendorCode` 或 `nmID` 直接代替商品条码。

### Ozon 商品标识

| 标识 | 含义 |
|---|---|
| `offer_id` | 卖家货号 |
| `product_id` | Ozon 商品 ID |
| `sku` | Ozon 平台 SKU，FBO 接口常用 |
| `draft_id` | FBO 供货草稿 ID |
| `order_id` | FBO 供货单 ID |

## 库存与在途口径

计算前至少需要区分：

- 可售库存。
- 预留库存。
- 不可售库存。
- 已创建但尚未发货的在途。
- 已发货但尚未到仓的在途。
- 已到仓但尚未验收。
- 已验收但尚未上架。
- 本地可发库存。

### 有效在途

只有仍可能正常完成入库的数量才能作为区域分配和执行判断中的有效在途。

以下情况不应继续作为有效在途：

- 供货单已取消。
- 平台已拒收。
- 商品已从供货单删除。
- 长期停滞并已确认不能正常入库。
- 实际验收结果已经表明存在缺货或差异。

### 当前项目库存来源

Ozon FBO 可售库存主要使用：

```http
POST /v1/analytics/stocks
```

WB FBW 库存主要使用：

```http
GET /api/v1/warehouse_remains
```

平台库存通过定时任务同步到 `Ec::SkuInventoryLevel`。报表 GET 请求只读取数据库，不应直接调用平台 API 或触发写库。

## 上游补货流程边界

分仓 Agent 的输入是上游流程已经确认的：

```text
内部 SKU
待分仓总量
可用时间或批次
必要的业务限制
```

分仓 Agent 不负责：

- 判断哪些 SKU 需要补货。
- 计算 SKU 总补货量。
- 设置目标库存或覆盖天数。
- 生成缺货或补货提醒。
- 自行扩大上游给定的待分仓数量。

销量、平台库存和在途仍可作为“既定数量应该分到哪里”的依据，但不能被分仓 Agent 用来重新决定总补货量。

如果上游数量与实际可执行条件冲突，分仓 Agent 应返回未分配数量和原因，而不是静默修改上游任务。

## 区域和仓库分配

### 基础权重法

```text
区域权重 = 区域销量 / 全部区域销量
区域建议量 = 上游待分仓数量 × 区域权重
```

### 区域优先级法

可以结合每个区域的销量、可售库存和有效在途判断既定数量的分配优先级。

区域优先级只用于分配既定数量，不用于决定是否补货或总补货量。具体权重和评分方式需要单独验证后再确定。

### 必须满足的约束

```text
所有分仓建议之和 <= 上游给定的 SKU 待分仓数量
```

还应限制：

- 一个 SKU 最多分到几个仓。
- 单仓最低发货数量。
- 单仓最高库存数量。
- 本地库存不足时的区域优先级。
- 整箱取整后的剩余数量如何分配。

### 区域、集群和仓库关系

```text
销售区域
  ↓
平台集群
  ↓
最终目的仓
  ↓
可能的中转仓或交货点
```

必须区分最终目的仓和卖家实际交货仓，两者在中转供货中不是同一个仓库。

### WB 仓库表

`raw_wb_warehouse_regions`：

- 表示 WB 平台的 FBW 仓库及区域。
- 可以作为 FBW 最终目的仓候选目录。
- `warehouse_id` 是 WB 平台仓库或 Office ID。

`raw_wb_warehouses`：

- 来自 `GET /api/v3/warehouses`。
- 表示卖家自己的 FBS 仓库。
- 不能作为 FBW 供货目的仓。

仓库存在于 `raw_wb_warehouse_regions`，不代表当前商品、数量和日期一定能够送入该仓。

## 平台准入校验

平台准入应分为两次：第一次用于获取候选仓库、包装能力、日期和费用约束；完成多 SKU 拼箱、拼托和配送优化后，第二次使用完整方案做最终复核。第一次的结果不是最终预约承诺。

```text
候选准入查询
  -> 包装与配送优化草案
  -> 完整方案最终复核
  -> 通过后预约并锁定执行
```

优化改变 SKU 组合、数量、包装类型、仓库或日期时，都可能使第一次准入失效。最终复核失败后，可根据平台明确返回的原因重新优化一次；仍失败则拆分方案或转人工处理。

平台仓库准入会受以下条件影响：

- 商品条码和商品品类。
- 商品尺寸、体积及危险品属性。
- 发货数量。
- 包装类型。
- 仓库容量。
- 仓库临时关闭。
- 送货日期和时段。
- 付费验收系数。

### WB

校验商品可以进入哪些仓库及支持的包装类型：

```http
POST /api/v1/acceptance/options
```

请求的核心数据：

```json
[
  {
    "barcode": "2052183571202",
    "quantity": 50
  }
]
```

主要返回字段：

- `warehouseID`
- `canBox`
- `canMonopallet`
- `canSupersafe`
- `isBoxOnPallet`

查询未来接货容量和费率：

```http
GET /api/tariffs/v1/acceptance/coefficients
```

查询中转路线和费用：

```http
GET /api/v1/transit-tariffs
```

### Ozon

Ozon 通常先按集群产生分仓建议，再通过 FBO 草稿计算返回当前真正能够接收整批商品的仓库及可预约时段。

因此 ERP 输出的是建议目的仓，最终可执行仓库必须以平台草稿计算结果为准。

## 包装、标签和运输

分仓数量还需要转换成实际包装方案。

常见约束：

- 箱装、单件托盘或 SuperSafe。
- 每箱、每托盘允许的条码数量。
- 每个条码在包装中的件数。
- 是否必须整箱。
- 商品总体积。
- 超过一定体积后是否必须上托。
- 是否需要 KIZ 等商品标识。

包装结构示例：

```text
供货单 40673325
└── 托盘 WB_1617431493
    ├── 商品条码 2052183571202 × 50
    └── 商品条码 2052203734440 × 32
```

需要区分三种标签：

| 标签 | 用途 |
|---|---|
| 商品 `barcode` | 识别单件商品规格 |
| 包装 ShK | 识别某个箱子或托盘 |
| 供货 ShK | 识别整张供货单 |

包装 ShK 和供货 ShK 必须使用平台生成的编号，ERP 只能保存和打印，不能自行编造。

运输环节还可能需要：

- 司机姓名和电话。
- 车辆牌照和车型。
- 每台车辆对应的包装。
- 仓库通行证。
- 中转仓收货地址。
- 报关单或其他进口单据。

## 供货单生命周期

```text
建议生成
  ↓
草稿
  ↓
已预约
  ↓
已计划
  ↓
待发货
  ↓
运输中
  ↓
到仓
  ↓
验收中
  ↓
已验收
  ↓
已上架
```

异常状态包括：

- 草稿过期。
- 预约失败。
- 商品或仓库被拒绝。
- 供货单取消。
- 延迟到仓。
- 少货、多货或错货。
- 仓库拒收。
- 验收后仍不可售。

系统需要持续同步：

```text
计划数量
包装数量
运输数量
验收数量
可售数量
差异数量
```

## WB 与 Ozon 的差异

### Ozon FBO

Ozon 公开了相对完整的写入链路：

```text
创建草稿
→ 查询草稿计算结果
→ 查询时段
→ 创建供货单
→ 查询异步创建状态
→ 创建货件和标签
→ 同步供货状态
```

适合基于官方 API 逐步实现自动建单。

### WB FBW

WB 公开 API 当前可以完成：

- 查询 FBW 库存。
- 查询已有 FBW 供货单。
- 获取 WB 仓库。
- 校验商品和包装准入。
- 查询接货系数。
- 查询中转路线。

WB Seller 后台内部支持完整的 FBW 建单流程：

```text
创建 UUID 草稿
→ 保存条码和数量
→ 获取仓库推荐
→ 选择包装和仓库
→ 选择送货日期
→ 创建包装单元
→ 生成包装 ShK
→ 创建通行证
→ 生成正式 supplyId
```

但截至 2026-08-03，公开的 WB Seller API 未提供创建 FBW 草稿、预约、包装和正式提交的写接口。

比较稳妥的 WB 实施方式：

```text
ERP 自动计算分仓
→ 公开 API 自动校验
→ ERP 生成 WB 导入 Excel
→ 人工在 Seller 后台上传、预约和提交
```

直接调用 Seller 后台内部接口会依赖登录态和未公开契约，存在页面改版、接口变化、验证码和平台风控风险。

## 自动化风险与保护措施

### 主要风险

1. 任务重试后重复创建供货单。
2. 没有识别已有在途，造成重复分仓或重复发货。
3. 多仓建议合计超过上游给定的待分仓数量。
4. 区域销量、库存或在途口径错误，导致分仓位置失真。
5. 商品绑定错误，发错店铺或规格。
6. 仓库临时关闭或拒绝接收商品。
7. 忽略整箱、体积和包装要求。
8. 忽略付费验收、中转和仓储成本。
9. 平台已创建草稿，但本地任务误判失败后再次创建。
10. 计划数量、实际发货量和验收量不一致。

### 必要保护措施

- 使用业务幂等键。
- 为同一 SKU 的重复分仓和平台写入设置冷却期。
- 提交前重新读取库存和有效在途。
- 限制店铺配额、SKU 待分仓总量和单仓发货量。
- 保证分仓合计不超过上游给定的待分仓数量。
- 设置付费验收和物流费用上限。
- 按箱规和托盘规则取整。
- 高价值、大数量和低置信度任务必须人工审批。
- 定时同步平台状态并处理取消、拒收和差异。

## 推荐实施路线

### 第一阶段：可信的推荐系统

- 校正内部 SKU 与平台商品的绑定。
- 明确上游待分仓任务、区域销量、库存和在途口径。
- 在报表中展示每个计算因子。
- 保证分仓合计不超过上游给定的待分仓数量。
- 给出置信度、数据完整度和异常提示。
- 不向平台写入任何数据。

### 第二阶段：平台可执行性校验

- WB 接入 `acceptance/options` 和接货系数。
- Ozon 创建草稿并读取平台计算结果，但不正式提交。
- 检查仓库、包装、日期和费用。
- 将无法自动执行的建议转入人工处理。

### 第三阶段：半自动建单

- 自动生成每个 WB 目的仓的导入 Excel。
- Ozon 自动创建供货草稿。
- 人工检查数量、仓库、包装和费用。
- 审批后才提交平台。

### 第四阶段：有限全自动

优先自动处理：

- 销量稳定的 A 类商品。
- 商品绑定完整的商品。
- 非新品、非季节性商品。
- 免费或低成本验收。
- 数量低于安全上限。
- 不涉及特殊包装、危险品和特殊标识。

以下情况继续人工审批：

- 高价值商品。
- 新品和历史数据不足的商品。
- 销量突然增长。
- 高额付费验收。
- 大批量供货。
- 特殊包装、KIZ 或进口单据。

## 业务规则确认清单

正式开发自动分仓前，需要确认：

- [ ] 上游补货流程如何提供 SKU 和待分仓数量？
- [ ] 分仓 Agent 是否允许只分配部分数量并返回剩余量？
- [ ] 区域销量、库存和在途使用什么口径？
- [ ] 哪些供货状态影响区域分配和平台执行？
- [ ] 在途多久未更新后视为异常？
- [ ] 单仓最低发货量是多少？
- [ ] 是否必须按照整箱数量发货？
- [ ] 一个 SKU 最多分到几个仓？
- [ ] 既定数量无法全部落仓时如何返回上游？
- [ ] 是否接受付费验收？
- [ ] 单仓或单次供货最高费用是多少？
- [ ] 哪些商品允许自动提交？
- [ ] 哪些条件必须人工审批？
- [ ] 审批后多久必须完成实际发货？
- [ ] 取消、拒收和验收差异如何回滚？
- [ ] 如何防止同一批建议重复创建供货单？

## 推荐的策略配置结构

后续可以将业务规则固化成分仓策略，而不是散落在报表代码中：

```yaml
inbound:
  stale_after_days: 30
allocation:
  max_warehouses_per_sku: 3
  minimum_quantity_per_warehouse: 5
  require_full_carton: true
cost_limits:
  allow_paid_acceptance: false
  maximum_acceptance_cost: 0
approval:
  maximum_automatic_quantity: 100
  require_for_new_products: true
  require_for_low_confidence: true
```
