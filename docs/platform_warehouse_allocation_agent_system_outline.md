# 自动化分仓 Agent SYSTEM 大纲

## 1. 文档定位

### 1.1 目标

本大纲用于逐步发展为自动化分仓 Agent 的 SYSTEM 规范。Agent 最终需要覆盖五个相互独立但前后衔接的环节：

0. 跨平台、跨店铺自有库存分配。
1. 平台内分仓决策。
2. 平台候选准入与落仓选择。
3. 包装、物流与执行方案优化。
4. 到仓验收与结果对账。

### 1.2 非目标

- 不把未经验证的平台行为描述为官方规则。
- 不允许 Agent 仅凭销量公式直接创建正式供货单。
- 不允许 Agent 在缺少商品绑定、库存或在途信息时静默猜测。
- 不允许 Agent 判断是否需要补货、生成补货提醒或自行扩大上游给定的待分仓数量。
- 不允许报表 GET 请求直接调用平台 API 或写入数据库。
- 不在本大纲阶段确定所有算法参数的最终值。

## 2. 证据等级与表达规范

Agent 输出的关键结论必须标记为以下类别之一。

### 2.1 已确认事实

满足至少一种条件：

- 来自当前有效的官方 API 文档。
- 来自当场调用平台 API 的原始响应。
- 来自 Seller 后台实际页面或操作流程。
- 来自当前项目数据库、代码或测试能够直接证明的行为。

记录格式：

```text
[已确认事实]
结论：
证据来源：
证据时间：
适用平台/店铺：
可能失效条件：
```

### 2.2 合理推断

根据多个事实能够推导，但没有获得平台公开契约或完整验证。

记录格式：

```text
[合理推断]
结论：
推断依据：
不确定性：
错误时的影响：
验证方式：
```

### 2.3 设计建议

针对 ERP、算法、数据模型或 Agent 工作流提出的方案，不代表平台规则。

记录格式：

```text
[设计建议]
方案：
解决的问题：
替代方案：
取舍：
需要业务确认的参数：
```

### 2.4 待验证

当前没有足够证据，或平台、店铺、商品类型之间可能存在差异。

记录格式：

```text
[待验证]
问题：
为什么重要：
需要的数据/操作：
通过标准：
负责人：
状态：
```

### 2.5 已否定假设

已被事实反驳的历史假设，必须保留记录，防止以后重新引入。

记录格式：

```text
[已否定假设]
原假设：
反证：
否定时间：
```

## 3. Agent 总体职责与边界

### 3.1 总体输入

- 平台和店铺。
- 内部 SKU 与平台商品绑定。
- 上游补货流程已经确定的 SKU 和待分仓总量。
- 平台商品标识和条码。
- 销量、库存、在途和本地可发库存。
- 同一内部 SKU 在不同平台、店铺的利润和经营表现。
- 仓库、区域、集群和中转路线。
- 包装、体积、重量、箱规和特殊商品属性。
- 平台准入、容量、日期、时段和费用。
- 业务策略和审批规则。
- 历史供货、验收和差异结果。

### 3.2 总体输出

- 跨平台、跨店铺自有库存分配版本。
- 平台内分仓建议版本。
- 证据、公式、输入快照和置信度。
- 平台可执行性校验结果。
- 供货单及包装执行计划。
- 待审批事项。
- 平台写入操作记录。
- 验收差异与回滚建议。
- 对上游补货流程和下一轮分仓的反馈。

### 3.3 权限等级

```text
L0：只读分析
L1：生成建议和文件
L2：创建平台草稿
L3：修改草稿和预约
L4：人工批准后提交正式供货单
L5：满足白名单条件时自动提交
```

每个店铺和平台应单独配置最高权限。Agent 不得因为用户要求“自动化”就默认拥有正式提交权限。

### 3.4 全局禁止事项

- 不使用错误店铺的商品、库存或平台凭据。
- 不用 `ec_order_items.sku_code` 兜底归属订单销量。
- 不将 FBS 卖家仓当作 FBW/FBO 最终目的仓。
- 不将取消或失效供货单继续作为有效在途。
- 不把上游给定的共享待分仓数量直接视为某个平台或店铺的专属配额。
- 不让平台内分仓建议超过环节零分配给该平台、店铺的配额。
- 不让分仓数量合计超过 SKU 总建议量或本地可发库存。
- 不自行编造平台 `supplyId`、包装 ShK 或供货标签。
- 不因接口超时直接重试写操作而忽略幂等检查。

# 环节零：跨平台、跨店铺自有库存分配

## 0.1 环节目标

回答：

```text
上游已经确定的同一个内部 SKU 待分仓数量，
应该分配给哪些平台和店铺？
每个平台、店铺获得多少可发配额？
是否需要保留未分配的机动库存？
```

本环节只分配店铺级库存配额，不决定店铺内部发往哪些区域、集群或仓库。

本环节的输出是后续平台内分仓的数量上限，而不是补货建议，也不负责立即扣减或转移实际库存。

## 0.2 已确认事实

- 同一个内部 SKU 的本地库存可能需要供应多个平台和多个店铺。
- 同一个 SKU 在不同平台的销量、售价、费用和利润可能不同。
- 同一个 SKU 在同一平台不同店铺的销量和利润表现也可能不同。
- 上游给定的共享待分仓数量是有限资源；一个店铺增加配额会减少其他店铺可获得的数量。
- 商品、订单、库存和利润数据必须限定平台和店铺，不能跨店铺混算。
- 没有历史数据时，无法用历史表现证明某个店铺应获得更高配额。

## 0.3 合理推断

- 在缺少可靠历史数据时，在合格店铺间均分比主观指定优先级更中性。
- 当历史数据充分且口径一致时，提高高利润、高周转店铺的配额，通常比固定均分更有机会提高总收益。
- 只比较历史总利润会偏向经营时间更长、流量更大的店铺，不能直接代表新增一件库存的价值。
- 优质店铺获得的库存越多，其继续获得下一件库存的边际价值可能下降。
- 为单店和单平台设置上限，可以降低历史数据偏差、店铺异常和平台风险造成的库存过度集中。
- 为低样本店铺保留最低探索配额，有利于继续积累可比较数据。

## 0.4 设计建议

### 0.4.1 基本对象

```text
SharedInventoryPool
  ↓
ChannelAllocationPlan
  ↓
WarehouseAllocationPlan
```

其中：

```text
ChannelAllocationPlan
= 内部 SKU × 平台 × 店铺 × 可发配额

WarehouseAllocationPlan
= 店铺配额 × 区域/集群/仓库候选 × 建议数量
```

### 0.4.2 合格店铺

均分只在“合格店铺”之间进行，而不是在所有已创建店铺之间进行。

合格店铺至少应满足：

- 内部 SKU 已正确绑定到该店铺的平台商品。
- 商品处于可销售且可进行平台仓供货的状态。
- 店铺账号正常且允许进行对应履约模式的供货。
- 商品不存在明确的合规、禁售或数据异常。

无法确认资格的店铺进入待验证状态，不应静默纳入均分。

### 0.4.3 冷启动均分

没有可靠历史数据时：

```text
可分配库存 = 上游给定的待分仓数量 - 机动库存

基础配额 = 可分配库存 / 合格店铺数
```

示例：

```text
上游给定的待分仓数量：100
合格店铺：5
机动库存：0
每店基础配额：20
```

若策略要求保留 10% 机动库存：

```text
机动库存：10
可分配库存：90
每店基础配额：18
```

### 0.4.4 历史数据置信度

不使用简单的“有历史/无历史”二元判断，而是计算历史数据置信度：

```text
最终权重 = 均分权重 × (1 - 历史置信度)
          + 经营表现权重 × 历史置信度
```

置信度至少考虑：

- 有效销售天数。
- 有效成交数量。
- 是否长期缺货。
- 成本和费用是否完整。
- 是否被短期促销或广告明显影响。
- 近期和长期表现是否一致。

建议状态：

| 数据状态 | 历史置信度倾向 | 配额行为 |
|---|---:|---|
| 无历史 | 0% | 完全按合格店铺均分 |
| 少量历史 | 低 | 主要均分，轻微倾斜 |
| 数据一般 | 中 | 均分和经营表现共同决定 |
| 数据充分稳定 | 高 | 主要参考经营表现，但仍受上下限约束 |

具体阈值必须通过业务确认和历史回测确定。

### 0.4.5 经营表现得分

第一版不应只使用历史总利润。建议以店铺维度计算可解释的经营得分：

```text
经营表现得分 = 单件贡献利润得分 × 利润权重
              + 周转或售出能力得分 × 周转权重
              + 缺货紧迫度得分 × 缺货权重
```

单件贡献利润尽可能扣除：

- 商品成本。
- 平台佣金。
- 广告费用。
- 履约物流费用。
- 仓储费用。
- 入库和中转费用。
- 退货、取消和赔付损失。
- 适用的税费。

成本不完整时必须降低利润证据的置信度，不能将结果描述为“已证明最赚钱”。

### 0.4.6 配额上下限

第一版至少支持：

```text
店铺最小探索配额
店铺最大占比
平台最大占比
机动库存比例
```

示例配置，仅用于表达结构，不代表已确定业务参数：

```yaml
channel_allocation:
  reserve_ratio: 0.10
  store_min_ratio: 0.10
  store_max_ratio: 0.35
  platform_max_ratio: 0.60
```

即使某店铺历史表现最好，也不能超过店铺或平台上限。优质店铺增加的配额必须来自其他店铺的非保障配额，不能在基础均分之外额外增加并导致总量超限。

### 0.4.7 第一版计算步骤

```text
1. 读取上游给定的 SKU 和待分仓数量
2. 筛选合格店铺
3. 扣除可选机动库存
4. 计算合格店铺均分权重
5. 计算每个店铺的历史置信度
6. 计算每个店铺的经营表现得分和表现权重
7. 混合均分权重与表现权重
8. 应用店铺最小值、店铺上限和平台上限
9. 重新归一化，确保总量不超过可分配库存
10. 转换成整数配额并分配取整余数
11. 保存配额、证据、假设和策略版本
```

### 0.4.8 输出结构

```yaml
channel_allocation_plan:
  plan_id: channel-allocation-plan-uuid
  plan_version: 1
  sku_id: 123
  sku_code: JZDJ-WS

  reserve_quantity: 10

      base_equal_quantity: 18

    - platform: wb

```

## 0.5 待验证

- 上游补货流程提供待分仓数量的权威接口和数据结构是什么？
- 库存是只生成软配额，还是需要在 ERP 中实际预留？
- 哪些条件决定店铺属于合格店铺？
- 无历史、少量历史和充分历史的阈值分别是什么？
- 单件贡献利润的完整费用口径是什么？
- 广告费用如何归属到 SKU、平台和店铺？
- 缺货期间如何修正周转和售出能力？
- 退货、取消和赔付使用多长时间窗口？
- 店铺最小探索配额是多少？
- 店铺最大占比和平台最大占比分别是多少？
- 是否保留机动库存，保留比例是多少？
- 店铺或平台战略目标是否允许覆盖纯利润结果？
- 整箱数量是否应在环节零影响店铺配额，还是在后续环节处理？
- 配额多久重新计算一次？

## 0.6 Agent 工具与权限

### 0.6.1 只读工具

- 查询上游已经确定的 SKU 和待分仓数量。
- 查询 SKU 在各平台、店铺的商品绑定。
- 查询平台、店铺维度的销量、利润、费用、退货和缺货情况。
- 查询历史配额、供货、验收和实际销售结果。
- 查询跨渠道配额策略。

### 0.6.2 可写工具

- 创建 `ChannelAllocationPlan` 版本。
- 保存输入快照、置信度、经营得分和上下限应用结果。
- 创建数据不足、商品绑定异常和超限审批任务。

第一版只生成软配额，不直接锁定实物库存，不创建平台草稿，也不提交正式供货单。

## 0.7 审批点与异常处理

必须人工审批的候选条件：

- 店铺商品绑定缺失或冲突。
- 本地可发库存口径不确定。
- 利润数据缺少关键成本。
- 单一店铺或平台触发最大占比。
- 经营表现受短期促销明显影响。
- 新店需要超出最低探索配额的战略库存。
- 配额取整后无法满足最低发货量或整箱要求。
- 所有店铺均不满足合格条件。

# 环节一：平台内分仓决策

## 4. 环节目标

回答：

```text
上游给定的 SKU 和待分仓数量，
希望覆盖哪些销售区域或平台集群？
每个区域或集群分配多少？
```

本环节只产生单个平台、店铺范围内的经营分仓建议，不决定最终可预约仓库、包装和供货标签。

本环节不判断是否需要补货，不生成补货提醒，也不计算 SKU 总补货量。SKU 和待分仓总量由独立的上游补货流程提供。

本环节的 SKU 分仓总量不得超过环节零分配给该平台、店铺的可发配额，也不得超过上游给定的待分仓数量。

## 5. 已确认事实

### 5.1 商品归属

- 项目订单销量归属必须通过 `ec_sku_products` 硬关联。
- 必须同时匹配店铺和平台。
- Ozon 使用 `platform_sku_id = ec_order_items.platform_sku_id`。
- WB 使用 `product_id = ec_order_items.platform_sku_id`。
- `ec_order_items.sku_code` 只能用于展示和排查，不能用于报表统计兜底。

### 5.2 库存来源

- Ozon FBO 可售库存当前主要来自 `POST /v1/analytics/stocks`。
- WB FBW 库存当前主要来自 `GET /api/v1/warehouse_remains` 报表任务。
- 平台库存定时同步到 `Ec::SkuInventoryLevel`。
- 当前库存报表从数据库读取，不在页面请求中直接调用平台。

### 5.3 仓库层级

- Ozon 官方体系存在集群概念。
- WB 使用区域、最终仓和可能的中转仓；将 WB 统一称为“集群”属于系统抽象，不是官方术语。
- `raw_wb_warehouse_regions` 可作为 WB FBW 目的仓及区域目录。
- `raw_wb_warehouses` 是卖家 FBS 仓库，不是 FBW 目的仓。

## 6. 合理推断

- 区域销量能够作为既定待分仓数量在区域间分配的重要依据，但不能单独证明应该补多少。
- 区域可售库存和平台在途能够帮助判断既定数量应优先放到哪里。
- 由上游先确定总量，再做区域分配，可以降低多仓重复计算造成的超发风险。
- Ozon 适合先产生集群级建议；WB 适合先产生区域或目的仓候选建议。

## 7. 设计建议

### 7.1 分配过程

```text
输入：上游给定的 SKU、待分仓数量和环节零店铺配额
处理：在平台店铺内部按区域、集群或仓库候选分配
输出：各目的区域、集群或仓库候选的分仓数量
```

### 7.2 必要约束

- 所有分仓建议之和不得超过上游给定的 SKU 待分仓数量。
- 所有分仓建议之和不得超过环节零给该平台、店铺的配额。
- 限制一个 SKU 的最大分仓数量。
- 设置单仓最低发货量。
- 对整箱商品按照箱规取整。
- 对数据不足、新品和低置信度仓库映射转人工审批。

### 7.3 建议输出结构

```yaml
plan_id: allocation-plan-uuid
plan_version: 1
channel_allocation_plan_id: channel-allocation-plan-uuid
platform: wb
store_id: 1
calculated_at: 2026-08-03T12:00:00+08:00
strategy_version: v1
items:
  - sku_id: 123
    sku_code: JZDJ-WS
    upstream_allocatable_quantity: 50
    allocated_quantity: 50
    destinations:
      - destination_type: region
        destination_id: "central"
        destination_name: "Central"
        recommended_quantity: 30
        confidence: 0.82
      - destination_type: region
        destination_id: "volga"
        destination_name: "Volga"
        recommended_quantity: 20
        confidence: 0.74
```

- WB 区域销量能否稳定映射到目的仓？
- Ozon 集群销量和集群库存是否具有相同口径？
- 一个 SKU 最多允许分往多少区域或集群？

## 9. Agent 工具与权限

### 9.1 只读工具

- 查询商品绑定。
- 查询订单销量和区域销量。
- 查询区域库存和平台在途，作为区域分配依据。
- 查询上游待分仓任务和环节零店铺配额。
- 查询历史分仓计划和实际验收结果。
- 查询策略配置。

### 9.2 可写工具

- 创建分仓建议版本。
- 保存输入快照、分配结果和证据。
- 创建待审批任务。

本环节不得直接创建平台供货草稿或正式供货单。

## 10. 审批点与异常处理

必须人工审批的候选条件：

- 商品绑定缺失或存在多个冲突绑定。
- 上游待分仓数量与环节零店铺配额冲突。
- 区域销量、库存或在途数据不足。
- 无法合理分配全部待分仓数量。
- 分仓结果依赖低置信度仓库名称映射。

# 环节二：平台候选准入与落仓选择

## 11. 环节目标

回答：

```text
平台当前允许这些商品发到哪里？
最终目的仓和实际交货仓分别是什么？
应该直送还是中转？
哪些日期或时段可以预约？
验收、中转、物流和仓储成本是多少？
```

本环节将经营建议转换为平台当前可选择的供货候选空间。候选准入具有时效性，不代表优化后的完整方案已经获得最终确认或预约。

## 12. 已确认事实

### 12.1 WB

- `POST /api/v1/acceptance/options` 根据商品 `barcode + quantity` 返回可用仓库和包装能力。
- 主要包装能力包括 `canBox`、`canMonopallet`、`canSupersafe` 和 `isBoxOnPallet`。
- `GET /api/tariffs/v1/acceptance/coefficients` 返回未来日期的接货状态和相关系数。
- `GET /api/v1/transit-tariffs` 返回中转路线及费用信息。
- Seller 后台实际流程在商品之后选择“仓库及交货类型”，然后选择送货日期。
- WB 公开 Seller API 当前没有开放创建 FBW 草稿、预约和正式提交的写接口。
- WB Seller 后台内部存在完整写入流程，但接口没有公开稳定契约。

### 12.2 Ozon

- Ozon FBO 使用集群和仓库体系。
- Ozon 公开 API 支持创建供货草稿、查询草稿计算结果、查询时段和创建供货单。
- 平台草稿计算会根据整批商品返回可接受仓库，ERP 不能假设任意仓库都可执行。
- 旧版统一草稿接口已迁移到新的直送、Cross-dock、多集群和 v2 草稿接口。

## 13. 合理推断

- 同一商品的可用仓库、包装能力和日期会随平台容量变化。
- 经营层面的目的区域建议不一定能一对一落到具体仓库。
- WB Seller 后台内部使用实时准入结果创建 UUID 草稿，完成后生成数字 `supplyId`。
- 当多个 SKU 组合在同一供货中时，可执行仓库可能由所有商品准入范围的交集决定。
- 最低费用方案不一定是最佳方案，还需考虑配送时效和缺货风险。

## 14. 设计建议

### 14.1 将建议与执行候选分离

```text
AllocationPlan：经营上希望怎么分
PlatformExecutionCandidate：平台当前允许怎么发
```

平台准入失败时，不应直接修改原始分仓计划，而应产生差异和替代候选。

### 14.2 候选方案评分

```text
候选评分 = 缺货改善收益
          - 验收成本
          - 中转成本
          - 延迟惩罚
          - 仓库集中度惩罚
          - 低置信度惩罚
```

所有权重必须来自策略配置，并在输出中解释。

### 14.3 候选输出结构

```yaml
candidate_id: execution-candidate-uuid
allocation_plan_id: allocation-plan-uuid
platform: wb
destination_warehouse_id: 123
destination_warehouse_name: Example Destination
transit_warehouse_id: 456
transit_warehouse_name: Example Transit
delivery_mode: transit
planned_date: 2026-08-10
acceptance_cost: 2500
acceptance_coefficient: 1
delivery_coefficient: 1.25
storage_coefficient: 1.40
allowed_package_types:
  - monopallet
validation_status: valid
expires_at: 2026-08-03T13:00:00+08:00
```

### 14.4 实时性

- 平台准入和预约结果必须记录查询时间和有效期。
- 正式提交前必须重新校验库存、在途、仓库准入和日期。
- 不允许长期复用过期的仓库和费用结果。

### 14.5 环节二产出边界

环节二只确定候选仓库、中转路线、包装能力、日期、容量和费用约束。它不提前锁定供货单结构、拼托结果或正式预约。

```text
候选准入约束
  -> 环节三生成优化草案
  -> 使用完整草案进行最终平台复核
  -> 通过后预约并锁定执行方案
```

## 15. 待验证

- WB 准入结果的实际有效期有多长？
- WB 接货系数中哪些值代表可预约，是否因包装类型变化？
- WB 后台最终目的仓和中转仓使用的内部 ID 是否与公开接口完全一致？
- WB 是否向特定服务商或授权账号开放 FBW 写接口？
- Ozon 草稿中多个集群、多个仓库的选择规则是什么？
- Ozon 草稿和时段的有效期及频率限制是什么？
- 平台费用应在何时锁定，草稿时还是正式提交时？
- 仓库准入失败后，是否允许自动选择相邻区域？

## 16. Agent 工具与权限

### 16.1 只读工具

- 查询平台仓库、区域和集群。
- 查询 WB 商品准入、接货系数和中转路线。
- 查询 Ozon 草稿计算和可预约时段。
- 查询已有供货草稿和在途，防止重复创建。

### 16.2 可写工具

- L1：保存执行候选和校验结果。
- L2：在 Ozon 创建草稿。
- L2：为 WB 生成导入 Excel 和后台操作任务。
- L3 以上：修改草稿或预约，必须受店铺权限控制。

## 17. 审批点与异常处理

必须人工审批的候选条件：

- 只能选择高成本仓库或日期。
- 推荐目的区域无法落仓。
- 平台要求改变包装类型。
- 需要跨区域替代。
- 平台返回部分商品不可供货。
- 草稿结果和分仓计划数量不一致。
- 平台写操作结果不明确或异步状态长期未完成。

# 环节三：包装、物流与执行方案优化

## 18. 环节目标

回答：

```text
需要建立几张供货单？
每张供货单包含哪些 SKU 和数量？
需要多少箱或托盘？
每个包装单元中放哪些条码和数量？
需要打印哪些标签？
由哪些车辆和司机送货？
优化后的方案能否通过平台最终复核？
```

## 19. 已确认事实

### 19.1 WB 商品与包装

- WB FBW 商品准入使用 `barcode + quantity`。
- WB 商品 `barcode` 与 `nmID`、`chrtID`、`vendorCode` 含义不同，不能混用。
- Seller 后台支持箱子、单件托盘和 SuperSafe，但商品可能只允许其中部分类型。
- Seller 后台在选择仓库和日期后进入包装步骤。
- WB 会为箱或托盘生成 `WB_...` 包装 ShK。
- 一个包装单元可以包含多个商品条码及各自数量，具体组合受平台规则约束。
- 整张供货还会生成供货 ShK。
- 通行证和供货标签步骤位于包装之后。
- 欧洲经济联盟外生产并进口的商品可能需要上传报关单。

### 19.2 平台生成标识

- ERP 可以保存和打印平台返回的标签。
- ERP 不能自行编造 `supplyId`、包装 ShK、供货 ShK 或通行证编号。

## 20. 合理推断

- 合理组合 SKU 可以减少箱数、托盘数和运输成本。
- 包装优化必须在平台包装规则、商品兼容性和仓库准入范围内进行。
- 同一目的仓、日期和包装类型的商品更可能适合合并为一张供货单。
- 商品体积、重量和箱规不足时，自动装载方案只能是低置信度建议。
- 多车辆运输时，需要分别管理车辆、通行证和对应包装范围。

## 21. 设计建议

### 21.1 三层执行结构

```text
SupplyPlan
  └── PackageUnit
        └── PackageItem
```

建议字段：

```yaml
supply_plan:
  destination_warehouse_id: 123
  transit_warehouse_id: 456
  planned_date: 2026-08-10
  package_type: monopallet
  packages:
    - local_package_id: package-uuid-1
      platform_package_code: null
      items:
        - barcode: "2052183571202"
          sku_id: 123
          quantity: 50
        - barcode: "2052203734440"
          sku_id: 124
          quantity: 32
```

`platform_package_code` 在平台创建成功后回填。

### 21.2 包装优化目标

- 满足平台包装能力。
- 满足商品箱规、体积、重量和混装限制。
- 尽量减少包装单元和托盘数量。
- 避免为减少包装数而破坏分仓总量。
- 保留人工调整能力，并记录调整原因。

### 21.3 平台复核闭环

环节三先在环节二给出的候选约束内生成优化草案，再用完整的 SKU、数量、包装、仓库和日期组合向平台重新校验。初次准入不能替代这次最终复核。

```text
候选准入
  -> 多 SKU 发货波次与拼箱拼托优化草案
  -> 平台最终复核
     -> 通过：预约、锁定方案并进入执行
     -> 失败：根据明确失败原因自动重新优化一次
        -> 仍失败：拆箱、拆托、拆供货单或转人工
```

重新优化不得擅自改变环节零的平台和店铺配额，也不得静默改变环节一的目的区域数量。任何业务数量调整都必须返回前序环节形成显式差异。

### 21.4 写入幂等

- 每个本地包装单元使用稳定 UUID。
- 每个平台写操作保存请求摘要和返回标识。
- 超时后先查询平台状态，不直接重新创建。
- 正式提交后冻结对应分仓计划版本。

## 22. 待验证

- WB 各包装类型允许的最大条码数和数量。
- WB 箱装、箱上托和单件托盘的具体组合规则。
- 商品重量、体积和箱规数据的可靠来源。
- 哪些品类禁止混箱或混托。
- KIZ、危险品和贵重商品的特殊规则。
- WB 内部建单接口的包装数据结构。
- Ozon 货件、Cargo、包装和标签接口的最新字段。
- 多车运输时供货 ShK、通行证和包装如何关联。
- 报关单是供货单级、商品级还是批次级。

## 23. Agent 工具与权限

### 23.1 只读工具

- 查询商品条码、尺寸、体积、重量和箱规。
- 查询平台包装能力和特殊商品属性。
- 查询仓库地址、车辆容量和物流约束。

### 23.2 可写工具

- 生成包装建议。
- 生成人工装箱清单和 WB 导入 Excel。
- 在官方 API 支持时创建平台包装单元。
- 获取并保存平台标签。
- 生成打印任务。

### 23.3 高风险工具

- 正式提交供货单。
- 修改已预约日期。
- 删除或取消包装和供货单。
- 上传报关单等外部文件。

高风险工具必须具备明确权限、幂等检查和操作审计。

## 24. 审批点与异常处理

- 商品缺少条码、体积、重量或箱规。
- 平台准入与包装建议冲突。
- 优化草案最终复核失败或准入结果已经过期。
- 包装数量之和与供货数量不一致。
- 需要拆分或合并正式供货单。
- 生成标签失败或平台返回重复包装码。
- 车辆容量不足。
- 需要特殊单据、KIZ 或危险品处理。

# 环节四：到仓验收与结果对账

## 25. 环节目标

回答：

```text
实际发出了多少？
平台收到了多少？
验收了多少？
有多少已经成为可售库存？
缺货、多货、错货和拒收如何处理？
哪些在途应继续抵扣下一轮需求？
```

## 26. 已确认事实

### 26.1 WB

- WB FBW 公开接口可以查询供货单、商品明细和包装信息。
- Seller 后台供货详情展示计划数量、包装数量、验收数量、开始销售数量和差异。
- Seller 后台区分计划日期、实际日期、目的仓和中转仓。
- 已验收数量可能与计划数量不一致。

### 26.2 Ozon

- Ozon 公开接口可以查询供货单列表、详情和 Bundle 商品组成。
- 当前项目已经同步 Ozon 供货单及商品组成，用于平台在途计算。

### 26.3 项目机制

- 平台在途同步到 `Ec::SkuInventoryLevel` 的 `fulfillment_type=inbound`。
- 平台在途会影响分仓位置判断，但待分仓总量由上游补货流程提供。
- 页面 GET 请求不应触发平台同步或状态修复。

## 27. 合理推断

- 计划、发出、验收和可售之间的差异应反馈给上游补货流程及下一轮分仓。
- 已到仓但长期未验收的供货单需要单独预警，不能永久作为正常在途。
- 多货、少货和错货可能表示包装执行、仓库验收或商品绑定存在问题。
- 分仓算法的真实效果应以缺货改善、周转、成本和验收结果衡量，而不只看推荐是否被执行。

## 28. 设计建议

### 28.1 数量状态

```text
recommended_quantity
approved_quantity
platform_planned_quantity
packed_quantity
shipped_quantity
received_quantity
accepted_quantity
available_quantity
discrepancy_quantity
```

这些数量不得互相覆盖，应保留历史变化。

### 28.2 在途状态规则

将平台状态映射为内部状态：

```text
draft
planned
ready_to_ship
shipped
arrived
accepting
accepted
available
cancelled
rejected
stale
```

为每个内部状态明确：

- 是否计入有效在途。
- 抵扣多少数量。
- 多久未更新后进入异常。
- 是否需要人工处理。

### 28.3 对账结果

```yaml
reconciliation:
  supply_id: "40673325"
  planned_quantity: 82
  packed_quantity: 82
  accepted_quantity: 82
  available_quantity: 82
  discrepancy_quantity: 0

```

### 28.4 算法反馈

跟踪以下指标：

- 建议执行率。
- 平台准入通过率。
- 预约成功率。
- 平均到仓时间。
- 验收差异率。
- 上架延迟。
- 分仓执行后的区域缺货率。
- 库存周转天数。
- 付费验收和中转成本。
- 因自动化造成的重复供货次数。

## 29. 待验证

- WB 和 Ozon 每个供货状态的准确语义。
- 哪些状态和数量应计入有效在途。
- 供货单取消后库存建议何时恢复。
- 到仓未验收的预警阈值。
- 验收后未可售的预警阈值。
- 多货、少货、拒收和错货的数据来源。
- 是否能获得包装级验收差异。
- 平台仓间调拨是否会被误判为卖家在途。
- 如何归因缺货改善是分仓效果还是自然销量变化。

## 30. Agent 工具与权限

### 30.1 只读工具

- 查询平台供货单状态。
- 查询商品、包装和验收数量。
- 查询最新可售库存。
- 查询操作审计和历史状态。

### 30.2 可写工具

- 更新内部供货状态。
- 更新有效在途数量。
- 创建差异和超时预警。
- 生成补发、取消或人工核查建议。

Agent 不得仅因为发现差异就自动创建补发单。差异应先返回上游补货流程；只有上游生成新的待分仓任务后，才能重新进入环节零和环节一。

## 31. 审批点与异常处理

- 平台状态与本地状态冲突。
- 计划数量与包装数量不一致。
- 验收数量小于或大于发货数量。
- 已验收但长时间未成为可售库存。
- 取消结果不明确。
- 同一平台供货单被绑定到多个本地计划。
- 差异触发补发后可能造成重复库存。

## 33. 幂等与审计

- 店铺和平台。
- 操作类型。
- 业务幂等键。
- 本地计划版本。
- 请求摘要。

- 平台对象 ID。

## 34. Agent 决策输出格式

每个关键决定应输出：

```yaml
decision:
  action: create_draft
  status: requires_approval
  conclusion: "Create one Ozon FBO draft for the Moscow cluster"
  evidence:
    confirmed_facts: []
    reasonable_inferences: []
  assumptions: []
  unresolved_questions: []
  risks: []
  alternatives: []

```

## 35. 置信度

置信度不能只给一个无解释的分数，应由以下维度组成：

- 商品绑定完整度。
- 销量样本完整度。
- 库存更新时间。
- 在途状态确定性。
- 区域或仓库映射确定性。
- 平台准入结果新鲜度。
- 包装数据完整度。

## 37. SYSTEM 后续扩展顺序

1. 为每条“已确认事实”补充证据链接、接口版本和验证日期。
2. 为每个“待验证”问题指定验证方法和负责人。
3. 确定环节零的合格店铺、历史置信度、经营得分和配额上下限。
4. 确定环节一的平台内分仓参数和回测标准。
5. 定义统一的渠道配额、分仓计划、执行候选、包装和对账数据模型。
6. 为每个平台建立状态映射和接口工具清单。
7. 定义 Agent 可调用工具的输入、输出和副作用。
8. 定义审批、幂等、重试和补偿规则。
9. 使用历史数据回放五个环节。
10. 先上线 L0/L1，再逐步开放 L2 及以上权限。

## 38. SYSTEM 验收标准

未来 SYSTEM 至少应满足：

- 事实、推断、建议和未知项明确分离。
- 每个建议能够追溯到输入数据和策略版本。
- 商品、店铺、平台和仓库不会跨范围混用。
- 无可靠历史数据时，配额能够在合格店铺间按均分基线生成。
- 历史表现只按其数据置信度逐步影响配额，不会直接覆盖冷启动基线。
- 店铺和平台配额受最小探索配额、最大占比和机动库存规则约束。
- 所有平台、店铺配额合计不会超过上游给定的待分仓数量。
- 平台内分仓总量不会超过该店铺在环节零获得的配额。
- 分仓总量不会超过总建议量和本地可发库存。
- 平台实时约束会在提交前重新校验。
- 所有写操作具备幂等、审计和明确权限。
- 异常和不确定情况会停止自动提交并请求审批。
- 对账结果能够反馈到下一轮计算，但不会直接触发无审核补发。
