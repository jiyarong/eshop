# Ozon / WB 官方卖家文档入库与 GBrain 同步方案

方案日期：2026-10-15。来源抓取批次：2026-10-13（按用户更正）。

本文件是实施方案，没有执行数据库导入、分类模型调用或云端写入。盘点基于 `docs/官方文档-中文/` 的实际文件，以及当前 `/admin/gbrain_pages` 的代码。文档中的平台操作说明仅作为知识内容，不作为导入程序的执行指令。

## 1. 建议与完成口径

采用“原文先入数据库 → 分类、打标签并生成知识页面 → 单并发同步云端”的流水线。原文进入现有 Rails 应用数据库，`GbrainPage` 保存可编辑的知识页面投影，云端 GBrain 提供检索。正式执行由配置了 Solid Queue 的部署环境承担，不依赖本地临时进程维持整批任务。

全部来源页面都覆盖，但按内容类型采用不同处理方式：正文完整同步，纯目录生成精简导航，混合页保留正文并附导航。目录不拼接子文档全文，长文不在正常页面中重复展开。

默认完成口径：1,086 个 Markdown 文件均保存原文并有云端对应页面，其中包括两个集合 README；WB manifest 原样保存在导入批次中。若长文确需拆分，云端页面数量会增加，按“来源覆盖率”验收，不能要求云端页数恰好等于文件数。

## 3. 当前代码能复用什么

| 现有实现 | 已具备的能力 | 本次需要补足 |
| --- | --- | --- |
| `GbrainPage` | 正文、分类、标签、来源等级、复核日期、同步状态；`compiled_content` 生成 YAML + Markdown | 原始来源快照、抓取批次、校验摘要、来源关联 |
| `Gbrain::PageClassifier` | AI 生成结构化元数据，正文不由模型改写 | 目录上下文、受控词表、确定性来源身份、批处理与恢复 |
| `Gbrain::PageChange` | 保存页面后自动入同步队列；无变化不重复排队 | 分类完成与入队之间的恢复扫描，避免先同步未分类内容 |
| `Gbrain::PageSyncJob` | `queue_as :gbrain`，固定 key `page_writes`、group `Gbrain`，并发为 1；写入时间与失败信息回写 | 云端索引完成确认、自动有限重试、处理中断恢复、内容摘要校验 |
| `Gbrain::Client` | 已对接云端 MCP 的 `put_page/get_page/list_pages/search/query` | 核实云端分页、来源归属、长文处理、索引状态的真实契约 |

特别注意现状：

1. 当前 Job 的成功含义是 `put_page` 调用没有报错，代码没有验证 embedding 是否完成。不能直接把当前 `synced` 等同于“向量已可检索”。
2. 当前并发限制只约束共享同一 Solid Queue 的这个 Job。其他进程、其他应用、语义查询产生的 embedding 不受这个限制约束。HTTP 返回后若后台仍在 embedding，也不能保证实际并发为 1。
3. 并发锁 duration 为 30 分钟，需要与云端最大任务时长匹配。不能靠固定延迟或任意加长租约解决异步索引、超时后仍在执行的问题。
4. 现有 Job 抛错后保存 `failed`，当前类及 `ApplicationJob` 没有配置自动 `retry_on`；硬中断还可能留在 `syncing`，现有执行入口会跳过这个状态。
5. 当前管理页面远程列表只请求前 100 条后本地分页，不能用它统计本次千篇文档是否全部同步。当前本地列表也没有分页，批量接入时应增加分页并只选择列表需要的列。

## 4. 最小数据结构

建议新增两张业务表，并扩展现有 `gbrain_pages`；不引入第二套向量库或自建 embedding 服务。

### `gbrain_import_batches`：一个平台的一次来源快照

本次建立 Ozon、WB 两条批次记录，均归属集合 `seller-official-2026-10-13`。保存平台、`captured_on=2026-10-13`、实际导入时间、文件数/总字节数、目录清单摘要、状态、原始 manifest 文本及其 SHA-256。WB 另存 `source_retrieved_at=2026-10-13T19:45:58+0800`；Ozon 没有精确抓取时刻，不编造。

批次按平台和来源清单摘要唯一。相同清单重复导入复用批次；同一天文件集合确有改变时保留另一版清单，不以日期单独去重。

### `gbrain_source_documents`：逐文件保存原文与处理进度

保存：

- 批次关联、平台、相对路径、官方来源 URL、稳定来源键。
- `raw_content` 原始 UTF-8 文本（包括 front matter，不做 strip、换行替换或格式修复）、`raw_sha256`、字节数。
- 原始 front matter JSON、官方原始标题（WB 可从 manifest 读取俄文标题）、原始时间字符串、可解析的官方更新时间。
- `document_kind`：`article/directory/mixed/collection_index`。
- 分类状态、分类结果 JSON、分类输入摘要、分类器/词表版本、尝试次数、错误与处理时间。

唯一约束为批次 + 相对路径；另为平台 + 来源键建立查找索引。每个新来源快照保存新记录，保留旧原文。相同快照重复运行不产生重复行。README 按 `collection_index` 存原文；manifest 保存于批次；忽略 `.DS_Store`。

### `gbrain_pages`：沿用当前后台管理的知识页面

新增可空的 `source_document_id`，指向当前投影采用的来源快照；一个来源可对应多个页面，以容纳确有必要的长文拆分。新增期望与已确认同步的 payload SHA-256，并记录写入/索引核验信息。来源记录和原文不会随知识投影删除而删除。

原始文档先进入 source 表，分类完成后才创建或更新完整有效的 `GbrainPage`。现有模型要求新页面同时具备 title、tags、summary 等字段，不应为了“先保存原文”而把半成品塞进现有页面或放宽全部手工页面校验。

后台继续通过 `/admin/gbrain_pages` 查看同步后的投影，增加来源原文、分类结果和批次进度入口即可，不另建一套知识编辑器。导入更新若发现人工编辑导致投影偏离上次生成摘要，应标记冲突保留人工内容，不能覆盖。

## 5. 来源身份、分类与标签

### 身份先确定，AI 不负责决定页面主键

- 来源身份用“平台 + 规范化官方 URL”；有可靠官方 ID 时同时保存。URL 规范化只消除已知无意义差异，不能随意删除业务 query 参数或拼错的官方路径。
- Ozon slug 使用 `sources/ozon/seller-guide/<原文件路径去掉.md>`。
- WB slug 使用 `sources/wb/seller-guide/<官方 material URL 最后一段>`，不依赖可变化的排序编号。
- 两个 README 对应 `sources/ozon/seller-guide/index`、`sources/wb/seller-guide/index`。
- 生成的 slug 统一转小写，来源路径保持原样；例如 `hand-in-UPD-2.md` 映射为 `hand-in-upd-2`。规范化后再次检查冲突。
- 以上规则已对本次清单检查：没有 slug 冲突，最长 Ozon 189 字符、WB 110 字符，均在当前 MCP 读取入口 200 字符限制内。
- 后续路径或 URL 真正迁移时维护来源别名映射；现有 `GbrainPage` 禁止修改 slug，不能让 AI 因分类改变而生成新身份。

导入的是可引用的官方来源，建议统一 `page_type=source`。子类型区分 `official-seller-article`、`official-seller-directory`、`official-seller-mixed`、`seller-guide-index`。业务上的“政策”“操作指南”等另用标签表达，不直接把一切政策原文强制设为 `page_type=policy`：当前模型要求 policy 必须有生效日期，而更新时间、抓取时间均不能充当生效日期。

### 分类分三步

1. **规则提取**：平台、来源 URL、原始标题、目录路径、页面类型、父章节中文标题、官方原 tags。Ozon 用已有 section 文件重建祖先；WB 用 README 与 manifest 获取一级章节，再结合子目录和正文识别二级主题。
2. **受控映射**：将目录和原 tags 映射到固定 topic、业务模式等词表。目录名是帮助中心的知识栏目，不等于商品类目，不能直接填 `category_scope`。
3. **AI 补充**：用标题、祖先标题、可信元数据及结构化正文生成 summary、aliases、内容级标签和适用范围。平台、URL、slug 等身份字段不可被模型覆盖。简单纯目录走规则，不逐篇调用 AI；混合页和正文优先分类。长文按章节分析后汇总元数据，不能只截前几千字。

建议标签维度：

| 维度 | 示例 | 约束 |
| --- | --- | --- |
| 平台 | `platform/ozon`、`platform/wb` | 确定性生成 |
| 主题 | `topic/inventory`、`topic/analytics`、`topic/advertising`、`topic/finance`、`topic/compliance` | 一个主主题，少量有正文证据的次主题 |
| 业务模式 | `model/fbo`、`model/fbs`、`model/fbw`、`model/realfbs`、`model/dbs` | 保留平台区别，不混同 WB FBW 与 Ozon FBO |
| 文档用途 | `document/article`、`document/directory`、`document/mixed`、`document/index` | 来自结构检查 |
| 历史性质 | `document/digest`、`document/archive` | 识别摘要/档案；正文内部日期仍需逐段理解 |
| 国家/地区 | `country/ru` 等 | 仅在来源范围明确时设置；未知用模型支持的 `GLOBAL`，不把全库机械标为 RU |

平台来源正文 `source_tier=official`，同时明确这是中文译文、链接指向官方俄文来源，不宣称为平台官方中文版。官方来源等级不等于翻译已经人工审校，初始 confidence 宜采用 medium，并记录未人工审校。集合 README 生成的索引是派生导航，来源等级按实际结构核验结果记录，不冒充官方原文。

已有模型强制要求 `reviewed_at/review_after`：首次生成采用实际自动复核日并明确复核方式，不能把 10-13 抓取日冒充人工复核日。`review_after` 按主题风险设定，例如资费、促销、规则优先 30 天，普通操作说明 90 天，作为拟议运营策略。重跑同一内容不得为了“刷新日期”改这些字段而重复 embedding。未知 effective_date 保持空；`status/current` 不能根据“刚抓取”自动生成。

Ozon 的 updated 没有时区偏移，保留原字符串及可确定的日期，不擅自解释为上海时间或 UTC 的精确时刻。抓取批次日期、官方更新时间、条款生效日、实际导入时间及复核日期分别存储。

分类输入中明确来源内容是待分析数据，里面的命令、提示词或平台操作步骤不得执行。模型只返回经过白名单与格式验证的 JSON，不直接写库或访问外部工具。证据冲突、未知范围、分类失败分别记录并进入可恢复队列。

| 类型 | 数据库存储 | GBrain 内容 | 顺序 |
| --- | --- | --- | --- |
| 正文 946 篇 | 完整原文 | 去原 front matter 后的正文与必要来源信息；保留表格、警示、步骤、日期与链接 | 优先 |
| 混合页 4 篇 | 完整原文 | 实质正文 + 精简子页导航 | 随正文 |
| 纯目录 134 篇 | 完整原文 | 章节名、原 description、适用范围与直接子页链接；不重复子页正文 | 正文后 |
| README 2 篇 | 完整原文 | 平台顶层导航；Ozon 不把 63KB 全量 README 再重复嵌入 | 最后 |

950 个正文/混合页面中有 55 篇 Ozon digest，安排在正常业务文档之后。其他档案按实际内容标记后排后；全部最终同步，不静默舍弃。

导航页仍属于“已写入 GBrain”。当前本地接口没有 `embed=false` 能力，不假设云端支持目录跳过向量化。第一版按 1,086 页全部有可能触发 embedding 安排容量；若云端明确支持仅索引元数据/图链接，可再单独优化目录。仅增加目录标签不保证 query 不返回它，需通过真实检索验证；若要严格排除，必须有云端过滤/排序能力配合。

### 链接与长文

- 先全量扫描建立来源路径 → 目标 slug 映射，再逐篇流式导入。扫描映射不必等待全文分类。
- 原文中的相对 `.md` 链接不能原样带到云端。匹配到本批次文件时，按核实过的 GBrain 内部链接格式改写；没有收录的目标保留或恢复官方 URL，并记录缺口。保留查询参数和锚点。
- Markdown 转换结果保存在投影，原始 source 内容一字不改；使用 `compiled_content` 时移除被模板重复添加的首个标题，避免嵌套两套 front matter。
- 8 篇大文档先验证 GBrain 自带切块与请求限制；如果能够正确分块，仍保持一来源一页面，不在 ERP 再做相同工作。
- 只有请求/上下文限制或检索效果证实需要时，才按章节、资费版本、城市/仓库等业务边界拆页。保留父页与来源定位，长表在子页重复表头，不截断规则条件，不只保存摘要。拆页 key 不依赖每次波动的纯数字顺序。
- 原文引用的外部图片、PDF、XLSX 等先保留链接。是否下载归档、图片 OCR 或附件正文提取属于后续明确范围，当前 1,086 个 Markdown 的完成率不能冒充附件内容覆盖率。

## 7. 流水线与单并发保证

```mermaid
flowchart LR
  A[扫描来源清单与路径映射] --> B[逐文件保存原文和校验摘要]
  B --> C[提交后进入分类队列]
  C --> D[规则分类和必要 AI 分析]
  D --> E[保存完整 GbrainPage 投影]
  E --> F[gbrain 队列串行写入]
  F --> G[确认远程内容与索引完成]
  G --> H[记录已同步摘要和验收结果]
  D --> R[保存失败状态并有限重试]
  F --> R
  R --> C
```

流水线按篇推进：A 文档等待云端 embedding 时，B/C 文档可继续原文落库、分类。不需要等全部落库后再开始分类，也不需要让所有阶段共用单并发。分类先用独立队列、1 个 worker 起步；写入队列复用现有全局固定键的单并发约束。Worker 处理每篇时只读取该篇内容，列表与进度统计使用 SQL 聚合，避免把全量正文加载进内存。

**真正需要串行的是同一 embedding 服务的请求。** 需要在 GBrain/embedding 调用端设置全局容量 1，覆盖其他写入、其他应用以及 query 产生的向量请求；ERP 单写入队列作为入口限流补充。

- 若 `put_page` 同步完成全部索引，当前调用完成后可以处理下一篇。
- 若 `put_page` 返回的是接收/排队结果，等待该任务明确完成后再释放本次写入占位；保存任务 ID 与状态以便进程恢复。若云端已经用全局单消费者严格串行，可由该消费者保证 embedding 容量，但 ERP 必须保留“已接收”和“索引完成”的区别。
- 若 HTTP 超时，先按 slug、内容摘要或远程任务状态核对结果，不能立即重发或启动下一篇并假设上一篇已停止。没有可核验的索引完成契约时，先补齐云端状态能力，再宣称严格单并发和检索就绪。
- 不在等待网络时持有数据库行锁。领取、状态更新使用短事务与条件更新；锁过期或 worker 退出后由恢复扫描处理，不能直接把 `syncing` 重置后盲目重写。

## 8. 幂等、更新与恢复

分开记录三种摘要：原文件摘要、分类输入摘要、最终云端 payload 摘要。

1. 相同批次、相同路径、相同 raw 摘要：跳过重复入库，恢复未完成阶段即可。
2. 分类输入、分类器版本及词表版本不变：复用分类结果，不重复调用 AI。
3. 最终 payload 与已同步摘要相同：不调用 `put_page`。不能仅按 `updated_at` 判断变化。
4. 新抓取批次即使原文相同，也在数据库保存来源快照；只更新投影来源关联，不因批次号、最新抓取时间、自动刷新复核日期而重写未变化的云端正文。云端显示的是当前内容版本的来源时间，最新检查批次由数据库提供。
5. 标签或正文确实改变才生成新 payload；记录新旧摘要与来源版本。
6. 写入期间出现新版本：旧调用只可确认其捕获的 payload；不得将新版本标为 synced。保留新版本 pending 并继续排队。
7. 可重试的网络错误/限流使用指数退避和有限次数；内容格式、超限、分类校验等进入明确失败状态。单篇终止后其他正常页面继续，但远程仍可能执行的超时任务必须先确认。
8. 数据库保存是处理事实来源；定期扫描“原文已保存但未分类”“投影已生成但无同步任务”“长时间处理中”“写入成功但本地未确认”等状态并补发幂等任务。事务提交后入队与队列数据库之间不能假设绝对原子。
9. 本次来源清单缺失某页面不等于要求删除历史知识。删除、替换与知识归档单独记录；批次恢复不得误删原文或人工页面。

建议本地阶段状态使用 source 的 `stored/classifying/classified/failed`，投影沿用现有写入状态。若云端异步索引，另存远程索引状态 `unknown/pending/ready/failed`，不要用一个状态同时表达原文、分类和检索是否完成。

## 9. 实施步骤与验证

### 第一步：预检与小批试导入

先实现只读 dry-run：输出来源数、拟定 slug、分类候选、目录树、时间异常、链接异常和请求体大小，不调用平台 API 或写入 GBrain。

随后选择 12 篇在目标部署环境做可控试导入：覆盖 Ozon/WB 普通正文、纯目录、四个混合页中的重要业务说明、未知更新时间、历史档案、两篇同名不同来源，以及最大仓库地址表。这个阶段核实：

- `put_page` 是覆盖更新还是会追加重复内容；成功响应是否表示 embedding 完成。
- 云端单并发的实际覆盖范围、超时后任务状态、可用索引状态字段。
- front matter 与内部链接的真实支持格式；来源 `source_id` 如何归属。
- 长文切块、最大请求限制、表格和锚点检索。
- 完成耗时、重试次数、排队情况与正文级检索质量。

当前 `Gbrain::Client#put_page` 只传 slug/content，不能据此假设在 front matter 写一个 `source_id` 就能形成真实检索隔离。可拟定 `ozon-seller-official`、`wb-seller-official` 两个来源键，但必须核实云端来源注册/映射契约后生效。

### 第二步：全量流式运行

按已有来源顺序逐文件落库，分类后依据业务优先级排入云端队列：库存、供货、物流、退货、资费、财务、广告、商品与分析 → 其他正文 → 历史摘要/档案 → 纯目录与平台索引。目录标签和祖先上下文来自预扫描，不依赖目录已写入云端。

同步后台展示各批次总数、原文已保存、待分类、待写入、索引待确认、失败、已完成。失败支持按阶段重试，暂停时停止派发新云端写入，保留已在执行任务的核验。

### 第三步：完整验收

- 原文：两个批次覆盖全部 1,086 个 Markdown，逐篇 SHA-256 与磁盘一致；manifest 原始文本摘要一致。
- 分类：950 个正文/混合页和 136 个导航/集合索引都有有效映射或明确可处理的失败记录；完成验收时失败应清零或逐项明确接受原因，不能悄悄跳过。
- 来源：1,084 个官方页面 URL 均保留；47 个未知更新时间未被伪造；同名页面未合并；4 个混合页正文未丢失。
- 同步：按已知来源映射逐 slug 核对远程投影内容、版本摘要与索引完成状态；不用当前后台前 100 条列表估算覆盖率。
- 检索：分别验证两平台“库存/补货”“退货”“广告计费”“销售漏斗”“佣金/资费”，并增加“采购资金暂不可用”、本地化加价取消及不同时间条款的案例。确认答案引用完整正文、适用条件、来源和日期，没有把目录或历史摘要当当前规则。
- 并发：验证实际 embedding 请求最大并发为 1，包括索引异步、超时、重试和其他调用入口，不能只看 ERP 同步 Job 数。
- 恢复：模拟分类失败、写入失败、云端成功但本地进程中断、内容处理中更新；恢复后无重复版本被错误标为成功。
- 幂等：同一来源清单再运行一次，新增原文记录数、AI 分类次数、云端 put 次数均为 0，未完成任务除外。

实施代码测试覆盖上述状态转换与边界，使用 FakeClient 验证请求，不在 Rails 测试中访问云端。相关 Rails 命令先初始化项目 rbenv；migration 使用 `rails generate migration` 生成。正式运行前仍须先完成下方的 dry-run 和小批验证。

### 容量估算

不拆页时约 1,086 次初始 put；每页内部可能产生多次 embedding 请求，需以试导入实测为准。若实测平均每页完整写入与索引耗时分别为 10/30/60 秒，则串行阶段约为 3.0/9.1/18.1 小时，加上重试与核验。这是情景估算，不是对当前云端速度的测量。
