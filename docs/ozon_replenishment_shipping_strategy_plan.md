# Ozon 补货数量与箱送 / 托盘策略改造方案

日期：2026-10-21。范围：现有 Rails 项目的 Ozon FBO 补货工作台、打托计算器及供货链路。

本文是分析和建议设计，不表示规则、策略参数或箱送执行功能已经上线。现有几何算法可继续复用，主要改造需求边界、货位分类、费用报价与方案选择。

## 1. 对改进意见的判断

| 意见 | 判断 | 实现时需要补足的条件 |
|---|---|---|
| 超出普通件的任一边上限才进入 KGT | 对俄罗斯 FBO 资料，这是合理的互斥解释；现有实现把不可分拣普通件也归入 KGT | 三边先从大到小排序；还要检查单件重量，普通件上限为 35kg；特殊品类和平台实际仓储区另行判断 |
| 补货量应有上下区间 | 合理，28 天适合作为目标，不能同时成为自动装托的绝对上限 | 明确最低、目标、最高覆盖天数；整箱取整、库存、到货时间都参与约束 |
| 有空间就多放一些，可以降低越库成本 | 在同托且未跨计费台阶时，新增运输费可能为零 | 分拣、包装、仓储、资金和滞销风险仍可能增加；占用的托盘空间也可能排挤更急的 SKU |
| 动态规划解决选品与装载 | 可以用于有限离散候选的组合选择 | 总问题同时包含库存决策、固定费用和三维装箱，不能用一个体积背包替代实际几何校验 |
| 优先考虑按箱送，托盘明显划算时再用 | 适合作为待比较的业务策略 | 箱送必须合法可用；运输货位中的箱子上托后，越库仍按普通托盘计费，不能误当作按箱计费 |

建议产品目标：在满足补货服务要求、库存和平台约束的前提下，选择总成本较低的补货数量与发运方式。装载率只作辅助指标。

## 2. 当前实现及具体缺口

| 位置 | 当前行为 | 本次改造 |
|---|---|---|
| `app/models/ec/sku_dimension.rb` | 单品三边排序后，`>=45 / >=32 / >=32` 任一满足即 `kgt`；重量只判断 FBO 上限 120kg | 区分可分拣普通件、不可分拣普通件与 KGT；补齐 10kg、35kg 的分层解释 |
| `app/services/ec/ozon_warehouse_recommendation_query.rb` | 缺口为 `ceil(日均销量 × target_days) - 可售 - 在途`，默认 28 天 | 保留现有报表口径，工作台新增数量区间及到货覆盖的解释，不静默改变全站报表 |
| `app/services/ec/pallet_plans/workbench_query.rb` | 建议箱数为缺口向上取整，再受可分配库存限制 | 输出最低 / 目标 / 最高箱数、对应件数和覆盖天数 |
| `app/javascript/controllers/pallet_workbench_controller.js#recommendOne` | 从全部筛选结果中按缺口、日销、SKU 排序，取前 5 个，再提交建议箱数 | 将策略选品移到服务端；当前前 5 个候选不等于最经济的一托 |
| `app/services/ec/pallet_plans/packing.rb` | 在既定数量上限内选择组合，偏好外箱体积、重量与 SKU 数；不会主动增加到需求上限以外 | 增加需求与成本编排层，复用装托服务校验候选 |
| `app/services/pallet_packing/calculator.rb` | 稳定条带分区 + beam search；内层评分首先偏好覆盖更多 SKU | 保留几何内核；让编排层比较多种可行布局，避免几何评分先丢掉经济性更好的单 SKU 方案 |
| `app/services/pallet_packing/fees.rb` | Ozon FBO 仅有托盘费用，路线价手填；分拣模式和仓储费率整批统一 | 扩展箱 / 托报价、按货位组成识别分拣、按 SKU 计算预计仓储，保留费用未知状态 |
| `app/models/raw_ozon/cross_dock_tariff*.rb` | 已有箱 / 托路线价、生效期快照；基础金额只是体积乘费率 | 直接复用数据；上层补逐货位取整、托盘最低体积、点位费、折扣和日期选择 |
| `app/services/ec/pallet_plans/ozon_supply_runner.rb` | 创建货位固定提交 `type: "PALLET"`，结果回填到 `Ec::Pallet` | 箱送真实执行需要独立接入 BOX 货位及回读，不是更换计算器按钮即可完成 |

当前 `normal/kgt` 还影响同托分组。分类变化会改变可混托范围和费用，不能只改页面显示。当前每托最多 5 SKU 是工程边界，应继续明确标注，不能称为 Ozon 通用上限。

## 3. 分类规则：把重叠表转成互斥判断

以带最终销售包装的**单件商品**为准；外箱用于装托与箱货位重量检查。不能把整箱尺寸用来判断商品是否为 KGT。

俄罗斯 FBO 建议按以下顺序解释；这是对官方重叠区间的实现规则，执行前仍要与该账号、目的仓的实际商品标签核对：

```text
L >= M >= S，分别为排序后的长边、中边、短边；W 为单件包装重量

资料缺失、非正数                       → unknown，阻止自动推荐
L > 220 或 M > 120 或 S > 80 或 W > 120 → 不满足通用 FBO 上限
L > 120 或 M > 60  或 S > 50 或 W > 35  → KGT
L <= 45 且 M <= 32 且 S <= 32 且 W <= 10 → 普通可分拣件
其余                                   → 普通不可分拣件
```

边界等于普通件上限时仍在普通件范围。45 / 32 / 32 是区分可分拣与不可分拣的边界，不应直接用作 KGT 触发线。

例如：`78×52×5cm、5kg` 应作为普通不可分拣候选；`130×50×20cm、7kg` 为 KGT；`40×30×20cm、36kg` 也为 KGT。小尺寸不抵消超重条件。

兼容建议：`ozon_size_category=normal` 暂时继续覆盖两类普通件，单独在分类结果与方案快照中记录 `storage_zone`。混托和分拣判断使用明确仓储区，不能因为两者都是 normal 就视为同区。平台已有明确仓储区时优先采用该事实，特殊品类不靠尺寸推断。

官方资料有市场和页面差异：CIS 大件页仍保留 45/32/32 下限；其货位页的不可分拣中边上限还出现 80cm，与俄罗斯资料 60cm 不同。本方案首先针对俄罗斯 FBO，不将一套数值无条件推广到全部市场。

商品为普通件，也不等于一定允许散箱送货。例如单件 30kg 尚未触发 KGT 重量线，但已超过普通箱货位 25kg 的限制；多件外箱超过 25kg 时只有在允许重新包装并有准确箱规的情况下才能拆箱。

## 4. ZJ004 的 14 与 18：真正要比较的是什么

本次没有收到原图和该方案的店铺、集群、库存与包装快照，以下仅分析文字中的假设，不能当作对 ZJ004 实际排布的复算。

假设“14 件对应 28 天”表示零期初库存、每箱一件、稳定日销 `0.5 件/天`：

| 补货件数 | 覆盖天数 | 相对 14 件 |
|---:|---:|---|
| 14 | 28 | 基准 |
| 15 | 30 | 增加 2 天 |
| 17 | 34 | 增加 6 天 |
| 18 | 36 | 增加 8 天；比基准数量增加约 28.6% |

若最高覆盖设为 35 天，18 件即使装得下也不能自动推荐，最多只能发 17 件。若放宽至 42 天，则 18 件才进入可比较范围。如果 14 / 18 指的是箱数，必须乘每箱件数后重新计算。

实际 14 件通常只是扣减现有库存和在途后的缺口，不等于 28 天全部需求，因此不能直接用 `28/14` 推出日销或增量天数。

“多放一件运输免费”需要同时满足：仍为同一托、未跨最低计费体积、路线及折扣不变、没有额外出车或货位。即使这些条件成立，新增分拣费、材料人工、净新增持有成本、滞销风险仍应计算。

判断多发的依据是：多发是否能在共同计划周期内减少后续发运成本或缺货损失，并且收益超过上述新增成本。未来仍要发同样次数、同样最低收费的托盘时，不能虚构一次“省下的未来运费”。

## 5. 补货区间与库存时间口径

建议先试算 `最低21 / 目标28 / 最高35天`。这三个数是待业务验证的策略参数，不是平台规则；新品、零销量及销量失真 SKU 先保留人工决策。

沿用同店铺、同集群、同 SKU 的需求范围。记：

- `d`：有效预测日销，首版复用现有日均销量，同时保留统计区间和可信度。
- `I_eta`：本次预计上架时点的可用库存预测，按日期纳入现有可售和能及时到达的承诺量，再扣预计销售；未满足的历史需求不能自动当作仍待履约订单。
- `m`：每完整外箱件数；`A`：排除当前编辑计划自身占用后的实际可分配件数。

```text
最低箱数 = ceil(max(d × 最低天数 - I_eta, 0) / m)
目标箱数 = ceil(max(d × 目标天数 - I_eta, 0) / m)
天数支持的最高箱数 = floor(max(d × 最高天数 - I_eta, 0) / m)
库存支持的最高箱数 = floor(max(A, 0) / m)
允许最高箱数 = min(天数支持的最高箱数, 库存支持的最高箱数)
```

几何容量由具体方案校验，不能把各 SKU 单独满托容量同时视为混托可用容量。

最低箱数超过允许最高箱数时，输出无法补足及原因。目标箱数因整箱取整突破最高覆盖时，也要展示冲突，不能静默突破上限。最高天数按入仓后覆盖定义时，不再重复加一次运输提前期。

`I_eta` 必须按时间处理：本次上架后才到的在途不能防止此前缺货；尚未绑定、已取消、跨集群的计划不直接减少当前缺口。继续复用现有承诺去重逻辑，平台在途和对应本地计划不能扣两遍。到货时间未知时，保留“按当前库存位置计算”的降级结果，并明确不是到货覆盖预测。

## 6. 箱送 / 托盘：先可行，再比较费用

需要区分三个概念：商品最终销售包装、运输箱、平台申报货位。供货路线的 DIRECT / CROSSDOCK 与 BOX / PALLET 是两个独立维度。

| 方式 | 实物与申报 | 越库计费 | 关键条件 |
|---|---|---|---|
| 普通箱货位 | 按箱提交组成及标签 | 每箱商品体积分别向上取整，再按箱路线价计算 | 每箱最多 25kg；普通供货通常最多 30 箱；点位、总体积和商品准入通过 |
| 普通托盘货位 | 按托提交组成及标签，托上可有多个外箱 | 每托至少 1900L，使用托盘路线价 | 含托尺寸 120×80×220cm、货重最多 800kg；实际几何可行 |
| 运输货位 | 托盘作为运输货位，内部箱另填组成并分别贴标 | 官方说明越库费用与普通托盘相同 | 账号逐步开放；官方页面为最多 1500 箱，每箱最多 230 SKU；需单独核实 API 能力 |

CIS 准备供货页要求超过 30 箱或 1000L 时使用托盘。俄罗斯合同第 9.1 条另明确同车超过 30 箱须上托，不因拆成多票而豁免；其第 2.3.4 条的 1m³ 则是 Ozon 提供卸货的条件，不能单凭这一条推导俄罗斯所有场景的散箱禁令。箱数、体积和卸货要求必须按市场、交付方式与点位分别核实，不能混用这些资料。PVZ / PPZ 只收箱；KGT 在 SC 必须上托。

运输货位不是免除托盘最低计费体积的办法。它是否能降低某项入库处理费，需要核对处理规则，不能从“内部是单 SKU 箱”直接推导整托免分拣。

## 7. 费用计算和经济比较

### 7.1 报价输入与来源

复用 `RawOzon::CrossDockTariffSnapshot.for_effective_date` 和 `CrossDockTariff#rate_for`，按预计交货日期、适用市场、发货点费率区和目标集群匹配箱 / 托价。保存快照 ID、费率、生效期、折扣资格及计费基数。

`is_current` 是导入状态，不足以证明适用于发货日期。实际费用在交货时锁定；预约或发货日期改变并跨费率版本时重新报价。10 月 21 日当前段与 10 月 30 日未来段分开，不引用 7 月旧知识库里的 0.75 / 0.15 ₽/L 作为当前仓/SC 额外处理费。现有路线单价数据库字段仅保留两位小数，本地旧工作簿存在四位小数单价；报价接入时须先核对并保留原始费率精度，最终金额再按结算口径舍入。

当前在线 CIS 费用页显示仓/SC 处理费已包含在物流中，PVZ 箱 5 ₽/L、PPZ 箱 4 ₽/L。本地俄罗斯 10 月资料另含 Pick-up 1.55 ₽/L 和出车费；这些项目必须按实际点位和版本匹配，不能整批套固定默认值。

未知路线与“不归属费率区”的平台明确情况不同，不能查不到路线就自动套 1.5 ₽/L。无有效报价时显示费用未知，停止“最省钱”自动结论。

### 7.2 基本公式

```text
V_j = 第 j 个货位中 Σ(商品件数 × 单件销售包装体积L)
箱路线运输费 = Σ ceil(V_j) × 对应箱路线价 × 有效运输折扣系数
托路线运输费 = Σ max(ceil(V_j), 1900) × 对应托路线价 × 有效运输折扣系数

本次发运总成本 = 路线运输 + 点位处理/取货 + 入库分拣
               + 自有仓至交货点运输 + 包材/托盘/人工 + 实际出车固定费
```

物理装载体积用外箱尺寸；越库体积用单件销售包装体积之和；分拣按商品件数及单件体积计算。平台已有计费体积时采用该来源，本地包装尺寸推算只能作为估算并保留来源说明。箱路线费按每个箱货位取整，不能先把整批商品体积合并取整。最低 1900L 按每托应用，不能只对整批应用一次。

分拣不能给所有方案强制同一个模式：单 SKU 组成正确与多 SKU 同区混货的费用不同；跨区、纠错和优惠资格另算。仓储成本应使用预计逐日库存、适用仓储区费率与剩余免费期，不能对全部发出件数统一乘“28天 × 默认仓储价”。

### 7.3 两层比较，避免不同数量的假节省

第一层固定同一目标补货清单与时效要求，比较合法的箱、托及组合方案。这时能直接解释“换交付方式节省多少”。

第二层才改变补货量。在共同计划周期（例如 56 天，具体周期由补货节奏确定）内比较：

```text
计划周期成本 = 本次及周期内后续发运成本
             + 预计库存持有成本 + 缺货损失 + 滞销/过期风险
             + 期末剩余库存的后续成本调整
```

同时报告最低覆盖缺口和目标覆盖偏差。下限不足的方案不能只因便宜被推荐为达标。不要只比较总运费或单件运费，也不要把多发的商品全部算成新增销售利润。

自有仓库存本来就已购入，资金成本比较应体现提前转入 FBO 与留在自有仓的净差异，不能再次计入整笔采购成本。缺少可靠持有成本、后续补货或损失参数时，只给出物流费用比较和覆盖变化，标明经济比较未完成，不宣称最优收益。

运费示意（非实际报价）：箱价 10 ₽/L、托价 8 ₽/L，700L 同一清单，箱路线费约 7000 ₽、托最低 15200 ₽，还需分别加其余成本。简化交点为 `1900×8/10=1520L`；对于执行散箱 1000L 上限的场景，这个交点已不可行，其他场景仍须检查箱数、重量、点位和整车规则，不能把数学交点直接当作可执行方案。

## 8. 推荐算法与实现边界

采用“有限候选数量 + 既有几何内核 + 费用比较”，先交付可解释的启发式方案。普通一维动态规划只适合简化后的离散选择；总体问题包含三维几何、SKU 数量上限、仓储区、分拣阶梯和固定费用，不保证全局最优。

流程：

1. 批量获取当前筛选范围的有效 SKU、销量、库存、承诺、包装及规则和费率快照。
2. 计算需求区间，先保障最低覆盖，目标天数作为可解释偏好；库存不足时报告未满足量。
3. 固定目标数量生成同清单的箱 / 托基准方案；为真正存在剩余空间和经济收益的 SKU 生成逐整箱增量候选。
4. 分仓储区和平台准入形成候选池。按紧急程度、边际收益及装载形状保留有限候选；不能先固定取前 5 个便不再考虑其他 SKU。
5. 单 SKU、多 SKU 混托、纯箱候选分别保留。单托仍最多 5 SKU；手工指定一托不得静默拆托。以 beam search / 局部替换选择有限组合，缓存相同输入的几何计算。
6. 对最终候选逐托校验尺寸、重量、支撑、朝向及逐 SKU 数量守恒，再计算准确费用。几何不通过的候选不参与经济推荐。
7. 输出基准、推荐和未满足需求；每项数量变化都有理由。混合箱/托首先作为组合方案，真实提交按平台是否允许混合或需拆票决定，库存合计只扣一次，固定费按实际发运次数计算。

搜索上限和候选池大小通过基准测量确定；超时返回当前可行方案及搜索受限说明，不宣称全局最优。当前计算器的几何最优候选也不是经济最优证明。

## 9. Rails 落地结构

首阶段只新增必要的独立职责，不建立通用求解平台：

- 分类规则：修正 `Ec::SkuDimension` 的俄罗斯 FBO 基础判断，输出两类普通件的仓储区依据。需要按市场区分时，在工作台上下文显式选择规则，不能用一个全局持久字段代替全部市场准入。
- 需求区间：在 `Ec::PalletPlans` 下增加需求区间服务，复用 `Availability` 和工作台已有批量数据，避免每个候选重复查询。
- 费用报价：在现有 `PalletPacking::Fees` 周围增加箱 / 托报价入口，复用现有费率模型；统一金额精度、拆项和未知数据协议。
- 方案选择：在 `Ec::PalletPlans` 下增加推荐编排服务，负责候选与评分，几何仍交给 `Packing/Calculator`。前端提交策略与约束，服务端重新读取并校验。
- 计划快照：保存策略版本、覆盖区间、数据截至时间、基准与推荐数量、货位清单、规则与费率依据及费用拆项。已有历史计划保留原快照，不因分类修改重写历史排布和费用。

箱送仅做预览时可先使用结果快照。需要真实保存、占用、提交与回读时，建议增加最小化的箱货位及明细记录，与现有 `Ec::Pallet/PalletItem` 并存，共享 `PalletPlanItem`；不能把 25kg 箱货位伪装成托盘。运输货位的嵌套关系待账号/API 能力核实后再落库，首版不预建完整包装树。

`Save/Build/Workflow/Availability/OzonReconciler/OzonSupplyRunner` 都要覆盖箱货位。BOX 的真实 schema、条码、`quant`、货位 ID 回填与规则校验先用官方 schema 和实际测试样本确认，不能只将 PALLET 字符串替换为 BOX。继续保留写前持久化、互斥锁、响应不明后的查询恢复及禁止盲目重试。

新增数据结构使用 `rails generate migration`。旧草稿采用新规则时显式重新计算；已确认、已绑定或提交中的计划沿用冻结版本与现有编辑限制。

## 10. 页面结果与实施顺序

页面建议展示可比较方案，而不是只有“装满一托”按钮：

- 目标补货清单的箱送基准：箱数、件数、费用拆项、预计上架时间、排除原因。
- 目标补货清单的托盘基准：托数、利用率、同清单费用差。
- 允许增补的推荐：多发哪些 SKU、件数、覆盖变化、当次新增费用、周期预计收益及依据。

每行可查看最低 / 目标 / 最高数量；操作文案使用 zh/en/ru I18n。继续 Rails ERB + Turbo，复用现有人员/SKU/日期/表格组件。保留修改后旧结果失效、revision 丢弃旧响应、保存前重新校验、一次撤销及按计划隔离本地草稿。

推荐拆成四个可独立验收的交付：

| 阶段 | 交付 | 验收 |
|---|---|---|
| A：规则和数据基线 | 分类互斥解释、重量分层、需求区间展示、按日期选费率 | 边界与代表 SKU 结果可解释；梳理所有因分类变化受影响的草稿；缺失数据保持未知 |
| B：同量箱托比较 | 纯预览箱 / 托报价及可行性检查 | 同一清单与服务要求下逐货位对账；无合法箱方案时不参与低价推荐 |
| C：有限增补推荐 | 在覆盖上限内寻找经济性更好的数量与布局 | 能解释为何选 14 / 15 / 17 / 18；未减少后续费用时不伪造收益；能优先给更急 SKU 留空间 |
| D：箱送真实执行 | 保存、库存承诺、BOX 提交、回读及恢复；具备权限后再接运输货位 | 与现有托盘路径共同通过权限、数量、状态、幂等和异常恢复验收 |

先做 A、B 可最快验证“哪些品适合箱送”。C 必须使用 B 的费用口径；D 依赖箱报价与平台货位能力验证，不把未接通的预览伪装成可提交方案。

## 11. 测试与验收清单

1. 分类边界：120/60/50 与刚超限；35kg 与刚超重；45/32/32、10kg；220/120/80、120kg；三边任意输入顺序；单品与外箱独立；未知及特殊仓储区。
2. 数量：每箱 1 / 多件；取整导致无解；缺口为零；库存不足；不同日期在途；本地/平台承诺去重；编辑排除自身占用；零销量与销量不可靠。
3. 费用：每箱单独进位；每托最低 1900L；新开一托台阶；单 SKU / 同区混 SKU / 跨区差异；折扣仅作用于合格项目；固定费按实际批次只计一次；费率 10 月 29/30 日边界；无报价不补 0。
4. 策略：假设日销 0.5 时 14/15/18 对应 28/30/36 天；最高 35 天拒绝 18；增加商品但不改变未来发运次数时不能声称省下一次运费；相同输入结果稳定；未达最低覆盖显式报告。
5. 货位：单件 30kg 与多件外箱 30kg 的差异；31 箱、适用场景的 1000L 边界及同车跨票箱数；普通箱、普通托与运输货位区别；平台不支持混合时拆分及数量守恒；每托 5 SKU 工程限制。
6. 执行：BOX/PALLET 分别回填；计划、货位、平台三层逐 SKU 数量一致；可见范围与管理权限；响应不明不重建；确认时重新查库存和规则版本；历史计划快照不被覆盖。
7. 性能：代表性单 SKU / 多 SKU 输出对照；关闭 query cache 后记录 SQL 次数、最大 SQL 长度和实例化条数，验证候选数增长不造成逐候选 SQL；几何耗时与数据查询耗时分开报告。

实现后运行相关 Rails 模型、服务、Controller 测试；修改 Stimulus 时运行既有相关 JS 测试。真实数据性能验证保持只读，平台写入测试另按执行阶段范围进行。本文只新增方案文档，没有进行业务代码变更或测试通过声明。
