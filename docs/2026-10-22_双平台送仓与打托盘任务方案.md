# 任务二：双平台库存分配、送仓规划与箱托执行方案

整理日期：2026-10-22。适用项目：白俄罗斯自有库存面向 Ozon FBO、WB FBW 的送仓经营与执行；FBS 作为共享自有库存的需求方和占用来源参与计算，不能将 FBS 托盘收货规则直接套用于 FBO 送仓。

依据：两段会议记录、当前工作区静态代码核查、现有 `docs/platform_warehouse_allocation_meeting_brief.md`、GBrain 平台资料。本文是实施建议；没有运行测试、查询真实业务数据库或平台实时接口，没有修改业务代码。职责、排序规则和工作量均待业务确认。

## 1. 任务目标和边界

**先从共享可用库存出发，确定哪些 SKU 应分给哪个平台、店铺和区域，再在本次运力、平台准入与经济性约束下，生成可解释、可人工调整、可实际执行的送仓与箱托方案。**

会议应整理为以下业务链路：

```text
统一销量与库存口径、取得候选SKU及待分仓上限
 → 跨平台/店铺分配
 → 平台内集群或区域分配
 → 相容商品组成运输候选批次
 → 核对准入、路线、时段及费用规则
 → 箱送/托送/分批方案比较与装载验证
 → 人工确认
 → 库存预留 + 平台建单或导出材料
 → 打包、出库、在途、验收、费用对账
```

遵循已有分仓会议文档的边界：补货或经营决策上游提供候选 SKU 和待分仓总量/上限，分仓模块负责既定数量的去向，不自行发起采购。会议提出的“自动选品池”，可在上游利用销量、缺口和库存批量生成；运营不必凭记忆逐个选品。

待分仓上限不等于必须全部发走。运力不足、缺乏有效需求、利润不足或规则不明时，必须允许留仓、延期和未分配，并说明原因。

## 4. 第一优先级：把四种数量彻底分开

| 指标 | 明确定义 | 不应直接解释为 |
|---|---|---|
| 预测销量 | 某店铺/履约模式/区域、某未来区间的预计需求 | 可以从自有仓发出的数量 |
| 需求缺口 | 预计需求减去同口径可售库存及有效到货后的不足 | 最终送仓建议 |
| 可分配库存 | 指定库存池中，扣除已占用和保护量后，可供本次分配的库存 | 各平台各自独占的全量库存 |
| 建议送仓量 | 缺口、共享库存配额、利润、整箱、运力、准入等约束后的建议 | 实际已发货或已扣减的数量 |

当前两个建议字段已经有限制，不能统一说成“都只是全平台缺口”：

```text
送仓工作台建议件数 = min(目标集群 shortage, max(fbs_allocatable, 0))
打包工作台建议箱数 = min(ceil(shortage / 每箱件数), floor(max(allocatable, 0) / 每箱件数))
```

但两者尚未解决跨平台竞争同一库存、整车运力和边际收益选择，因此离会议所需的最终智能送仓建议还有差距。

另一个问题是**预测口径不一致**：当前“严格预测28天”为动态日预测×28，使用库存快照及订单回退；仓库缺口基于所选区间销量÷天数×目标覆盖天数。两者不同不必然是算术错误，但应明确标签、窗口和来源；若未来用严格预测驱动建议量，必须统一整个计算链和回归基线。

## 5. 数据审计与预测基线

### 5.1 先复现会议中的异常

选取会议异常 SKU，并补充正常畅销、退货多、缺货、新品、同 SKU 多店铺等代表样本，逐行列出：

- 内部 SKU、平台商品硬关联、店铺、履约模式、目标集群。
- 查询时间、用户时区、历史窗口、完整日数、是否含今天。
- 下单数、取消数、签收数、退货数、净销量，分别注明事件日期。
- 订单日销量、库存快照日销量、有效在售天数及断货天数。
- 平台可售、锁定/已下单、有效在途及到货日期。
- 页面预测、缺口、建议件数/箱数与人工复算结果。

需要检验：周销量是否错误再乘7；累计量是否被当成日均再乘28；一对多关联是否重复计数；跨店铺/集群是否重复覆盖；快照是否迟到；退货是否被二次扣除。

当前仓库推荐销量排除了 `cancelled/returned` 订单，库存账另外处理退货分配。这是已知代码口径，不是本次已发现的错误。是否按订单整体状态处理会影响部分退货，需用样本核实。

### 5.2 预测与财务销量分开

建议基础需求使用明确的有效订单/成交需求口径；财务净销量用于利润核对，不直接用“本周成交减历史退货”代表未来需求。退货只有确认回到可售库存后才能回补可供应量。

历史销量因缺货被压低时，提供有效在售天数和置信度；新品、无有效天数和数据缺失，不自动解释为零需求。第一阶段先选定一套可复现基线，再评估动态预测是否优于基线，不在数据未核对时继续叠加复杂模型。

SKU 归属继续遵守 `ec_sku_products` 的店铺、平台、平台商品ID硬关联，不使用订单冗余 `sku_code` 或 `offer_id` 兜底。

## 6. 库存与缺口的建议计算口径

以下是待业务批准的目标定义，不描述当前代码已经实现。

### 6.1 共享库存上限

```text
本次可分配量 A
 = max(0, 已核实的自有仓可用实物
          − 尚未体现在库存中的FBS待发占用
          − 其他已确认执行占用
          − FBS/自有业务未来安全保护量)
```

要逐项核对现有库存服务是否已扣减，禁止重复减。隔离、残次和不可售库存不进入“可用实物”；若已排除，也不能再扣一次。

共享的前提是库存所有权、法人、仓库、批次、销售资格允许共享。当前基础库存存在店铺口径，不能不经核对就把全 SKU 数量合并成可跨店自由调用的公共池。

### 6.2 在到货时点计算缺口

对每个 SKU × 平台 × 店铺 × 集群，统一同一预测函数和时间轴：

```text
预计新货可售日 T = 发货日 + 国内/跨境运输 + 平台分拨 + 验收上架时长
T时点预计可售库存 = max(当前真正可售库存 − 现在至T的预测消耗 + T前能到的有效在途, 0)
目标覆盖需求 = T后目标覆盖天数内的预测需求
目标缺口 = max(目标覆盖需求 − T时点预计可售库存, 0)
```

上述简式假设在途时序不会额外影响消耗；正式实现按日推进库存与到货，日终库存不能小于0，缺货日丢失的销售另记。如果库存不足后的销售已丢失，不能继续把它当成到货后必须补交的积压订单。到货前不可挽回的缺货天数和到货后可避免的缺货收益分别展示；只有确实存在的延期未履约订单才单独计入需求。

在途按预计日期与目的地归属计入，已取消、拒收、过期或与已预留批次重复的记录不能再加。平台可售字段是否已经净掉锁定订单需明确，避免重复扣减。

最低/目标/最高覆盖天数输出三个缺口区间；沿用项目已有补货区间配置与校验，不把会议中的28天写成所有 SKU 固定规则。

### 6.3 整箱和配额

先对共享库存分配店铺配额，再计算各集群整箱建议。必须满足：

```text
所有平台/店铺/集群分配件数之和 ≤ 同一库存池的可分配量A
单店铺各集群分配件数之和 ≤ 该店铺配额
分配件数 = 箱数 × 每箱件数（要求整箱的场景）
```

向上补齐缺口造成的超目标量要显示；不能因各集群分别向上取整而突破总库存。残余散件可留仓；允许散件时须作为独立获准的包装方式，不默认拆箱。

## 7. 分配优先级：先硬规则，再引入优化

“利润高”建议解释为**同一币种、同一观察期下的预期增量贡献**，而非售价、历史利润总额或单件利润率。Ozon、WB 报表币种不同，比较前要采用一致汇率与税务口径。

建议第一版采用透明的分层决策：

1. 排除无资格、无可分配库存、包装不完整、已明确不接收的候选；缺少关键数据的候选进入待核实池，显示阻塞原因。
2. 对可在到货后改善缺货、预期贡献为正的 SKU，先补至最低覆盖；库存不足时按预计可避免的利润损失排序。
3. 剩余库存与运力用于补至目标覆盖，按整箱边际贡献排序。
4. 达到目标后是否补至最高覆盖，须同时考虑额外仓储、滞销和资金占用；不因“车还没装满”自动发出低价值商品。
5. 新店、新品或低置信度 SKU 使用明确的小额试销配额/人工确认，不以缺失历史利润默认判定为负收益，也不默认均分全部库存。

业务若要求战略保供或必须发出的 SKU，作为明确优先项及审批记录，不藏在模型权重里。胡源需要确认“利润最大化”和“最低覆盖保障”冲突时的业务优先级。

可用于比较方案的指标：

```text
预期方案贡献
 = 预计新增可成交件数 × 可比的单件贡献
   − 本次新增自有运输、越库、点位处理与分拣成本
   − 新增仓储、资金和滞销风险成本
```

同一笔费用只能计一次。若单件贡献已扣除送仓成本，方案级不能再次全额扣除。新增可成交件数应受观察期需求和原有库存约束，不能把所有送仓件数都当成未来必然销量。

不建议第一版让大模型直接输出最终数量。AI 可解释推荐和异常；数量由固定规则与约束计算产生，保留输入和版本供复现。

## 8. 运力和箱托规划

### 8.1 本次运力必须先输入

至少有：出发仓、可交货时间、最大载重（含箱/托自重）、托位数、车厢长宽高、可堆叠要求、卸货条件、路线与运输报价。只有托位数和吨位而无车厢几何时，只能做容量初筛，不能声称整车装载已验证。

物流可给多个车型/班次报价。运力不足时允许部分发出、延期或新增班次比较，不保证“装满一车”就是最佳方案。

### 8.2 三个层次的约束分开

| 层次 | 约束例子 |
|---|---|
| 商品准入 | 单件最终销售包装尺寸、重量、危险品/特殊存放区、账号资格 |
| 供货与货位 | 单箱重量、单托高度重量、混装、货位数量、标签和供货单归属 |
| 车辆运输 | 车厢尺寸、整车总重、托位、装卸顺序、稳定性、路线和时效 |

同一车能送往同一明斯克交货点，不代表不同目的集群、供货单、店铺或存放区可以混在同一个托盘。第一版优先按已确认的供货单/目的地/存放区隔离，多个子计划可以合车；只有平台明确支持时再开放混装。

### 8.3 方案生成方法

第一版使用规则分组、确定性排序及现有几何算法验证：

1. 对相容 SKU 建立候选批次；按目的地、货位限制和存放区分组。
2. 为同一候选清单生成可行的箱送、托送或分批方案。
3. 复用现有 `Packing/BoxPacking` 检查实际摆放，不以体积相加替代几何可行性。
4. 加入车辆装载、总重和托位验证；现有单托限制不能代替整车限制。
5. 对库存配额、数量及费用反馈进行有限次调整。任何减量、删 SKU 或延期均显示前后差异并由运营确认。

可输出保守易执行、成本较低、缺货风险较低等少量不同方案。沿用既有分仓文档：目标3–5套**通过验证**的候选；只有1套可行就输出1套，不凑数。不宣称启发式结果是全局最优。

若后续实际规模和成本差异证明需要，再引入整数规划/约束求解，并与可行基线比较。三维排布、跨平台配额及阶梯运费不是简单一维动态规划问题，不宜在第一版承诺一个算法同时精确最优。

### 8.4 完整成本拆分

比较至少分列：

- 自有仓至交货点的卡车、司机、装卸、包装耗材费用。
- 平台路线运输、交货点处理和货位分拣费用。
- 预计仓储和资金占用成本及依据。
- 已验证折扣、税费及未知项目。

知识库示例中的 Ozon 托盘最低计费体积、逐货位取整，只有在账号与路线适用性确认后才纳入。物理外箱体积、商品体积之和、平台计费体积各自保留。

缺费率时显示已知费用小计和未知项。两方案均有未知的关键费用时，不能给出确定的“最省钱”标签。允许基于准入或容量推荐可行方式，并明确费用尚未完整。

## 9. 状态、库存和计划追踪

会议所说“建计划后扣库存”应分为**可分配库存预留**与**实物出库**。计划创建不等于货已离仓。

| 状态/事件 | 库存处理 | 注意事项 |
|---|---|---|
| 自动建议、候选方案、预估送仓计划 | 不扣实物、不占执行库存 | 多套候选互斥，不能同时预留 |
| 用户确认执行批次 | 原子校验并预留 | 与 FBS 订单和其他平台计划竞争同一合法库存池 |
| 打包/已打包、尚未出库 | 保持预留 | 实物仍在自有仓 |
| 平台正式建单成功 | 记录单号，按原执行预留处理 | 建单成功不推断已打包或已发出 |
| 实际出库/已发出 | 实物出库转在途，预留转移或抵扣 | 不能再从自有可用量重复减同一批商品 |
| 验收/上架、部分收货 | 按确认数量逐步结清在途 | 不以整单 completed 推断件数全部一致 |
| 发出前取消 | 释放未出库预留 | 平台取消结果不明时保留待核实 |
| 发出后取消/拒收 | 进入异常或退回在途 | 不自动恢复自有可售库存 |

现有 `PalletPlan` 的 `reserved/packing/packed/dispatched` 属于占用状态，并通过 `max(units − platform_covered_units, 0)` 避免重复覆盖，应在该机制内设计跨平台扩展。`draft` 和 `DeliveryPlan` 目前不占库存；改变语义必须评估所有入口，不能在父计划和执行批次同时扣减。

并发确认需要共享库存业务键上的串行保护或等价数据库约束；只锁一份送仓父计划不能保证两个独立计划之间不超分。取消、编辑、重复请求和状态回读要保持幂等。建议先梳理现有锁和库存来源，再确定最小改动方案。

## 10. 页面和导出方案

继续使用 Rails Controller + ERB + Turbo/Stimulus，复用现有 SKU/人员/日期/多选筛选、排序、表格和抽屉组件；三种 locale 经 I18n 提供文案。

建议在现有送仓工作台增加联合规划入口，界面按业务顺序展开：

1. 规划周期、库存池、店铺范围、出发点和本次运力。
2. 自动候选 SKU 池，可按商品或集群视角切换；不受列表分页限制。
3. 每个 SKU 展示双平台配额、目标区域缺口、到货时间、库存保护量、建议箱数、利润依据和缺失信息。
4. 运营调整数量，系统重新计算全局库存、运力和费用；保留人工调整理由。
5. 方案比较、箱托明细、未分配清单和执行确认。

Excel 可先交付人工试运行，但必须附数据截止时间、时区、规则版本、单位、配额守恒、已知/未知费用、未选原因。建议工作表：候选池、平台店铺分配、集群分配、供货批次、箱托清单、运力成本、待核实项。

Excel 是决策和执行辅助，不自动占库存或执行平台操作；导出后再次确认须重新核验可用库存与版本。

## 11. 技术接入建议

优先添加一个跨平台决策/运输批次编排层，关联多个现有平台执行子计划；不要把当前单店铺、单集群 `PalletPlan` 改成无法校验的一张多平台大单。

最小输出对象包括候选需求、库存池及保护量、平台店铺配额、集群分配、方案版本、车辆/波次、子执行计划与差异说明。最终是否新增模型、表或服务类，留待详细技术设计和代码检查后决定，本文不提前固化架构或迁移。

查询必须复用项目 SQL 范围下推、Relation 子查询、批量聚合和预加载约束。联合决策同一数据快照内复用销量、库存、利润和映射，避免按 SKU×店铺×集群逐项循环查询。

页面 GET 保持只读。平台实时准入查询若需要创建临时草稿，应作为显式后台动作记录外部副作用和有效期，不在 GET 或 AI 自由循环里重复创建。正式写操作继续由后台 Job → 平台 Client 执行，不把 API 调用放入核心 `Ec::*` 报表查询。

## 12. 建议阶段与交付

工作量仅为排期讨论起点，以一名熟悉项目的开发人员与运营可及时复核为前提，外部账号权限、运力资料和附件缺失会影响时间。不以日期替代验收门槛。

| 阶段 | 主要工作 | 交付与进入下一阶段的条件 | 粗略工作量 |
|---|---|---|---|
| S0 数据与规则审计 | 复现会议异常、统一预测/缺口、库存池和成本口径；核实明斯克点位 | SKU逐项复算表、数据差异原因、执行关键规则清单 | 3–5人日 |
| S1 Ozon硬规则与人工试运行 | 自动候选池、FBS/WB库存保护、Ozon店铺/集群分配、未分配原因、Excel | 库存守恒；每项建议可解释；运营可以按表执行和反馈 | 5–8人日 |
| S2 运力与经济方案 | 车辆约束、边际价值排序、分拣费用与箱托比较、多集群运输批次 | 同批次各子计划合计正确；至少有可行基线；费用不重复 | 8–12人日 |
| S3 Ozon闭环加固 | 复用后台建单、确认预留、出库/在途/验收对账、幂等与异常恢复 | 人工确认后执行；重复请求和响应不明不重复建单；数量对账 | 5–8人日 |
| S4 WB执行适配与联合分配 | 核对WB实际点位与费用能力，接入计划/包装，API可用则接入，否则导表 | 同一库存池Ozon+WB+FBS不超分；WB执行材料与平台记录匹配 | 另行评估，先做能力盘点 |

S0 与知识库任务的规则盘点、校验原型并行；S1 可以用已确认的规则先试运行。S2 的自动费用排序必须依赖关键规则通过验收。Ozon 当前已有执行链路，S3 是整合和加固，不应重复开发整套 API。

## 13. 验收清单

### 数据与建议

- 同 SKU 多店铺、多平台归属正确；无硬关联的订单不会纳入。
- 周销量、日均、28天预测各有明确窗口、单位、公式和复算样本。
- 取消、部分退货、晚到财务记录、断货和无数据均有回归案例。
- 同一库存池所有平台、集群、FBS保护与执行占用之和不超上限；不存在两次向上取整超分。
- 到货前断货、迟到在途、新品无历史和负利润候选有明确处理结果。

### 装载与费用

- 车辆载重含托盘/包装自重；平台单托限制和整车上限同时满足。
- 箱、托、普通货位、运输货位与不同存放区不混用。
- 选中的 SKU、箱数、件数和实际几何结果一致；未选和减量均可解释。
- 相同清单的箱托比较计费基数、最低收费、取整、折扣和日期版本正确。
- 已知费用与未知项目分开；无完整报价时不输出确定性最低总价。
- 至少覆盖“装载率更高但利润更低”“单件利润更高但周转慢”“高紧急度但来不及到货”案例。

### 执行和性能

- 候选与草稿不错误占用；确认、并发、取消、部分发出/收货、拒收和重试保持数量守恒。
- 外部响应不明不盲目重建，供货成功不错误推进实物状态。
- 运行相关 Rails/Stimulus 回归；不主动启动浏览器或前端构建。
- 在只读代表数据上比较完整输出、未命中缓存SQL数、最大SQL长度、实例化记录数；批量规划不随SKU×集群数量产生可合并的循环查询。
