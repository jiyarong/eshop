# SKU 工作台首页性能优化

测量日期：2026-10-20。

## 修改范围

- 默认利润排序的周报在同一请求内传给当前页指标查询，复用完整指标和环比；复用前核对周报日期范围。
- SKU 的 SPU、营销状态、开发人员和运营人员关联在分页后预加载。
- 诊断、计划筛选的 SKU 范围使用 Relation 子查询，避免先加载全量 ID 和无关关联 JOIN。
- 计划弹窗批量预加载评估，继续按观察结束日、ID 选择最新结果。
- WB/Ozon 漏斗先限定账号、平台商品和日期，再按账号、商品、自然周在 SQL 汇总，避免加载账号下所有商品的每日模型。

## 本地完整请求对比

本地 development 数据库共有 238 个可见 SKU；使用已有管理员，测量无筛选参数的 HTML `GET /operator_skus`，包含默认利润排序、第一页 10 个 SKU 的指标、筛选组件、计划弹窗和布局渲染。业务时间固定为上海时区 2026-10-20 12:00。数据库事务设置为只读，关闭 ActiveRecord query cache；未触发平台同步、补数据或后台任务。

耗时为独立 Rails 进程首次请求的单次样本，包含开发环境加载和相同的通知订阅开销；没有清空数据库及操作系统缓存，不作为生产性能承诺。最长 SQL 来自既有 WB 财务归因的商品/条码筛选。

对剩余耗时靠前的销量、库存账本、库存周转查询及最长 WB 财务 SQL 执行了只读 `EXPLAIN (ANALYZE, BUFFERS)`。销量/库存命中 SKU 商品索引、订单明细 Bitmap 扫描和订单主键索引；WB 财务使用 Bitmap 扫描。此次执行时间分别约为 30.2、19.7、11.7、4.8 ms，因此没有新增索引。

## 结果与回归

- 对比全部 238 个 SKU 的利润排序值、当前页完整指标（包括环比、库存预测及漏斗利润预估）和去除随机 CSRF 令牌后的整页 HTML，结果一致。
- 计划从 1 条增加到 3 条时，评估 SQL 均为 1 条；验证较早观察周期的记录即使晚创建，也不会取代最新周期结果。
- 漏斗从 1 个增加到 2 个 SKU 时，SQL 数量不增长，每日记录实例化为 0；覆盖两个自然周的首尾边界和未绑定商品排除。
- 周报复用测试对比所有利润指标与环比，同时验证其他周的报表不会复用。
- 相关 Rails 测试：25 runs、334 assertions，全部通过。路径为 `test/controllers/operator_skus_controller_test.rb`、`test/controllers/reports_sku_access_test.rb`、`test/services/ec/operator_sku_metrics_query_test.rb`、`test/services/ec/operator_sku_sales_funnel_metrics_query_test.rb`。
- 对 8 个修改的 Ruby 文件运行 RuboCop：修改行无新增告警；整文件检查仍有 41 条既有布局格式告警，未扩展修改无关行。
